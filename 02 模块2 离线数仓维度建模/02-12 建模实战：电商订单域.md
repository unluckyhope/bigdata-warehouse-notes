# 02-12 建模实战：电商订单域

> [!abstract] 一句话结论
> 建订单域不是「写几张表」，而是一条五步闭环：**定边界（域）→ 定过程（总线矩阵）→ 定粒度（四步法）→ 定口径（指标字典）→ 定运维（分区/幂等/校验）**。
> 任何一步跳过，都会在三个月后以「数据对不上」的形式回来找你。本篇用中型电商的体量从 ODS 走到 ADS。

---

## 一、心智模型：一条链路，五个决策点

```
需求：「我要看每天的 GMV、转化率、复购」——不要直接写 SQL
① 边界：订单/明细/支付/退款 + 用户/商品/店铺/地区/渠道
② 过程：下单 / 支付 / 退款 / 加购 / 浏览
③ 粒度：订单×商品 / 一次支付 / 一次退款 / 一个订单（累积快照）
④ 口径：GMV 有下单/支付/成交三种，先定义再算
⑤ 运维：dt 分区 + overwrite + 六段校验 + 生命周期
```

三条铁律：**粒度先于指标**、**口径先于 SQL**、**幂等先于调度**（不能重跑的任务不配上调度）。

| 对象 | 规模 | 说明 |
| --- | --- | --- |
| 日订单 / 日明细 | 200 万 / 600 万 | 平均一单 3 个商品 |
| SKU / 用户 | 50 万 / 3000 万 | 在售约 20 万 |
| 明细 3 年 | 65.7 亿行 | parquet 约 1~1.6 TB |

---

## 二、核心知识点

### 2.1 业务背景与源表清单

业务形态：**自营**（自己发货）、**平台**（商家入驻、抽佣）、**直播**（达人带货、分成）。三者共用交易链路但结算与履约不同——所以 `dim_shop.shop_type` 必须是一等维度，否则按业务类型的分析都要重做。

| 源表 | 说明 | 日增 | 入仓 |
| --- | --- | --- | --- |
| `ods_order` / `ods_order_item` | 订单主表 / 明细 | 200 万 / 600 万 | CDC 增量 |
| `ods_payment` / `ods_refund` | 支付流水 / 退款单 | 220 万 / 8 万 | CDC 增量 |
| `ods_user` / `ods_sku` / `ods_shop` | 用户 / 商品 / 店铺 | 3 万 / 1 万 / 200 | 每日全量 |
| `ods_log_page_view` | 埋点 | 2 亿 | 日志落表 |

类型约定：主键/外键 `bigint`，金额 `decimal(18,2)`，时间 `timestamp`，枚举 `string`。状态枚举：`order_status` CREATED/PAID/SHIPPED/FINISHED/CANCELLED；`pay_status` INIT/SUCCESS/FAIL；`refund_status` APPLY/AGREE/SUCCESS/REJECT。

```
ods_order      order_id｜user_id｜shop_id｜order_status｜order_time｜pay_time｜channel_id｜province_code｜total_amount
ods_order_item order_item_id｜order_id｜sku_id｜shop_id｜quantity｜item_amount｜pay_amount｜refund_status
ods_payment    payment_id｜order_id｜user_id｜pay_channel｜pay_amount｜pay_status｜pay_time｜trade_no
ods_refund     refund_id｜order_id｜order_item_id｜refund_amount｜refund_type｜refund_status｜refund_time
ods_user       user_id｜user_name｜phone｜gender｜birthday｜user_level｜city_code｜register_time
ods_sku        sku_id｜sku_name｜category1_id｜category2_id｜category3_id｜brand_id｜shop_id｜price
ods_shop       shop_id｜shop_name｜shop_type｜merchant_id｜main_category｜status
ods_log_page_view  log_id｜user_id｜session_id｜page_id｜sku_id｜event_type｜channel_id｜event_time
```

### 2.2 步骤 1：数据域与主题划分

原则：**按业务过程划域，不按部门划域**——按部门划（运营/财务/供应链）会让同一份订单建三遍、口径三套。

| 数据域 | 边界 | 事实表 | 主要维度 |
| --- | --- | --- | --- |
| 交易域 | 下单 → 支付 → 退款 | 明细/支付/退款三张事务事实 + 一张累积快照 | 日期/用户/商品/店铺/渠道/地区 |
| 流量域 | 浏览、加购、收藏 | `dwd_traffic_page_view_di` | 日期/用户/商品/渠道/地区 |
| 用户域 / 商品域 / 公共域 | 注册、等级、地址 / SKU、类目、品牌 / 日期、地区、渠道 | — | 用户（SCD2）、商品、店铺 + 三张静态维 |

**订单域边界**：从「提交订单」到「退款完成」；**不含**库存扣减（供应链域）、券核销（营销域）、物流轨迹（履约域）——这些域通过 `order_id` 关联，但不混进本域事实表。

> [!important] 边界的作用是「拒绝」
> 划域的价值是有依据地把东西挡在外面：营销域算用券占比，应自己建券事实表再关联，而不是往明细加 10 个券字段——每加一个外域字段，粒度、更新频率、负责人都会模糊。

### 2.3 步骤 2：总线矩阵

| 业务过程 | 日期 | 用户 | 商品 | 店铺 | 渠道 | 地区 |
| --- | --- | --- | --- | --- | --- | --- |
| 下单 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 支付 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 退款 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 加购 | ✅ | ✅ | ✅ | — | ✅ | ✅ |
| 浏览 | ✅ | ✅ | ✅ | — | ✅ | ✅ |

**一行=一张事实表，一列=一个一致性维度**；同一列在所有行里必须是同一维表、同一套编码。

| 维度 | 主键 | 来源 | 更新方式 | 说明 |
| --- | --- | --- | --- | --- |
| `dim_date` | `date_key` | 静态 | 一次性 | 节假日、促销日 |
| `dim_user_scd2` | `user_id`+`start_date` | `ods_user` | SCD2 拉链 | 等级、地址会变 |
| `dim_sku` | `sku_id` | `ods_sku` | 每日全量（SCD1） | 类目调整不回刷历史 |
| `dim_shop` | `shop_id` | `ods_shop` | 每日全量（SCD1） | 类型极少变 |
| `dim_channel` / `dim_region` | `channel_id` / `region_code` | 静态 | 一次性 | 4 渠道 / 省市大区 |

> [!warning] 一致性维度不是「同一张表」，是「同一套编码」
> `dim_sku.shop_id` 与订单表的 `shop_id` 必须指向同一个 `dim_shop.shop_id`。「商品表存商家 ID、订单表存店铺 ID」会让按店铺汇总全错——而且 join 得上，不报错。

### 2.4 步骤 3：四步法建模 + 完整 DDL

| 业务过程 | 粒度声明 | 维度 | 事实（度量） | 表 |
| --- | --- | --- | --- | --- |
| 下单 | 一个订单的一个商品 | 日期/用户/商品/店铺/渠道/地区 | 件数、商品金额、优惠、运费、实付 | `dwd_trade_order_detail_di` |
| 支付 | 一次成功支付 | 日期/用户/店铺/渠道 | 支付金额 | `dwd_trade_order_pay_di` |
| 退款 | 一次退款成功 | 日期/用户/商品/店铺 | 退款金额 | `dwd_trade_refund_di` |
| 履约 | 一个订单（多里程碑） | 日期/用户/店铺/渠道/地区 | 订单/支付/退款金额 | `dwd_trade_order_process_acc` |

```sql
-- ① 订单明细事务事实表（下单时点快照，只追加）
create table dwd.dwd_trade_order_detail_di (
  order_id bigint comment '订单ID', order_item_id bigint comment '明细ID',
  user_id bigint comment '用户ID', sku_id bigint comment '商品ID', shop_id bigint comment '店铺ID',
  channel_id int comment '1App/2小程序/3H5/4直播', province_code string comment '收货省',
  order_time timestamp comment '下单时间', quantity int comment '件数',
  item_amount decimal(18,2) comment '商品金额=单价×件数', discount_amount decimal(18,2) comment '优惠分摊',
  freight_amount decimal(18,2) comment '运费分摊', pay_amount decimal(18,2) comment '实付金额'
) comment '一行=一个订单的一个商品'
partitioned by (dt string comment '业务日期=下单日期 yyyy-MM-dd')
stored as parquet tblproperties ('parquet.compression' = 'SNAPPY');

-- ② 支付事实表（只入 SUCCESS，按支付成功日分区）
create table dwd.dwd_trade_order_pay_di (
  payment_id bigint, order_id bigint, user_id bigint, shop_id bigint, channel_id int,
  pay_channel string, pay_amount decimal(18,2), pay_time timestamp, trade_no string
) comment '一行=一次成功支付' partitioned by (dt string) stored as parquet;

-- ③ 退款事实表（只入 SUCCESS，按退款成功日分区）
create table dwd.dwd_trade_refund_di (
  refund_id bigint, order_id bigint, order_item_id bigint, user_id bigint, sku_id bigint,
  shop_id bigint, refund_amount decimal(18,2), refund_type string,
  apply_time timestamp, refund_time timestamp
) comment '一行=一次退款成功' partitioned by (dt string) stored as parquet;

-- ④ 订单累积快照（按 order_dt 分区，只重写变化分区）
create table dwd.dwd_trade_order_process_acc (
  order_id bigint, user_id bigint, shop_id bigint, channel_id int, province_code string,
  order_time timestamp, pay_time timestamp, ship_time timestamp, finish_time timestamp,
  cancel_time timestamp, refund_time timestamp, current_status string,
  order_amount decimal(18,2), pay_amount decimal(18,2), refund_amount decimal(18,2)
) comment '一行=一个订单的当前全貌' partitioned by (order_dt string comment '下单日期')
stored as parquet;

-- ⑤ 流量事实表 dwd_traffic_page_view_di 略（字段同埋点，去 referer，按 dt 分区）

-- ⑥ 维表：用户拉链 + 商品/店铺日快照 + 静态维
create table dim.dim_user_scd2 (
  user_id bigint, user_name string, phone string, gender string, birthday date, user_level string,
  province_code string, city_code string, register_time timestamp,
  start_date string comment '生效日期', end_date string comment '失效日期，9999-12-31=当前', is_current tinyint
) comment '主键 user_id + start_date' stored as parquet;

create table dim.dim_sku (
  sku_id bigint, sku_name string, category1_id bigint, category2_id bigint, category3_id bigint,
  brand_id bigint, shop_id bigint, price decimal(18,2), cost_price decimal(18,2), status string
) comment 'SCD1，每日全量' partitioned by (dt string) stored as parquet;

create table dim.dim_shop (
  shop_id bigint, shop_name string, shop_type string, merchant_id bigint, main_category string,
  province_code string, open_time timestamp, status string
) comment 'SCD1，每日全量' partitioned by (dt string) stored as parquet;

create table dim.dim_date (date_key string, year int, quarter int, month int, day int, week int,
  weekday int, is_weekend tinyint, is_holiday tinyint, promotion string) comment '静态' stored as parquet;
create table dim.dim_region (province_code string, province_name string, city_code string,
  city_name string, region_name string) comment '静态' stored as parquet;
```

> [!important] 明细表里为什么没有 `order_status`
> 事务事实表只记录「下单那一刻确定的事」。状态会变（PAID→SHIPPED→FINISHED），放进来就得每天回刷历史分区——那就变成累积快照了。**一条事实只记一次，状态变化另建一张表**。

### 2.5 步骤 4：拉链表每日合并与时点关联

`dim_user_scd2` 用「每日全量重写」：3000 万用户 × 1.3 个版本 ≈ 4000 万行，重写 10~20 分钟，换来**绝对幂等**。到 3 亿用户再改增量 merge（见 02-06）。

```sql
insert overwrite table dim.dim_user_scd2
with src as (
    select user_id, user_name, phone, gender, birthday, user_level,
           province_code, city_code, register_time, update_time, '${biz_date}' as start_date
    from ods.ods_user where dt = '${biz_date}' and is_deleted = 0
),
dedup as (   -- 同一天多次变更只取最后一次，否则出现两条相同 start_date
    select * from (select *, row_number() over (partition by user_id order by update_time desc) rn
                   from src) t where rn = 1
),
changed as ( -- 只保留真正变化的字段
    select d.user_id, d.user_name, d.phone, d.gender, d.birthday, d.user_level,
           d.province_code, d.city_code, d.register_time, d.start_date
    from dedup d left join dim.dim_user_scd2 o on d.user_id = o.user_id and o.is_current = 1
    where o.user_id is null   -- md5 打包比较，比逐字段 <> 少写一半
       or md5(concat_ws('|', d.user_name, d.phone, d.user_level, d.province_code, d.city_code))
       <> md5(concat_ws('|', o.user_name, o.phone, o.user_level, o.province_code, o.city_code))
),
all_ver as (   -- 只取 10 列，与 changed 对齐（dim 有 12 列）
    select user_id, user_name, phone, gender, birthday, user_level,
           province_code, city_code, register_time, start_date from dim.dim_user_scd2
    union all select * from changed
)
select user_id, user_name, phone, gender, birthday, user_level,
       province_code, city_code, register_time, start_date,
       coalesce(date_sub(next_start, 1), '9999-12-31') as end_date,
       case when next_start is null then 1 else 0 end as is_current
from (select *, lead(start_date) over (partition by user_id order by start_date) as next_start
      from all_ver) t;
```

> 生产上在 `all_ver` 后加 `row_number() over (partition by user_id, start_date)` 去重兜底。

**历史订单关联「下单时点」的用户属性**：

```sql
select o.order_id, o.user_id, u.user_level as user_level_at_order, u.province_code as province_at_order
from dwd.dwd_trade_order_detail_di o
join dim.dim_user_scd2 u
  on o.user_id = u.user_id
 and o.order_time >= cast(u.start_date as timestamp)
 and (u.end_date = '9999-12-31' or o.order_time < cast(date_add(u.end_date, 1) as timestamp))
where o.dt = '${biz_date}';
```

> [!danger] 三个必须注意的点
> 1. **必须带时间条件**，否则一个用户的所有版本都匹配，订单数翻几倍。
> 2. **`9999-12-31` 要特判**：`date_add('9999-12-31', 1)` 在 Hive 里可能溢出返回 NULL，当前版本全被过滤。
> 3. **非等值 join 走不了 hash join**：600 万 × 4000 万会跑到天亮。生产上先聚合到订单粒度、只取 2~3 个属性，或建日快照用 `dt` 等值 join。

### 2.6 步骤 5：DWS 层——为什么是这三个粒度

| 表 | 粒度 | 服务对象 | 主要指标 |
| --- | --- | --- | --- |
| `dws_trade_user_1d` | 用户 × 日 | 用户运营、复购 | 下单数/金额、支付单数/金额、退款金额 |
| `dws_trade_sku_1d` | 商品 × 日 | 商品/类目运营 | 下单件数/金额、退款金额、买家数 |
| `dws_trade_shop_1d` | 店铺 × 日 | 商家运营、治理 | 订单数、支付金额、退款金额、买家数、新买家数 |

**为什么是这三个**：它们是订单域**稳定的分析主体**，对应三条业务线；渠道/地区作为维度列冗余可上卷，真正的渠道 UV 在流量域算——**跨域去重指标别硬塞进来**。**为什么不是更少**：只建宽表，下游每次都得从 600 万明细聚合，买家数也无法复用。

```sql
-- 用户日粒度：先聚合再 join，避免明细放大（01-04 的结论）
insert overwrite table dws.dws_trade_user_1d partition (dt = '${biz_date}')
with ord_u as (
    select user_id, count(distinct order_id) order_cnt, sum(pay_amount) order_amount, sum(quantity) item_cnt,
           max(channel_id) channel_id, max(province_code) province_code
    from dwd.dwd_trade_order_detail_di where dt = '${biz_date}' group by user_id
),
pay_u as (select user_id, count(distinct order_id) pay_order_cnt, sum(pay_amount) pay_amount
          from dwd.dwd_trade_order_pay_di where dt = '${biz_date}' group by user_id),
ref_u as (select user_id, sum(refund_amount) refund_amount
          from dwd.dwd_trade_refund_di where dt = '${biz_date}' group by user_id)
select coalesce(o.user_id, p.user_id, r.user_id) as user_id, nvl(o.channel_id,-1) channel_id,
       nvl(o.province_code,'-1') province_code, nvl(o.order_cnt,0) order_cnt, nvl(o.order_amount,0) order_amount,
       nvl(o.item_cnt,0) item_cnt, nvl(p.pay_order_cnt,0) pay_order_cnt, nvl(p.pay_amount,0) pay_amount,
       nvl(r.refund_amount,0) refund_amount
from ord_u o full join pay_u p on o.user_id = p.user_id
            full join ref_u r on coalesce(o.user_id, p.user_id) = r.user_id;
```

> [!note] 商品 / 店铺两张表同构
> 把 `group by user_id` 换成 `sku_id`/`shop_id`，聚合列换成 `sum(quantity)`、`sum(pay_amount)`、`count(distinct user_id)`，再 `left join` 当日退款；**先聚合再 join**，否则退款会被放大。新买家 = 当日首单，**别扫全历史**（65 亿行），维护 `dws_user_shop_first_buy` 增量 merge。

### 2.7 步骤 6：ADS 层与指标口径

| 口径 | 时间锚点 | 是否扣退款 | 典型用途 | 数值关系 |
| --- | --- | --- | --- | --- |
| 下单 GMV | 下单时间 | 否 | 需求热度、活动效果 | 最大 |
| 支付 GMV | 支付成功时间 | 否 | 实际收款、财务口径 | 中 |
| 成交 GMV | 支付成功时间 | 是（扣当日退款） | 净收入、经营分析 | 最小 |

```sql
-- 一张表三个口径，靠 gmv_type 区分：下游选口径就是选一行
insert overwrite table ads.ads_gmv_d partition (dt = '${biz_date}')
with o as (select sum(pay_amount) amt, count(distinct order_id) cnt, count(distinct user_id) buyer_cnt
           from dwd.dwd_trade_order_detail_di where dt='${biz_date}'),
p as (select sum(pay_amount) amt, count(distinct order_id) cnt, count(distinct user_id) buyer_cnt
      from dwd.dwd_trade_order_pay_di where dt='${biz_date}'),
r as (select sum(refund_amount) amt from dwd.dwd_trade_refund_di where dt='${biz_date}')
select '${biz_date}' dt, 'order' gmv_type, o.amt, o.cnt, o.buyer_cnt from o
union all select '${biz_date}', 'pay', p.amt, p.cnt, p.buyer_cnt from p
union all select '${biz_date}', 'trade', p.amt - nvl(r.amt,0), p.cnt, p.buyer_cnt from p cross join r;

-- 转化率：浏览 → 加购 → 下单 → 支付，按渠道
insert overwrite table ads.ads_trade_convert_rate_d partition (dt = '${biz_date}')
with tr as (select channel_id, count(distinct case when event_type='VIEW' then user_id end) uv,
           count(distinct case when event_type='CART' then user_id end) cart_uv, count(*) pv
           from dwd.dwd_traffic_page_view_di
           where dt='${biz_date}' and user_id is not null group by channel_id),
od as (select channel_id, count(distinct user_id) order_uv
       from dwd.dwd_trade_order_detail_di where dt='${biz_date}' group by channel_id),
pa as (select channel_id, count(distinct user_id) pay_uv
       from dwd.dwd_trade_order_pay_di where dt='${biz_date}' group by channel_id)
select t.channel_id, t.pv, t.uv, t.cart_uv, nvl(o.order_uv,0) order_uv, nvl(p.pay_uv,0) pay_uv,
       round(nvl(o.order_uv,0)/t.uv, 4) order_rate, round(nvl(p.pay_uv,0)/t.uv, 4) pay_rate
from tr t left join od o on t.channel_id=o.channel_id left join pa p on t.channel_id=p.channel_id;
```

> [!warning] 转化率的分子分母不同源
> 分母来自流量域埋点、分子来自交易域，两域用户识别口径不同（未登录、跨设备、多账号），转化率**只看趋势，不做绝对值考核**；要考核就用 `session_id` 做同源漏斗。复购同理：维护 `dws_user_trade_accum`，别扫全历史。

| 指标 | 英文名 | 口径定义 | 分子 | 分母 | 维度 | 更新 | 负责人 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 下单 GMV | `gmv_order` | 按下单时间的商品实付金额，不扣退款/取消 | `sum(pay_amount)` | — | 日期/渠道/店铺 | T+1 | 交易数仓 |
| 支付 GMV | `gmv_pay` | 按支付成功时间的支付金额 | `sum(pay_amount)` | — | 日期/渠道/店铺 | T+1 | 交易数仓 |
| 成交 GMV | `gmv_trade` | 支付 GMV − 当日成功退款 | `sum(pay)-sum(refund)` | — | 日期/店铺 | T+1 | 交易数仓 |
| 支付转化率 | `pay_rate` | 当日支付用户数 / 当日浏览用户数 | `count(distinct pay user)` | `count(distinct view user)` | 日期/渠道 | T+1 | 增长 |
| 复购率 | `repurchase_rate` | 当日支付用户中历史支付单数 ≥2 占比 | `repurchase_cnt` | `buyer_cnt` | 日期/等级 | T+1 | 用户运营 |

### 2.8 步骤 7：分区与生命周期

| 表 | 分区键 | 粒度 | 保留 | 存储 | 归档 |
| --- | --- | --- | --- | --- | --- |
| `dwd_trade_order_detail_di` / `pay_di` / `refund_di` | `dt`（下单/支付/退款日） | 日 | 3 年 | 热 30/温 150/冷 2.5 年 | 满 1 年转月分区 + zstd |
| `dwd_trade_order_process_acc` | `order_dt` | 日 | 3 年 | 同上 | 终态订单满 1 年归档 |
| `dwd_traffic_page_view_di` | `dt` | 日 | 180 天 | 热 7/温 173 | 不归档，到期删 |
| `dim_user_scd2` | 无（全量重写） | — | 永久 | — | 历史版本可归档 |
| `dim_sku` / `dim_shop` | `dt` | 日 | 1 年 | — | 到期删旧快照 |
| `dws_*_1d` / `ads_*_d` | `dt` | 日 | 3 年 / 永久 | 小 | 不归档 |

依据：① 事实表按业务日期（90% 查询按天）；② 埋点 180 天，体积大、可重算性差；③ ADS 体量小、历史价值高。

### 2.9 步骤 8：幂等与重跑

每个任务只做一件事：**用 `${biz_date}` 覆盖自己的分区**——`insert overwrite table t partition (dt='${biz_date}')`。Spark 上必须同时 `set spark.sql.sources.partitionOverwriteMode = dynamic`，否则静态模式会覆盖全表。

```bash
#!/bin/bash
set -e
BIZ_DATE=$1
[ -z "$BIZ_DATE" ] && { echo "usage: $0 yyyy-MM-dd"; exit 1; }

# 1 ODS 就绪检查（上游没到就别跑）
hive -e "select count(*) from ods.ods_order_item where dt='${BIZ_DATE}'" | grep -q "^[1-9]"   || { echo "ODS not ready"; exit 2; }

# 2 DWD（可并行）
for t in dwd_trade_order_detail_di dwd_trade_order_pay_di dwd_trade_refund_di; do
  hive -e "insert overwrite table dwd.$t partition(dt='${BIZ_DATE}') select ... where dt='${BIZ_DATE}'"
done

# 3 累积快照：只重写受影响的下单分区
hive -e "set spark.sql.sources.partitionOverwriteMode=dynamic; insert overwrite table dwd.dwd_trade_order_process_acc partition(order_dt) select ..."

# 4 维表 → 5 DWS → 6 ADS（严格串行）
hive -e "insert overwrite table dim.dim_user_scd2 select ..."
hive -e "insert overwrite table dws.dws_trade_user_1d partition(dt='${BIZ_DATE}') select ..."
hive -e "insert overwrite table ads.ads_gmv_d partition(dt='${BIZ_DATE}') select ..."

# 7 校验（失败要阻断）
hive -f check_gmv.sql --hivevar biz_date=${BIZ_DATE}
```

> [!danger] 重跑的两个禁忌
> 1. **不要并发跑同一张表的不同日期**——`select max(dt)` 之类隐式依赖会互相踩，日期必须显式传参。
> 2. **不要「先删分区再跑」**——中间失败会让分区为空，下游读到 0；`insert overwrite` 本身是原子的（写临时目录再替换）。

### 2.10 步骤 9：六段校验

| # | 校验 | 要点 | 失败说明什么 |
| --- | --- | --- | --- |
| 1 | ODS→DWD 行数守恒 | 两边 `count(*)` 相等 | join 丢数（过滤孤儿明细）或重复 |
| 2 | 金额守恒 | `sum(pay_amount)` 相等（允许 0.01 分摊误差） | 金额被放大（维表重复）或精度截断 |
| 3 | 主键唯一 | `group by 主键 having count(*)>1` 为 0 行 | 上游重复推送或 join 放大 |
| 4 | 维表覆盖率 | 未匹配占比 < 0.1% | 维表延迟或编码不一致 |
| 5 | GMV 交叉验证 | 明细汇总 = ADS 支付口径 | 口径不一致或漏算 |
| 6 | 环比波动 | `abs(rows_dod)<20%`、`abs(amt_dod)<15%` | 上游少推、部分失败、口径变更 |

```sql
-- ①② 行数/金额守恒  ③ 主键唯一  ④ 维表覆盖率
select (select count(*) from ods.ods_order_item where dt='${biz_date}') ods_cnt,
       (select count(*) from dwd.dwd_trade_order_detail_di where dt='${biz_date}') dwd_cnt,
       (select sum(pay_amount) from ods.ods_order_item where dt='${biz_date}') ods_amt,
       (select sum(pay_amount) from dwd.dwd_trade_order_detail_di where dt='${biz_date}') dwd_amt;

select count(*) dup_cnt from (select order_id, order_item_id from dwd.dwd_trade_order_detail_di
  where dt='${biz_date}' group by order_id, order_item_id having count(*) > 1) t;

select sum(case when d.sku_id is null then 1 else 0 end)/count(*) unmatched_rate
from dwd.dwd_trade_order_detail_di f
left join dim.dim_sku d on f.sku_id = d.sku_id and d.dt = '${biz_date}'
where f.dt = '${biz_date}';
```

> ⑤ 交叉验证：`dwd_trade_order_pay_di` 的 `sum(pay_amount)` = `ads_gmv_d` 的 `gmv_type='pay'`；⑥ 环比用 `lag()` 取近 7 天，超阈值告警。

```sql
-- 复购率：当日支付用户中，历史累计支付单数 ≥2 的占比
insert overwrite table ads.ads_user_repurchase_d partition (dt='${biz_date}')
select '${biz_date}' dt, count(*) buyer_cnt, sum(if(pay_cnt>=2,1,0)) repurchase_cnt,
       round(sum(if(pay_cnt>=2,1,0))/count(*), 4) repurchase_rate
from (select user_id, count(distinct order_id) pay_cnt from dwd.dwd_trade_order_pay_di
      where dt<='${biz_date}' and user_id in
            (select user_id from dwd.dwd_trade_order_pay_di where dt='${biz_date}')
      group by user_id) h;
```

> [!important] 校验失败时的处置顺序
> 先看 ③ 主键唯一（它失败会让 ②⑤ 一起失败，是根因）；再看 ① 行数；最后看 ④ 覆盖率（通常是维表延迟，不是本层问题）。

### 2.11 步骤 10：三个已知风险与演进方向

| 风险 | 触发条件 | 影响 | 当前缓解 | 长期方案 |
| --- | --- | --- | --- | --- |
| 数据量涨 10 倍 | 日订单 2000 万 | 单分区 10GB+，join 慢 | 加 `dt+hour`、开 AQE、热点店铺单独处理 | 湖仓 + 分桶 + 增量计算 |
| 维表同步延迟 | 上游 T+1 才就绪 | 覆盖率掉到 95% | `-1` 兜底 + DQ 告警 | CDC 实时入湖 |
| 要分钟级时效 | 大促看实时 GMV | T+1 报表撑不住 | 小时级调度 + 小窗口重算 | Flink 双流 + 湖仓 |

**要不要上湖仓**：当下不需要。三条同时成立才做：① 分钟级时效；② 行级更新（拉链每天重写 4000 万行很痛）；③ time travel 回溯。**实时化**：下单/支付适合实时，退款/履约适合离线，共用一份指标字典。

### 3.2 三种 GMV 与幂等

```sql
select 'order' gmv_type, sum(pay_amount) gmv from tmp.dwd_order_detail where dt='2026-10-01'
union all select 'pay',   sum(pay_amount) from tmp.ods_order_item where dt='2026-10-01'
union all select 'trade', sum(pay_amount) - 0 from tmp.ods_order_item where dt='2026-10-01';
```

没有退款时三个数都是 500；把 `- 0` 改成 `- 50` 变 450——**口径差异只来自「时间锚点」和「是否扣退款」**。再跑一次 `insert overwrite` 行数仍是 3，换成 `insert into` 变 6（02-11 的 E1）。

拉链的验证同理：先插一条 `V1 / 2026-10-01 / 9999-12-31`，次日把等级改成 V2 再按 2.5 合并，应得到两行（`V1 10-01~10-01`、`V2 10-02~9999-12-31`）；出现两行 `is_current=1` 就是 02-11 的事故二。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| GMV 翻倍 / 支付金额翻倍 | 维表重复放大；未过滤 `pay_status`（INIT/FAIL 入表） | `count(*)` vs `count(distinct 主键)`；按 `pay_status` 分组 | join 前 `row_number` 去重；只入 SUCCESS |
| 订单数虚高 / 退款金额对不上 | 拉链关联没带时间条件；退款按申请日归属 | 检查 join 是否有时间区间；对比 `apply_time` 与 `refund_time` | 补条件 + `9999-12-31` 特判；按 `refund_time` 分区 |
| 累积快照越跑越慢 | 按快照日存全量 | 看分区数与行数增长 | 改按 `order_dt` 分区 + 局部重写 |
| 重跑后数据翻倍 / 毁一个月 | `insert into`；Spark STATIC 覆盖全表 | 重跑前后与其他日期的 `count(*)` | 改 `insert overwrite` + `partitionOverwriteMode=dynamic` |
| 转化率 > 100% / 复购率每天变 | 分子分母不同源；累计口径未固定（是否含当日） | 检查是否同一 `user_id` 集合；看 `dt <=` 还是 `dt <` | 固定同源口径或改 session 漏斗；口径写进字典 |
| 维表属性为空 | 维表 T+1 未就绪就跑了 DWD | 看覆盖率校验 | 就绪检查 + `-1` 兜底 |
| 大促当天跑挂 | 单分区暴增 + 热点店铺倾斜 | 看 task 时长分布 | 加小时分区、热点单独处理、开 AQE |

## 五、面试追问

> [!question] 1. 从 0 设计订单域数仓，你怎么讲？
> **一句话答法**：分层 → 域 → 矩阵 → 四步法 → 口径 → 治理：先定四层职责，划交易/流量/用户/商品域，画 5×6 矩阵，逐过程走四步法出表，最后定字典与分区/幂等/校验。
> **追问陷阱**：「为什么不先讲表结构」——表结构是结果；先说清有哪些业务过程、各自什么粒度。

> [!question] 2. 订单明细的粒度怎么定？为什么不是一单一行？
> **一句话答法**：一单多商品，按商品拆才能做商品/类目分析；一单一行商品维度无法下钻，金额也分摊不到 SKU。
> **追问陷阱**：「一单一行还有用吗」——有用，累积快照就是订单粒度，两者服务不同场景。

> [!question] 3. 下单、支付、退款为什么要三张事实表？
> **一句话答法**：三个业务过程、三个时间锚点、三种口径；混一张表，指标按哪个时间算永远说不清。
> **追问陷阱**：「怎么关联」——用 `order_id`，在 DWS 层聚合到目标粒度后再 join，不要在明细层链式 join。

> [!question] 4. 拉链为什么必须带时间条件？
> **一句话答法**：一个用户多个版本，不带时间条件就是笛卡尔匹配，一个订单关联出 N 行，人数和金额全错。
> **追问陷阱**：「开区间还是闭区间」——本文用闭区间 `< date_add(end_date,1)`，团队必须统一并特判 `9999-12-31`。

> [!question] 5. 三种 GMV 选哪个做正式口径？
> **一句话答法**：三个都产出，口径由业务和财务定：对外披露用支付 GMV，经营分析用成交 GMV，复盘用下单 GMV。
> **追问陷阱**：「老板问哪个对」——都对，差在口径；给出差额构成（未支付、退款、跨天支付）比争论对错有用。

> [!question] 6. DWS 为什么只建用户/商品/店铺三个粒度？
> **一句话答法**：这三个是稳定分析主体，覆盖 80% 下游；渠道和地区作为维度列冗余可上卷，不必单独建表。
> **追问陷阱**：「按渠道看复购」——从用户表上卷，但「用户归属渠道」（首单 or 末次）要先定义，否则一人算进多个渠道。

> [!question] 7. 怎么保证这条链路可重跑？
> **一句话答法**：业务日期分区 + `insert overwrite` + 显式传参 + 分层串行 + 上游就绪检查，五条缺一不可。
> **追问陷阱**：「重跑 30 天」——按天并行，同一天内仍按 DWD→DIM→DWS→ADS 串行；别用一个任务动态写 30 个分区。

> [!question] 8. 上线后 GMV 多了 3 万，怎么查？
> **一句话答法**：倒查——主键重复 → 维表重复 → 支付混入失败单 → 退款重复扣 → 口径变更，90% 是前两个。
> **追问陷阱**：「哪天开始错」——按日对比 `count(*)` 与 `count(distinct 主键)` 的差值，突变那天即起点。

> [!question] 9. 数据量涨 10 倍、又要分钟级，怎么办？
> **一句话答法**：先加二级分区、控文件大小、热点 key 单独处理、开 AQE；强时效指标走实时，其余仍走离线。
> **追问陷阱**：「为什么不直接上湖仓」——湖仓解决更新/时效/回溯，不解决单表扫描量大。分区和文件没做好，上湖仓一样慢。

> [!question] 10. 这条链路最大的设计风险是什么？
> **一句话答法**：拉链关联和维表重复——前者错在「多版本匹配」，后者错在「一对多放大」，都不报错，只让数字慢慢偏。
> **追问陷阱**：「怎么防」——两条 DQ：`is_current=1` 每人一条、维表主键唯一，再加金额守恒。规则比人可靠。

> [!question] 1.（单选）订单明细事实表的主键应该是？
> A. `order_id`　B. `order_item_id`　C. `order_id + order_item_id`　D. 自增 ID

> [!question] 2.（单选）拉链表关联历史订单时，必须加的条件是？
> A. `is_current = 1`　B. `order_time` 落在 `[start_date, end_date]` 区间　C. `user_id` 相等即可　D. `dt = 当天`

> [!question] 3.（判断）累积快照表按「快照日期」分区、每天存一份全量，是最佳实践。

> [!question] 4.（场景设计）业务说「昨天 GMV 比前天少了 40%，但订单量只少了 5%」。给出完整排查路径。

> [!question] 5.（场景设计）公司要新增「直播渠道」独立分析：直播订单的 GMV、退货率、主播佣金，佣金在另一个系统。请设计新增哪些表、放哪层、粒度和口径怎么定。

> [!success]- 答案与解析（点击展开）
> **1. C**　一单多商品，`order_id` 单独不唯一；业务唯一键是「订单 + 明细」，还能防住明细 ID 复用。自增 ID 是代理键，做不了业务唯一性校验。
>
> **2. B**　拉链要还原「下单时点」的属性，必须用时间区间匹配：只写 `user_id` 会匹配所有版本（放大），只写 `is_current=1` 拿到的是最新属性。闭区间 `< date_add(end_date,1)`，`9999-12-31` 要特判。
>
> **3. 错误**　按快照日存全量 = 200 万 × 365 = 7.3 亿行/年，查「某订单当前状态」还要扫全部分区。应按 `order_dt` 分区，一行一个版本，每天只重写有变化的分区。
>
> **4. 排查路径**：① 先分「量」还是「价」——GMV 跌 40%、单量只跌 5%，客单价跌约 37%；② 金额守恒：ODS 与 DWD 的 `sum(pay_amount)` 是否一致；③ 维表覆盖率是否从 99.9% 掉到 95%；④ 口径是否被改（含不含运费/优惠）；⑤ 上游 `pay_amount` 是否大量 0/NULL（元变分）；⑥ 大额订单是否被风控过滤。排序：上游金额异常 40% > 维表丢失 25% > 口径变更 20% > join 丢数 15%。
>
> **5. 直播渠道分析**
> | 表 | 层 | 粒度 | 主键 | 说明 |
> | --- | --- | --- | --- | --- |
> | `dim_anchor` | DIM | 一个主播 | `anchor_id` | 等级、机构、签约类型（SCD1 日快照） |
> | `dwd_live_room_session_di` | DWD | 一场直播 | `session_id` | 开播/下播、主播、房间、观看人数 |
> | `dwd_live_trade_order_di` | DWD | 订单×商品（仅直播单） | `order_id+order_item_id` | 从现有明细过滤 `channel_id=4`，补 `session_id` |
> | `dwd_live_commission_di` | DWD | 一次佣金结算 | `commission_id` | 佣金金额、费率、结算状态（另一系统） |
> | `ads_live_gmv_d` | ADS | 日×主播 | `dt+anchor_id` | GMV、退货率、佣金、ROI |
> **关键点**：① **不给订单明细加直播字段**，新建直播域事实表用 `order_id` 关联。② **退货率口径写死**：`退款金额/支付金额`，按退款日归属，否则分子分母跨期。③ **佣金粒度是「一次结算」**，不能直接 join 后 `sum`，先聚合到主播×日。④ **主播换机构**属 SCD2，当期分析 SCD1 够用。
