# 02-09 数据域与主题划分

> [!abstract] 一句话结论
> 数据域是按**业务过程**切的第一刀，决定 DWD 怎么分目录；主题是域内的**分析视角**，决定 DWS 怎么组织。先有域，后有主题，两者不是一回事。
> 域要**稳定**（不随组织架构变），主题要**灵活**（跟着分析需求变）。搞反了，组织一调整数仓就要重构。
> 面试里问「你们怎么划分数据域」，考的不是你背了八大域，而是你知不知道**退款的「行为」和「处理流程」该分到两个域**。

---

## 一、心智模型：先切域，再分主题

```
                        ┌──────────── 数据域（按业务过程切，稳定）────────────┐
   ODS  ──────────────→ │  交易域   商品域   用户域   营销域   履约域   售后域  │  ← DWD 按域分目录
                        └──────────────────────────────────────────────────┘
                                              │
                        ┌─────────────────────┴────────────────────────────┐
                        │  主题（域内的分析视角，灵活）                       │
                        │  交易域 → 下单主题 / 支付主题 / 退款主题            │  ← DWS 按主题组织
                        │  用户域 → 注册主题 / 活跃主题 / 留存主题            │
                        └──────────────────────────────────────────────────┘
                                              │
                                         ADS 报表 / 指标
```

**一句话区分**：

- **域**回答「这条数据是谁产生的、属于哪个业务过程」——是**数据的归属**，看数据本身。
- **主题**回答「分析时要看什么」——是**分析的视角**，看使用方式。

举例：`dwd_trade_payment_di`（支付流水）属于**交易域**。但分析时可以进三个主题：

| 主题 | 分析视角 | 产出 |
| --- | --- | --- |
| 交易域 · 支付主题 | 支付成功率、支付方式分布 | `dws_trade_pay_1d` |
| 用户域 · 消费主题 | 用户消费频次、客单价分层 | `dws_user_consume_1d`（引用支付表） |
| 财务域 · 收入主题 | 收入确认、渠道对账 | `dws_fin_income_1d`（引用支付表） |

**同一份 DWD 数据，可以被多个主题引用，但只能属于一个域**。这是「单一归属」原则，也是域和主题最容易混淆的地方——很多人以为「支付数据既能算交易也能算用户，所以两边都建一张」，结果就是重复建模。

> [!important] 判断一句话
> 问「这张表能不能被删掉而不影响数据完整性？」能删的是**主题/宽表**（可以重建），不能删的是**域内的 DWD 事实表**（是唯一事实来源）。

## 二、核心知识点

### 2.1 划分四原则

| 原则 | 含义 | 违反后的现象 |
| --- | --- | --- |
| **高内聚** | 同一域内的表服务同一批业务过程，改动时一起改 | 一个域里既有订单又有物流，改订单要拉物流的人评审 |
| **低耦合** | 域之间只通过维度/公共层交互，不直接依赖对方的 DWD | 交易域的 DWD 直接 join 售后域的 DWD，售后改表交易挂 |
| **边界稳定** | 域的划分依据是业务过程，不是组织架构 | 公司把「售后」拆成两个部门，数仓要重构 |
| **单一归属** | 一个业务过程只属于一个域，只能有一张 DWD 表 | 交易域和营销域各建一张「订单转化表」，数字对不上 |

**边界稳定**是最容易被忽视的一条。判断方法：**假设明天公司做组织架构调整（合并部门、拆部门、换汇报线），你的域要不要改？** 要改，说明你是按部门分的，不是按业务过程分的。

### 2.2 三种划分方式的利弊

| 划分方式 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **按业务过程**（Kimball 推荐） | 下单、支付、退款、发货各成一块 | 边界最稳定，与组织无关；天然对应事实表 | 需要建模者理解业务，不能照抄系统表 | 长期演进的数仓，**首选** |
| **按部门** | 交易部、市场部、供应链部各一块 | 直观，和需求方对齐，沟通成本低 | 组织一调整就要重构；跨部门业务过程被切断 | 早期快速上线，或纯报表型团队 |
| **按业务线/系统** | 自营、平台、直播；订单系统、支付系统各一块 | 贴合现状，ODS 到 DWD 映射简单 | 同一业务过程在不同业务线重复建模（3 份订单表） | 多业务线强隔离（如并购后的子公司） |

**现实中的做法**：**主域按业务过程分，业务线作为域内的一级分区/标签**。

```
dwd_trade_order_detail_di   （分区字段 biz_line = 'self' / 'platform' / 'live'）
```

而不是：

```
dwd_self_order_detail_di
dwd_platform_order_detail_di
dwd_live_order_detail_di     ← 三份订单逻辑，改一次要改三处
```

> [!warning] 业务线隔离的合理场景
> 如果两条业务线的订单模型**本质不同**（比如自营是「采购-库存-销售」，平台是「商家入驻-佣金结算」），可以拆域。判断标准是：**它们的业务过程是不是同一批**。是同一批（都是下单-支付-退款），就合并 + 加标签；不是同一批，才拆。

### 2.3 电商常见八大域拆解

| 域 | 缩写 | 职责边界 | 典型业务过程 | 对应 DWD 表 |
| --- | --- | --- | --- | --- |
| **交易** | `trade` | 从下单到支付完成的主链路 | 下单、支付、订单取消 | `dwd_trade_order_detail_di`、`dwd_trade_payment_di`、`dwd_trade_order_cancel_di` |
| **商品** | `item` | 商品的静态属性与变更 | SKU 发布、上下架、改价、类目调整 | `dwd_item_sku_publish_di`、`dwd_item_price_change_di`、`dwd_item_sku_df` |
| **用户** | `user` | 用户身份、账号、画像 | 注册、登录、实名认证、画像更新 | `dwd_user_register_di`、`dwd_user_login_di`、`dwd_user_profile_df` |
| **营销** | `mkt` | 活动、优惠券、投放 | 活动创建、优惠券发放、领券、广告曝光 | `dwd_mkt_coupon_issue_di`、`dwd_mkt_campaign_expose_di` |
| **履约** | `fulfill` | 仓、配、运 | 拣货、发货、揽收、签收 | `dwd_fulfill_delivery_di`、`dwd_fulfill_sign_di`、`dwd_fulfill_picking_di` |
| **售后** | `afs` | 退换修的处理流程 | 退货申请、审核、寄回、换货、维修 | `dwd_afs_return_apply_di`、`dwd_afs_refund_process_di` |
| **流量** | `traffic` | 曝光、点击、访问、搜索 | 页面浏览、点击、搜索、推荐曝光 | `dwd_traffic_page_view_di`、`dwd_traffic_click_di`、`dwd_traffic_search_di` |
| **财务** | `fin` | 结算、对账、发票 | 商家结算、平台对账、开票 | `dwd_fin_settlement_di`、`dwd_fin_reconcile_di`、`dwd_fin_invoice_di` |

**每个域 2~3 个业务过程就够了**。一个域超过 8 个业务过程，说明切得太粗（比如把「交易」做成「交易 + 营销 + 履约」），要再拆。

**域之间的依赖方向**（低耦合的关键）：

```
traffic ──→ trade ──→ fulfill ──→ afs
              │           │          │
              └───────────┴──────────┴──→ fin
item ──→ trade        user ──→ 所有域（作为维度）
mkt ──→ trade（优惠券核销）
```

规则：**箭头只能单向**。`trade` 可以引用 `item`、`user`、`mkt` 的维度，但 `item` 不能反过来引用 `trade` 的事实表。反向引用一旦出现，就是耦合。

### 2.4 争议归属的判定规则（加分项）

这是面试里最能区分「背过」和「做过」的部分。**判定三条铁律**：

1. **按业务过程判定，不按部门判定**——部门会变，业务过程不会。
2. **按「谁产生这条数据」判定，不按「谁使用」判定**——使用方可以有很多，生产方只有一个。
3. **一个业务过程只能属于一个域**；跨域只能引用，不能复制。

**六个典型争议**：

| 业务对象 | 常见争议 | 判定 | 理由 |
| --- | --- | --- | --- |
| **退款** | 交易域 vs 售后域 | **退款行为**（发起、成功、金额）→ **交易域**；**退款处理流程**（审核、寄回、验收、换货）→ **售后域** | 前者是资金反向流动（交易过程），后者是工单流程（服务过程） |
| **优惠券** | 营销域 vs 交易域 | **发放、领券** → 营销域；**核销（用券下单）** → 交易域 | 发放是营销动作，核销是下单动作的一部分 |
| **订单收货地址** | 用户域 vs 交易域 | 地址簿 → 用户域；**订单上的地址快照** → 交易域 | 订单地址是历史快照，不能跟着地址簿变（否则改地址会改历史订单） |
| **库存** | 商品域 vs 履约域 | 库存**快照**（可售量）→ 商品域；库存**变动**（入库、出库、锁定）→ 履约域 | 快照是商品的可售状态，变动是仓储作业过程 |
| **评价** | 交易域 vs 内容域 | 评价**提交**（订单衍生）→ 交易域；评价**内容运营**（审核、加精）→ 内容域 | 有订单才有评价，提交是交易后动作 |
| **发票** | 交易域 vs 财务域 | 开票**申请** → 交易域；**开票、寄送、红冲** → 财务域 | 申请是订单后动作，开具是财务过程 |

> [!tip] 一句话记忆
> **「行为」进业务域，「流程」进服务域，「快照」进主体域。**
> 退款行为进交易，退款流程进售后；订单地址快照进交易，地址簿进用户。

**为什么这条规则重要**：如果按部门分，退款会被整体塞进售后域——但退款金额是 GMV 净额口径的减项，交易域的报表每天都要用，跨域依赖就产生了。拆成「行为 + 流程」之后，交易域自己闭环，售后域只管工单，两边都不依赖对方。

### 2.5 命名规范：让表名自己说出域和粒度

**DWD 命名公式**：

```
dwd_{域}_{业务过程}_{粒度后缀}
```

| 部分 | 取值 | 说明 |
| --- | --- | --- |
| 层前缀 | `ods_` / `dwd_` / `dws_` / `ads_` / `dim_` | 必须小写，必须带 |
| 域 | `trade` / `item` / `user` / `mkt` / `fulfill` / `afs` / `traffic` / `fin` | 固定枚举，不允许自创缩写 |
| 业务过程 | `order_detail` / `payment` / `refund` / `delivery` … | 用下划线，不用驼峰，不用保留字 |
| 粒度后缀 | `_di` 日增量 / `_df` 日全量 / `_hi` 小时增量 / `_zip` 拉链 | 必须带，它决定这表怎么用 |

**DWS 命名**：`dws_{域}_{主题}_{统计粒度}_{周期}`，如 `dws_trade_pay_shop_1d`。

**五个示例（正误对照）**：

| 表名 | 判定 | 原因 |
| --- | --- | --- |
| `dwd_trade_order_detail_di` | ✅ | 层 + 域 + 过程 + 粒度，齐全 |
| `dwd_trade_payment_di` | ✅ | 同上 |
| `dwd_order_detail` | ❌ | 缺域（不知道归谁）、缺粒度后缀（不知道是全量还是增量） |
| `DWD_trade_OrderDetail` | ❌ | 大写 + 驼峰，Hive 会转小写导致和其他表冲突 |
| `dwd_trade_order_di_bak` | ❌ | `_bak` 是临时后缀，正式层不允许出现；临时表用 `tmp_` 前缀 + 生命周期 |

> [!warning] 保留字陷阱
> `order`、`user`、`group` 在多数引擎里是保留字。`dwd_trade_order_di` 在 Hive 里可能报错（取决于版本和引用方式），建议统一用 `order_detail` / `order_main` 规避。
> 这条要写进命名规范，否则每个人都会踩一次。

### 2.6 域 owner 与跨域指标归属

**域 owner 的职责**（写进 RACI，不能只写「负责」）：

| 职责 | 具体内容 |
| --- | --- |
| 模型 | 该域 DWD 表的设计、评审、变更 |
| 数据质量 | 该域核心表的 DQ 规则、告警处理 |
| 口径 | 该域指标的业务定义（与指标 owner 对齐） |
| 排期 | 该域需求的优先级 |
| 不做 | 不负责跨域指标、不负责 ADS 报表样式 |

**跨域指标怎么办**——三条路，按推荐度：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **公共指标层**（推荐） | 建 `dws_public_` / `ads_public_` 层，由数据架构组或指标委员会维护 | 归属清晰，避免争夺 | 需要额外的组织协调 |
| **归主事实表所在域** | 指标的主事实表在交易域，就归交易域 | 简单 | 容易变成「谁的表谁背锅」，其他域不认 |
| **硬塞进某个域** | ❌ | 无 | 该域 owner 没有权限改别的域的表，指标永远做不准 |

**判断「主事实表」的方法**：看指标的**分子**来自哪张事实表。支付转化率的分子是支付买家数（交易域），所以归交易域；但如果分母（访问 UV）在流量域，就必须走公共层，因为单一域无法闭环。

### 2.7 域和总线矩阵、分层的关系

| 关系 | 说明 |
| --- | --- |
| 域 → 总线矩阵的行 | 域是矩阵行的**分组**：交易域的行（下单/支付/退款）排在一起，读矩阵时一眼能看出哪个域覆盖不全 |
| 主题 → 总线矩阵的列组合 | 主题是列的**组合**：支付主题 = 日期 + 渠道 + 支付方式；用户消费主题 = 日期 + 用户 + 商品 |
| 域 → DWD 目录 | `dwd/trade/`、`dwd/item/`… 物理目录按域分，权限也按域授权 |
| 主题 → DWS 目录 | `dws/trade/pay/`、`dws/user/consume/`… 主题可以跨域引用，但目录归主域 |

**一句话**：域决定**数据放哪**，主题决定**数据怎么被看**。域是物理的（目录、权限、owner），主题是逻辑的（查询、报表、分析）。

### 2.8 组织架构调整了，域要不要跟着改

**不要。** 这是本节最重要的一条结论。

| 变化 | 域 | 主题 | 理由 |
| --- | --- | --- | --- |
| 售后部拆成「退货组」和「维修组」 | 不变（还是 `afs`） | 可加「维修分析」主题 | 业务过程没变，只是看的人变了 |
| 交易部并入「增长中心」 | 不变（还是 `trade`） | 不变 | 组织变化不影响业务过程 |
| 公司新增直播业务 | 新增 `live` 或复用 `traffic` + `trade` + 标签 | 新增「直播分析」主题 | 看业务过程是否是新的 |
| 收购一家公司，订单模型不同 | 可新增 `trade_xx` 子域 | 独立主题 | 业务过程本质不同才拆 |

**判断标准**：**业务过程变了吗？** 变了才动域；只是「谁来看、怎么看」变了，动主题。

> [!danger] 按部门分域的代价
> 组织架构平均 1~2 年调整一次，按部门分域意味着数仓 1~2 年重构一次。而重构的代价不是改目录，是**重跑历史数据 + 改所有下游 + 重新对账**。
> 所以「按业务过程分域」不是理论最优，是**总成本最低**。

### 3.3 实验二：命名规范合规检查

```sql
-- 不符合 dwd_{域}_{过程}_{粒度后缀} 的表
select table_name
from meta_table_catalog
where layer = 'DWD'
  and table_name not rlike '^dwd_[a-z]+_[a-z0-9_]+_(di|df|hi|zip)$';
```

**预期结果**：

| table_name | 问题 |
| --- | --- |
| `dwd_trade_order_di` | 语法上合规（`order` 是过程名），但它是 `dwd_trade_order_detail_di` 的**重复建模**——见实验三 |
| `dwd_mkt_order_convert_di` | 命名合规，但域归属错误（订单转化是交易域的过程） |

> 正则只能查出「格式错」，查不出「语义错」。所以命名检查必须配一条**业务过程唯一性**检查。

### 3.4 实验三：单一归属与重复建模检查

```sql
-- 同一个业务过程被分到多个域 → 一定是重复建模
select biz_process,
       count(distinct domain)   as domain_cnt,
       collect_set(domain)      as domains,
       collect_set(table_name)  as tables
from meta_table_catalog
where layer = 'DWD'
group by biz_process
having count(distinct domain) > 1;

-- 同一个域内，同一个业务过程有多张表 → 要么是分层（di/df），要么是重复
select domain, biz_process, count(*) as table_cnt,
       collect_set(table_name) as tables
from meta_table_catalog
where layer = 'DWD'
group by domain, biz_process
having count(*) > 1;
```

**预期结果（第一条）**：

| biz_process | domain_cnt | domains | tables |
| --- | --- | --- | --- |
| `order` | 2 | `["trade","mkt"]` | `["dwd_trade_order_detail_di","dwd_trade_order_di","dwd_mkt_order_convert_di"]` |

**解读**：`order` 这个业务过程在交易域和营销域各有一份。营销域的 `dwd_mkt_order_convert_di` 是典型的**跨域复制**——营销同学为了算「活动带来的订单」，直接把订单表复制了一份到营销域，然后自己加了 `campaign_id`。

后果：
1. 交易域改了订单状态枚举，营销域那份不会跟着改 → 两周后两个域的订单数差 3%。
2. 存储翻倍（1.2 亿行 × 2）。
3. 总线矩阵上「下单」这一行出现两张表，新人不知道该用哪个。

**正确做法**：营销域不建订单表，而是在 `dwd_trade_order_detail_di` 里补 `campaign_id`（下单时透传），营销域通过 `dws_mkt_campaign_convert_1d` 引用交易域的事实表。

### 3.5 实验四：域的数据量分布是否均衡

```sql
select domain,
       count(*)                as table_cnt,
       sum(row_cnt)            as total_rows,
       round(sum(row_cnt) / sum(sum(row_cnt)) over (), 4) as row_pct
from meta_table_catalog
where layer = 'DWD' and dt = '2026-10-24'
group by domain
order by total_rows desc;
```

**预期结果**：

| domain | table_cnt | total_rows | row_pct |
| --- | --- | --- | --- |
| traffic | 2 | 2,300,000,000 | 0.6847 |
| mkt | 3 | 628,000,000 | 0.1870 |
| trade | 4 | 341,000,000 | 0.1015 |
| fulfill | 2 | 39,000,000 | 0.0116 |
| user | 2 | 30,200,000 | 0.0090 |
| fin | 2 | 10,000,000 | 0.0030 |
| item | 3 | 7,800,000 | 0.0023 |
| afs | 2 | 2,900,000 | 0.0009 |

**解读**：流量域 2 张表占了 68% 的行数，营销域 3 张表占 19%（主要是 `campaign_expose` 的 5 亿行曝光）。这不代表划分错了，但意味着：

1. **存储和计算成本集中在流量域和营销域**，分区策略、生命周期、压缩格式要优先在这两个域做。
2. **它们不适合和交易域放同一个库**（权限、资源队列要隔离），否则一个跑飞的曝光任务会拖垮交易报表。
3. 流量域 2 张表 23 亿行，说明**粒度可能过细**（每次曝光一行），要考虑预聚合到会话级或天级。
4. trade 域 4 张表而不是 3 张——多出来的那张就是实验三查出的重复表，**行数占比能反过来暴露重复建模**（交易域凭空多了 1.2 亿行）。

> [!tip] 这个检查的真正用途
> 不是「让每个域数据量一样」，而是**发现「表少数据多」和「表多数据少」的异常域**。前者要优化粒度，后者要合并表（典型的过度设计）。

### 3.6 三个最容易分错的表

| 表 | 容易分到 | 正确归属 | 为什么 |
| --- | --- | --- | --- |
| `ods_coupon_use`（券核销） | 营销域（券是营销的） | **交易域** | 核销发生在下单瞬间，是订单的一个属性（`coupon_id` + `discount_amount`）。放营销域会导致「用券订单」和「订单」两套数据，GMV 对不上 |
| `ods_refund_apply`（退款申请） | 交易域（退款是交易的） | **售后域** | 申请是工单流程的起点（审核 → 寄回 → 验收），有 SLA、有客服、有状态机。退款**金额**在交易域，退款**流程**在售后域 |
| `ods_live_room`（直播间） | 交易域（直播带货） | **流量域** | 直播间是「内容场」，属于流量载体；直播带来的成交在交易域（`biz_line='live'`）。放交易域会让「没成交的直播场次」无处安放 |

**补充一个双写案例**：`ods_user_address` 同时进两个域，但不是重复建模——

- 用户域：`dwd_user_address_df`（地址簿，会随用户修改而变）
- 交易域：`dwd_trade_order_detail_di` 里的 `receiver_province_code`（订单地址**快照**，永不改变）

这不是「一个业务过程两个域」，而是**两个不同的业务过程**（维护地址簿 vs 下单），只是恰好用了同一份源数据。判断标准还是那句：**业务过程是不是同一个**。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 组织调整后数仓要重构 | 按部门分域 | 看域名单是否和部门名单一致 | 改成按业务过程分域，部门作为标签 |
| 同一业务过程两张表，数字对不上 | 跨域复制（如营销域自建订单表） | `group by biz_process having count(distinct domain)>1` | 删除复制表，改为引用 + 补维度列 |
| 新人不知道表放哪 | 命名缺域或缺粒度后缀 | 正则检查 `^dwd_[a-z]+_.+_(di|df)$` | 命名规范 + 建表模板 + 评审卡点 |
| `order` 表建表报错 | 保留字 | 看报错信息 | 改用 `order_detail` / `order_main` |
| 域 owner 互相推诿 | 跨域指标没有归属 | 看指标的主事实表在哪个域 | 建公共指标层，或明确「归主事实表所在域」 |
| 一个域 15 个业务过程，评审拉不动 | 域切得太粗 | 数每个域的业务过程数 | 超过 8 个就拆（如把「交易」拆出「履约」） |
| 直播业务的数据没地方放 | 按业务线分域，新业务无归属 | 看新业务属于哪个业务过程 | 复用现有域 + `biz_line` 标签，不轻易加域 |
| 主题和域混用，DWS 目录乱 | 没区分「归属」和「视角」 | 看 DWS 表是否跨域引用 | DWS 目录归主域，主题名做二级目录 |
| 域之间循环依赖 | 没有约定依赖方向 | 画依赖图，找环 | 约定单向：traffic→trade→fulfill→afs→fin |
| 源表分错域，下游全错 | 按表名猜归属，没看业务过程 | 逐个源表核对「谁产生、什么过程」 | 建源表-域映射表，纳入元数据管理 |

## 五、面试追问

> [!question] 1. 你们怎么划分数据域？
> **一句话答法**：按业务过程切，不按部门切。先列公司的业务过程（下单、支付、退款、发货…），把高内聚的过程归成一个域，一个业务过程只能属于一个域；业务线用 `biz_line` 标签区分，不拆域。
> **追问陷阱**：「为什么不全按部门分，沟通不是更方便吗」——部门 1~2 年调一次，按部门分域意味着数仓跟着重构，代价是重跑历史 + 改所有下游 + 重新对账。

> [!question] 2. 退款属于哪个域？
> **一句话答法**：拆开看——退款**行为**（发起、成功、金额）属交易域，退款**处理流程**（审核、寄回、验收、换货）属售后域。
> **追问陷阱**：「为什么不整体放售后」——退款金额是 GMV 净额口径的减项，交易域每天要用，放售后会造成跨域依赖；拆开后交易域闭环，售后只管工单。

> [!question] 3. 域和主题的区别？
> **一句话答法**：域是数据的**归属**（谁产生的、什么业务过程），决定 DWD 目录和权限；主题是**分析视角**，决定 DWS 怎么组织。同一份 DWD 可以被多个主题引用，但只属于一个域。
> **追问陷阱**：「支付数据既算交易也算用户，是不是要建两张表」——不用，DWD 只有一张，DWS 可以有两个主题的汇总表。

> [!question] 4. 组织架构调整了，域要不要跟着改？
> **一句话答法**：不改。域按业务过程划分，业务过程不随组织变；组织变了只调整主题（谁看什么）和权限。
> **追问陷阱**：「那什么情况下才加域」——出现**新的业务过程**（不是新的业务线、不是新的部门）才加域。比如新增「直播」如果只是新的销售渠道，复用交易域 + 标签就够了。

> [!question] 5. 跨域指标谁负责？
> **一句话答法**：三条路——建公共指标层（推荐，由数据架构组/指标委员会负责）、归主事实表所在域（分子来自哪张事实表就归哪个域）、禁止硬塞进某个域。
> **追问陷阱**：「公共层和 ADS 有什么区别」——公共层是可复用的中间层（多报表引用），ADS 是面向具体报表的最终结果；公共层要沉淀口径，ADS 只管展示。

> [!question] 6. 按业务过程、按部门、按业务线，怎么选？
> **一句话答法**：主域按业务过程（稳定），业务线做标签（灵活），部门只在早期快速上线时用，并且要预留重构计划。
> **追问陷阱**：「业务线模型差异很大怎么办」——如果业务过程本质不同（自营是采销存、平台是入驻抽佣），可以拆子域；如果只是同一批过程换个渠道，就合并 + 标签。

> [!question] 7. 新业务（比如直播）来了，怎么加？
> **一句话答法**：先问「有没有新的业务过程」。直播带货的成交还是下单-支付-退款，所以复用交易域 + `biz_line='live'`；直播的「场」（直播间、场次、在线人数）是新的业务过程，可以进流量域或新建内容域。
> **追问陷阱**：「什么时候必须新建域」——现有域的语义装不下这个业务过程，且强行塞进去会让现有域的表含义变模糊。

> [!question] 8. 域划分和总线矩阵什么关系？
> **一句话答法**：域是总线矩阵行的分组，主题是列的组合。域决定矩阵怎么分段读，主题决定一次分析要横跨哪几列。
> **追问陷阱**：「矩阵的行要不要按域排序」——要，按域排序能一眼看出哪个域覆盖不全（连续几行都是空格）。

> [!question] 9. 一个业务过程被两个域都建了表，怎么治理？
> **一句话答法**：先判定归属（按「谁产生数据」），保留主域的表，另一个域改为引用 + 补需要的维度列；然后加自动化检查（`group by biz_process having count(distinct domain)>1`），防止复发。
> **追问陷阱**：「业务方不愿意改怎么办」——用数据说话：两张表跑一个月对账，把差异行拿出来，通常一周内就会同意收敛。

> [!question] 10. 域 owner 的职责边界在哪？
> **一句话答法**：负责该域 DWD 的模型、DQ、口径、排期；不负责跨域指标、不负责 ADS 报表样式、不负责其他域的表。
> **追问陷阱**：「跨域指标出问题找谁」——找公共层 owner 或指标委员会，不能找某个域 owner，因为他没有权限改别的域。

> A. 退款成功（资金退回）
> B. 退款申请审核
> C. 优惠券核销
> D. 订单取消

> [!question] 3.（判断）公司把售后部拆成退货组和维修组，数据域应该跟着拆成两个。

> [!question] 4.（场景设计）一家电商（自营 + 平台 + 直播）要建数仓。请给出 8 个域的划分，并说明 `ods_coupon_use`、`ods_refund_apply`、`ods_live_room` 三张表分别归哪个域、为什么。

> [!question] 5.（场景设计）你发现营销域建了一张 `dwd_mkt_order_convert_di`，和交易域的 `dwd_trade_order_detail_di` 行数一样。请给出：① 这属于什么问题的判断依据；② 治理步骤；③ 如何防止再次发生。

> [!success]- 答案与解析（点击展开）
> **1. B**
> 域是数据归属（物理：目录、权限、owner），主题是分析视角（逻辑：查询、报表）。一个域可以有多个主题，主题也可以跨域引用数据。
>
> **2. B**
> 退款申请审核是**流程**，属售后域；退款成功（资金）是**行为**，属交易域；券核销是下单动作，属交易域；订单取消属交易域。
>
> **3. 错误**
> 域按业务过程划分，售后部拆组不产生新的业务过程，域不变；可以新增「维修分析」主题。按组织拆域会导致数仓随组织频繁重构。
>
> **4. 参考划分**
> | 域 | 核心业务过程 |
> | --- | --- |
> | trade 交易 | 下单、支付、退款（行为）、取消 |
> | item 商品 | SKU 发布、改价、上下架 |
> | user 用户 | 注册、登录、地址簿 |
> | mkt 营销 | 活动、券发放、投放 |
> | fulfill 履约 | 拣货、发货、签收 |
> | afs 售后 | 退货申请、审核、换货、维修 |
> | traffic 流量 | 曝光、点击、访问、直播场次 |
> | fin 财务 | 结算、对账、开票 |
>
> **三张表**：
> - `ods_coupon_use` → **trade**。核销发生在上单瞬间，是订单属性；放营销域会产生两套订单数据，GMV 对不上。
> - `ods_refund_apply` → **afs**。申请是工单流程起点（审核→寄回→验收），有 SLA 和状态机；退款金额才在 trade。
> - `ods_live_room` → **traffic**。直播间是内容场/流量载体，没成交的场次也要能记录；成交在 trade（`biz_line='live'`）。
>
> **5. 参考答案**
> ① **判断依据**：同一 `biz_process='order'` 出现在两个域（`group by biz_process having count(distinct domain)>1`）；且两表行数完全相同，说明是复制而非独立加工。
>
> ② **治理步骤**：
> 1. 确认营销域的真实需求（大概率是要 `campaign_id` 维度的订单）。
> 2. 在 `dwd_trade_order_detail_di` 补 `campaign_id`（下单时透传），或建 `dws_mkt_campaign_convert_1d` 引用交易域。
> 3. 营销域 SQL 改为引用新表，双跑一周对账。
> 4. 下线 `dwd_mkt_order_convert_di`，保留一个版本周期后删除。
>
> ③ **防复发**：
> - 元数据加检查：`biz_process` 跨域重复即告警。
> - 建表评审：DWD 层新表必须声明 `domain + biz_process`，与已有表冲突直接打回。
> - 权限：DWD 层按域授权，营销域账号无权限在 `trade` 目录建表（但可读）。
