# 02-08 指标口径与指标体系

> [!abstract] 一句话结论
> 一个指标 = **度量 + 聚合逻辑 + 维度 + 过滤条件 + 时间窗口**，五要素缺一个就有歧义；「GMV」三个字不是指标，是一个歧义源。
> 指标体系的价值不在「分三层」，而在**把口径从人的记忆里搬到字典里**——同一个词，任何人任何时间算出来都是同一个数。
> 面试里问「GMV 怎么定义」，考的不是定义，是你知不知道**同一份数据能算出三个 GMV**，以及你选哪个、为什么。

---

## 一、心智模型：指标是一个五元组，不是一个词

把「GMV = 1000 万」这句话拆开，它其实省略了四个关键信息：

```
指标 = 度量（measure）        —— 订单金额？支付金额？退款后金额？
     + 聚合逻辑（aggregation） —— sum？count distinct？avg？去重还是不去重？
     + 维度（dimension）       —— 按什么分组？全站还是某渠道？
     + 过滤条件（filter）      —— 剔除取消单？只算自营？只算新客？
     + 时间窗口（window）      —— 按下单时间还是支付时间？10-01 到 10-03 还是自然月？
```

五要素里任何一个变了，数字就变了。所以「GMV 是多少」这个问题，**在没确认五要素之前是无法回答的**。

面试官问「你们 GMV 怎么算」，本质是在问：你知不知道这五要素，以及你有没有把它们**写下来**。

```
                 ┌─────────────────────────────┐
                 │  指标 = 五元组               │
                 └─────────────────────────────┘
   度量 ──→ 决定「算什么」        sum(pay_amount) 而不是 count(*)
   聚合 ──→ 决定「怎么合」        sum 可加，count distinct 不可加
   维度 ──→ 决定「按什么切」      按渠道切完能不能加回总数
   过滤 ──→ 决定「算哪些行」      剔除取消/测试/刷单
   窗口 ──→ 决定「算哪段时间」    下单时间 vs 支付时间差一个跨天支付
```

**一个判断指标是否定义清楚的方法**：把定义交给另一个没参与过这个项目的人，他能不能**不问你任何问题**写出完全一样的 SQL。写不出来，就是没定义清楚。

---

## 二、核心知识点

### 2.1 三层指标体系：原子 / 派生 / 复合

这是阿里 OneData 体系的核心分层，目的是**把「可复用的计算」和「业务包装」分开**。

| 层级 | 定义 | 组成 | 例子 | 特点 |
| --- | --- | --- | --- | --- |
| **原子指标** | 基于某个业务过程的**度量 + 聚合逻辑**，不可再拆 | 业务过程 + 度量 + 聚合 | `sum(pay_amount)` on 支付过程 | 不含时间、不含修饰词；全公司只有几十个 |
| **派生指标** | 原子指标 + 修饰词 + 时间周期 | 时间周期 + 修饰词 + 原子指标 | `1d_支付_订单金额` | 数量爆炸（原子 × 修饰词 × 周期）；面向业务 |
| **复合指标** | 两个及以上派生指标做运算 | 派生指标 op 派生指标 | 支付转化率、客单价、复购率 | 比率/占比/人均，**不可直接相加** |

**判定规则（按顺序问三个问题）**：

1. 这个指标能不能拆成「A ÷ B」或「A - B」或「A × B」？能 → **复合指标**。
2. 去掉时间周期和修饰词（新客/支付/有效…）之后，剩下的部分是不是「某业务过程上的一次聚合」？是 → **派生指标**，剩下的那部分是**原子指标**。
3. 只剩「业务过程 + 度量 + 聚合函数」，没有任何业务限定 → **原子指标**。

**举例走一遍**：

```
"1d_新客_支付订单金额"
  ├─ 1d          时间周期
  ├─ 新客        修饰词（用户维度上的限定）
  └─ 支付订单金额 原子指标 = 支付过程 + 订单金额 + sum

"支付转化率"
  ├─ 分子：1d_支付_买家数（派生）
  └─ 分母：1d_下单_买家数（派生）
  → 复合指标（比率，不可加）
```

> [!important] 为什么要分三层
> **原子指标管复用，派生指标管业务，复合指标管分析。**
> 不分层的后果：业务每提一个新需求（「新客 GMV」「新客支付 GMV」「7 日新客支付 GMV」），开发就重写一遍 SQL，每个 SQL 里都有一份 `sum(pay_amount)` 和一份「新客」的判断逻辑。三个月后，这四份 SQL 里的「新客」定义已经不一样了——这就是口径漂移的起点。
> 分层之后，`sum(pay_amount)` 只有一份，「新客」的判断只有一份，新需求只是**换修饰词组合**。

### 2.2 命名规范：让指标名自己说出五要素

命名公式：

```
派生指标：  [时间周期]_[修饰词]_[原子指标]      例：1d_支付_订单金额
复合指标：  [业务名]_rate / [业务名]_avg         例：pay_conversion_rate
原子指标：  [业务过程]_[度量]                    例：pay_order_amount
```

**完整命名表**：

| 类型 | 公式 | 正确示例 | 错误示例 | 错在哪 |
| --- | --- | --- | --- | --- |
| 原子 | `{过程}_{度量}` | `pay_order_amount` | `gmv` | `gmv` 没说过程（下单/支付）、没说度量（金额/件数） |
| 派生 | `{周期}_{修饰}_{原子}` | `1d_支付_订单金额` | `order_amount_1d` | 顺序错，周期必须打头，便于按前缀扫描 |
| 派生 | 同上 | `7d_新客_支付买家数` | `new_user_gmv` | 「new_user」是修饰词不是周期；且 gmv 不是原子指标 |
| 复合 | `{业务}_rate` | `pay_conversion_rate` | `conversion_rate` | 没说哪一步转化（曝光→点击？下单→支付？） |
| 复合 | `{业务}_avg` | `order_avg_amount` | `atv` | 缩写不可读，且没说分母是订单数还是买家数 |

> [!tip] 命名的两个硬规则
> 1. **周期必须打头**：`1d_ / 7d_ / 1m_`，这样 `show tables like '1d_%'` 能一次捞出所有日粒度指标。
> 2. **一个词只能有一个意思**：`gmv` 如果在有的表里是下单口径、有的表里是支付口径，那这个词就该被禁用，改用 `gmv_create` / `gmv_pay` / `gmv_net`。

### 2.3 指标字典：字段设计与真实样例

指标字典（metric dictionary / metric store）是指标体系的**唯一事实来源**。字段设计：

| 字段 | 说明 | 是否必填 | 示例 |
| --- | --- | --- | --- |
| 指标编码 | 全局唯一，英文，遵循命名规范 | 必填 | `1d_支付_订单金额` |
| 中文名 | 业务方叫法 | 必填 | 支付GMV |
| 英文名 | 程序里用的名字 | 必填 | `gmv_pay_1d` |
| 业务定义 | **用业务语言**说清「算什么」，不含 SQL | 必填 | 统计周期内支付成功的订单金额之和，含运费，不含退款 |
| 计算公式 | 可执行的伪 SQL | 必填 | `sum(pay_amount) where pay_status='SUCCESS'` |
| 数据源表 | 具体到库表 + 分区字段 | 必填 | `dwd_trade_payment`（分区 `dt`=支付日期） |
| 统计粒度 | 一行代表什么 | 必填 | 订单（`order_id`） |
| 过滤条件 | 剔除规则 | 必填 | 剔除测试单、刷单、`pay_status<>'SUCCESS'` |
| 时间口径 | 用哪个时间字段归属 | 必填 | 支付时间 `pay_time` |
| 负责人 | 人，不是团队 | 必填 | 张三 |
| 更新频率 | T+1 / 小时级 | 必填 | T+1，每日 06:00 |
| 版本 | 口径变更必须升版本 | 必填 | v3（2026-09-01 起剔除退款） |

**样例（真实项目里可以直接照这个结构建表）**：

| 指标编码 | 中文名 | 计算公式 | 统计粒度 | 时间口径 | 负责人 | 版本 |
| --- | --- | --- | --- | --- | --- | --- |
| `1d_支付_订单金额` | 支付GMV | `sum(pay_amount)`，`pay_status='SUCCESS'` | 订单 | `pay_time` | 张三 | v3 |
| `1d_下单_买家数` | 下单买家数 | `count(distinct user_id)`，剔除取消单 | 用户 | `create_time` | 李四 | v2 |
| `1d_支付_买家数` | 支付买家数 | `count(distinct user_id)`，`pay_status='SUCCESS'` | 用户 | `pay_time` | 张三 | v2 |
| `pay_conversion_rate` | 支付转化率 | `1d_支付_买家数 / 1d_下单_买家数`，**同 cohort** | 用户 | `create_time` 圈人 | 张三 | v2 |
| `7d_复购_支付买家数` | 7日复购用户数 | 7 日内支付订单数 ≥ 2 的买家数 | 用户 | `pay_time` | 王五 | v1 |
| `1d_访问_访客数` | UV | `count(distinct visitor_id)` | 访客 | `visit_time` | 赵六 | v4 |

> [!warning] 字典里最容易漏的两个字段
> 1. **时间口径**：只写「按支付时间」不够，还要写「跨天支付归属支付日，不回归下单日」。
> 2. **版本 + 生效日期**：口径改了一定要写「从哪天起生效」，否则历史数据和新数据拼在一起，同比就是错的。

### 2.4 口径漂移的五大成因

口径漂移（metric drift）指**同一个指标名，在不同时间/不同人手里算出的数不一样**。五大成因，每个都给真实例子：

| 成因 | 真实例子 | 后果 | 防御手段 |
| --- | --- | --- | --- |
| **业务定义变了** | 去年「新客」= 首次注册，今年改成「首次支付」 | 新客数直接掉 60%，同比不可比 | 升版本 + 变更公告 + 新旧口径双跑一个月 |
| **数据源换了** | 订单金额从 `ods_order` 换成 `ods_order_new`（新表含运费） | GMV 莫名涨 3%，没人发现 | 血缘登记 + 换源必须回归对账（新旧并行跑 7 天） |
| **SQL 实现不一致** | A 用 `count(distinct order_id)`，B 在明细表上 `count(order_id)` | 订单数差 2.3 倍（一单多商品） | 指标只允许从 DWS 汇总层取，禁止各报表直连 DWD 重算 |
| **时区/时间边界不同** | 一方 `create_time >= '2026-10-01'`，另一方用 UTC 存储 | 每天差 8 小时数据，日终对账差 5% | 存储统一时区 + 用 `>= AND <` 半开区间 |
| **去重逻辑不同** | 一方按 `user_id` 去重，一方按 `device_id`；一方剔除退款，一方不剔 | UV 差 15%，复购率差一倍 | 去重键写进字典 + 口径回归测试用例 |

> [!danger] 口径漂移最可怕的不是「数不对」，是「没人发现」
> 上面五个例子里，有四个不会报错——SQL 正常跑完，报表正常出数，只是数字悄悄变了。
> 所以必须有**自动化的口径回归**：给每个核心指标准备一组「固定输入 → 期望输出」的测试用例（比如 10 条构造订单，期望 GMV=1630），每次改 SQL 都跑一遍。这就是指标的单元测试。

### 2.5 去重类指标的坑（重灾区）

**坑一：UV / 去重买家数不可跨维度相加**

```
10-01 UV = 3（v1, v2, v3）
10-02 UV = 3（v2, v3, v4）
两天 UV 相加 = 6
真实两天 UV   = 4（v1, v2, v3, v4）
```

原因：同一个人两天都来了，在日粒度被算了两次。**任何 `count(distinct)` 的结果都不可加**，包括跨天、跨渠道、跨品类。

```sql
-- ❌ 错：日 UV 求和当周 UV
select sum(uv) from (select dt, count(distinct visitor_id) as uv from dwd_traffic_page_view group by dt) t;

-- ✅ 对：直接对整周去重
select count(distinct visitor_id) from dwd_traffic_page_view
where dt between '2026-10-01' and '2026-10-03';
```

**坑二：跨天去重 ≠ 每天去重之和，月活 ≠ 日活之和**

推论：**任何「N 日累计去重」指标都必须重新扫描 N 天明细**，不能靠日指标累加。这就是为什么「月活」比「日活」贵得多——它不是加出来的，是重算的。

**坑三：`count(distinct)` 在分布式下的精度与代价**

| 实现 | 精度 | 代价 | 适用 |
| --- | --- | --- | --- |
| `count(distinct col)` 精确 | 精确 | 一次全量 shuffle，热点值倾斜严重（大 V 用户） | 数据量 < 亿级、要求精确对账 |
| `approx_count_distinct(col, rsd)` 近似（HyperLogLog） | 近似，相对误差约 `rsd`（Spark 默认 0.05，**待验证**） | 内存固定（几 KB/分组），可并行合并 | UV、曝光人数等大基数、允许 1~5% 误差 |

```sql
-- Spark 3.5：相对误差 5% 的近似去重
select dt, approx_count_distinct(visitor_id, 0.05) as uv_approx
from dwd_traffic_page_view
where dt between '2026-10-01' and '2026-10-03'
group by dt;

-- Hive 3.x：若集群无 approx_count_distinct，用精确 count(distinct)，或改用
-- 预聚合 bitmap（如 Doris/ClickHouse 的 bitmap_union），具体函数待验证
```

> [!warning] HLL 的三个使用禁忌
> 1. **不能用于对账/结算**：误差 5% 在财务场景是灾难。
> 2. **不能相加**：HLL  sketch 可以**合并（merge）**，但不能把两个 HLL 的估算值相加。
> 3. **小基数不准**：HLL 在基数很小时误差比例更大，分组后每组只有几十人时不要用。

**坑四：去重键选错，指标含义就变了**

`count(distinct user_id)` 是「登录用户数」，`count(distinct visitor_id)` 是「访客数（含未登录）」，`count(distinct device_id)` 是「设备数」。三个都能叫「UV」，差 20%~40%。**字典里必须写死去重键**。

### 2.6 比率类指标的坑

**坑一：分子分母必须同源、同过滤、同时间窗口**

```sql
-- ❌ 错：分子按支付时间，分母按下单时间，跨天支付的用户会被算成"没转化"
select
  (select count(distinct user_id) from dwd_trade_payment
    where dt between '2026-10-01' and '2026-10-03' and pay_status='SUCCESS')
  /
  (select count(distinct user_id) from dwd_trade_order_detail
    where dt between '2026-10-01' and '2026-10-03' and order_status<>'CANCEL');
```

分子分母用的是**两个不同的人群**（支付时间在窗口内的人 vs 下单时间在窗口内的人），算出来的比率没有业务含义。正确做法是**用下单时间圈定 cohort，再看这批人最终有没有支付**。

**坑二：「转化率」的分母到底是谁**

| 指标 | 分子 | 分母 | 回答的问题 |
| --- | --- | --- | --- |
| 点击率 CTR | 点击次数 | 曝光次数 | 素材/位置好不好 |
| 访问-下单转化率 | 下单买家数 | 访问 UV | 商品/价格有没有吸引力 |
| 下单-支付转化率 | 支付买家数 | 下单买家数 | 支付流程/库存/价格有没有问题 |
| 全链路转化率 | 支付买家数 | 曝光人数 | 整体效率 |

四个都叫「转化率」，分母差 2~3 个数量级。**看到「转化率」三个字，第一句话应该是「分母是谁」**。

**坑三：比率不能求平均**

```
10-01：100 次访问，10 单 → 10%
10-02：1000 次访问，50 单 → 5%
两天平均转化率 ≠ (10% + 5%) / 2 = 7.5%
正确 = (10 + 50) / (100 + 1000) = 5.45%
```

这是辛普森悖论在数仓里的日常表现。**所有比率指标的汇总，必须回到「总分子 / 总分母」重算**，不能对日比率求平均。

### 2.7 时间口径：三个时间，三个数

一张订单至少有四个时间：**下单时间 `create_time`、支付时间 `pay_time`、发货时间 `deliver_time`、完成时间 `finish_time`**。选哪个，决定这个数属于哪一天。

| 场景 | 应该用 | 理由 |
| --- | --- | --- |
| 考核 GMV 增长 | 支付时间 | 只有付了钱才算成交 |
| 分析下单行为/漏斗 | 下单时间 | 漏斗第一环必须按行为发生时间 |
| 财务收入确认 | 完成时间（或发货时间） | 收入确认准则 |
| 退款率 | 支付时间（分母）+ 退款时间（分子） | 分母是「哪批支付」，分子是「哪批退款」 |

**T+1 口径下「今天」到底指哪天**：

```
调度跑批：2026-10-25 凌晨 02:00 跑 T+1 任务
业务日期 dt = 2026-10-24（昨天）
SQL 里绝对不能写 current_date()，要写调度参数 ${bizdate} 或 date_sub(current_date(), 1)
```

```sql
-- ❌ 错：跑批跨零点、或补数时，"今天"会漂
where dt = date_format(current_date(), 'yyyy-MM-dd')

-- ✅ 对：用调度参数，补历史数据时行为一致
where dt = '${bizdate}'
```

**时间边界写法**：

```sql
-- ❌ 错：漏掉 10-31 当天 00:00 之后的数据（如果字段带时分秒）
where create_time between '2026-10-01' and '2026-10-31'

-- ✅ 对：半开区间
where create_time >= '2026-10-01 00:00:00' and create_time < '2026-11-01 00:00:00'
```

**跨时区**：跨境业务必须存两列（`event_time_local` + `event_time_utc`），报表按业务所在时区聚合。只存一列，大促跨时区必然对不上。

### 2.8 退款/取消要不要扣 GMV：三种口径，必须写死一种

| 口径 | 公式 | 适用场景 | 缺点 |
| --- | --- | --- | --- |
| **下单口径** | `sum(下单金额)`，剔除取消单 | 考核增长、活动效果、商家报名门槛 | 含未支付、含后续退款，虚高 |
| **支付口径** | `sum(支付成功金额)` | 收入预估、转化分析、对外披露常用 | 含后续退款，仍会虚高 |
| **净额口径** | `sum(支付金额) - sum(退款金额)` | 财务结算、利润分析、经营分析 | 退款跨期会让**历史数字变动** |

**退款归属期**是比「扣不扣」更细的一层：

- **按原单期归属**：10-01 的订单在 10-20 退款，冲减 10-01 的 GMV → 历史数据会变，但「这批订单最终贡献多少」是准的。
- **按退款发生期归属**：退款算在 10-20 → 历史数据稳定，但「10-01 的 GMV」里含着已退的钱。

> [!important] 生产上的写法
> 1. **同一个指标名只能对应一种口径**，三种口径就是三个指标编码（`gmv_create` / `gmv_pay` / `gmv_net`）。
> 2. **对外汇报用支付口径，财务结算用净额口径，活动复盘用下单口径**——这句话必须写进字典的「业务定义」里。
> 3. **净额口径必须声明退款归属期**，否则每月 1 号财务和数仓必然吵架。

### 2.9 指标治理流程：新增一个指标要走六步

```
① 注册（提需求，填字典草稿） → ② 评审（能否复用原子指标？口径是否冲突？）
→ ③ 开发（优先在 DWS 层加，不在 ADS 里写复杂 SQL）
→ ④ 验收（与旧口径/人工核算对账，差异 < 0.5% 才通过）
→ ⑤ 发布（字典生效，标注版本和生效日期，通知下游）
→ ⑥ 监控（日环比突变 > 30% 告警；季度清理无访问的僵尸指标）
```

**评审环节最关键的一条**：**先问「能不能用已有的原子指标 + 新修饰词拼出来」**。能拼就不要新建原子指标——原子指标每多一个，全公司的口径维护成本就多一份。

### 3.2 实验一：把四个指标拆成原子 / 派生 / 复合

```
GMV（支付口径）
└── 派生：1d_支付_订单金额
    └── 原子：pay_order_amount = 支付过程 + 订单金额 + sum
        └── 过滤：pay_status = 'SUCCESS'

支付转化率
├── 派生：1d_支付_买家数 ── 原子：pay_buyer_cnt = 支付过程 + 买家 + count distinct
└── 派生：1d_下单_买家数 ── 原子：order_buyer_cnt = 下单过程 + 买家 + count distinct
    └── 复合：分子 ÷ 分母（同 cohort）

客单价 ATV
├── 派生：1d_支付_订单金额（GMV）
└── 派生：1d_支付_订单数 ── 原子：pay_order_cnt = 支付过程 + 订单 + count distinct
    └── 复合：金额 ÷ 订单数（注意：不是 ÷ 买家数）

复购率
├── 派生：7d_复购_支付买家数（窗口内支付订单数 ≥ 2 的买家）
└── 派生：7d_支付_买家数
    └── 复合：复购买家数 ÷ 支付买家数
```

> 拆解树的价值：**每一个叶子节点都必须能落到一行字典**。落不下去，说明这个指标还没定义清楚。

### 3.3 实验二：同一份数据，三种 GMV 口径

```sql
with ord as (          -- 口径 A：下单口径（按下单时间，剔除取消单）
    select sum(item_amount - discount_amount) as amt
    from dwd_trade_order_detail
    where dt between '2026-10-01' and '2026-10-03'
      and order_status <> 'CANCEL'
),
ord_all as (           -- 口径 D：下单口径但不剔除取消单（很多事故就是这么来的）
    select sum(item_amount - discount_amount) as amt
    from dwd_trade_order_detail
    where dt between '2026-10-01' and '2026-10-03'
),
pay as (               -- 口径 B：支付口径（按支付时间）
    select sum(pay_amount) as amt
    from dwd_trade_payment
    where dt between '2026-10-01' and '2026-10-03'
      and pay_status = 'SUCCESS'
),
refund as (            -- 口径 C 的减项：退款（按退款发生时间）
    select coalesce(sum(refund_amount), 0) as amt
    from dwd_trade_refund
    where dt between '2026-10-01' and '2026-10-03'
      and refund_status = 'SUCCESS'
)
select 'A_下单口径' as caliber, ord.amt as gmv from ord
union all
select 'B_支付口径', pay.amt from pay
union all
select 'C_净额口径', pay.amt - refund.amt from pay cross join refund
union all
select 'D_下单含取消', ord_all.amt from ord_all;
```

**预期结果**：

| 口径 | gmv | 差额来源 |
| --- | --- | --- |
| A 下单口径 | 1630.00 | 含 o4（10-02 下单、10-04 才支付），不含 o5（取消） |
| B 支付口径 | 1130.00 | 不含 o4（跨天支付，落到 10-04），不含 o5（未支付） |
| C 净额口径 | 1030.00 | B 减去 r1 的 100（r2 的 400 在 10-04） |
| D 下单含取消 | 1750.00 | A 加上 o5 的 120 |

**四个数，同一份数据，同一段时间，都叫「GMV」**。差最多的两个相差 70%。这就是为什么「口径文档化」不是形式主义——**没有字典，这四个数会在四份报表里同时存在，然后有人在会上问「为什么你们的 GMV 和我们不一样」**。

### 3.4 实验三：支付转化率——两种算法差 20 个百分点

```sql
-- ✅ 正确：cohort 口径（按下单时间圈人，看这批人最终有没有支付）
with ord as (
    select distinct user_id
    from dwd_trade_order_detail
    where dt between '2026-10-01' and '2026-10-03'
      and order_status <> 'CANCEL'
),
pay as (
    select distinct o.user_id
    from dwd_trade_order_detail o
    join dwd_trade_payment p
      on o.order_id = p.order_id
     and p.pay_status = 'SUCCESS'
    where o.dt between '2026-10-01' and '2026-10-03'
      and o.order_status <> 'CANCEL'
)
select
    pay.cnt   as pay_buyer_cnt,
    ord.cnt   as order_buyer_cnt,
    round(pay.cnt / ord.cnt, 4) as pay_conversion_rate
from (select count(*) as cnt from pay) pay
cross join (select count(*) as cnt from ord) ord;

-- ❌ 错误：分子按支付时间过滤，跨天支付的用户被判为"未转化"
select
    pay.cnt   as pay_buyer_cnt,
    ord.cnt   as order_buyer_cnt,
    round(pay.cnt / ord.cnt, 4) as pay_conversion_rate_wrong
from (
    select count(distinct user_id) as cnt from dwd_trade_payment
    where dt between '2026-10-01' and '2026-10-03' and pay_status = 'SUCCESS'
) pay
cross join (
    select count(distinct user_id) as cnt from dwd_trade_order_detail
    where dt between '2026-10-01' and '2026-10-03' and order_status <> 'CANCEL'
) ord;
```

**预期结果**：

| 算法 | 分子 | 分母 | 转化率 |
| --- | --- | --- | --- |
| cohort（正确） | 4（1001/1002/1003/1005） | 5（1001/1002/1003/1004/1005） | 0.8000 |
| 按支付时间（错误） | 3（1003 在 10-04 支付，被排除） | 5 | 0.6000 |

> [!warning] 20 个百分点的差距，只因为一个 where 条件
> 这个错误在真实项目里极常见，而且**不会报错、不会有人质疑**——因为 60% 看起来也很合理。唯一能发现它的方式是：把「跨天支付」这个场景写进**口径测试用例**。
> 另外注意：`ord` 和 `pay` 里的 `join` 会因为「一单多商品」把订单放大（o1 有 2 行），所以必须 `distinct` 后再 count，或者先聚合到订单粒度。这就是「比率类指标也要防放大」的原因。

### 3.5 实验四：复购率与客单价——分母选谁

```sql
-- 复购率（7 日窗口简化为 10-01~10-03）
with pay_ord as (
    select user_id, count(distinct order_id) as ord_cnt
    from dwd_trade_payment
    where dt between '2026-10-01' and '2026-10-03'
      and pay_status = 'SUCCESS'
    group by user_id
)
select
    sum(if(ord_cnt >= 2, 1, 0))                        as repeat_buyer_cnt,
    count(*)                                           as pay_buyer_cnt,
    round(sum(if(ord_cnt >= 2, 1, 0)) / count(*), 4)   as repeat_rate
from pay_ord;

-- 客单价：两种分母，两个数
select
    sum(pay_amount)                                                  as gmv_pay,
    count(distinct order_id)                                         as order_cnt,
    count(distinct user_id)                                          as buyer_cnt,
    round(sum(pay_amount) / count(distinct order_id), 2)             as atv_per_order,
    round(sum(pay_amount) / count(distinct user_id), 2)              as atv_per_buyer
from dwd_trade_payment
where dt between '2026-10-01' and '2026-10-03'
  and pay_status = 'SUCCESS';
```

**预期结果**：

| 指标 | 值 | 说明 |
| --- | --- | --- |
| 复购买家数 | 2 | 1001（o1,o3）、1002（o2,o6） |
| 支付买家数 | 3 | 1001、1002、1005 |
| 复购率 | 0.6667 | 2 / 3 |
| 客单价（÷订单数） | 226.00 | 1130 / 5 |
| 客单价（÷买家数） | 376.67 | 1130 / 3 |

> **两个都叫「客单价」，差 66%**。行业惯例：`ATV`（average transaction value）= 金额/订单数，`ARPU`（average revenue per user）= 金额/用户数。字典里必须写英文名，否则中文名一定会打架。

### 3.6 实验五：UV 的可加性与近似去重

```sql
-- 每日 UV
select dt, count(distinct visitor_id) as uv
from dwd_traffic_page_view
where dt between '2026-10-01' and '2026-10-03'
group by dt order by dt;

-- ① 错误：日 UV 相加
select sum(uv) as uv_sum from (
    select dt, count(distinct visitor_id) as uv
    from dwd_traffic_page_view
    where dt between '2026-10-01' and '2026-10-03'
    group by dt
) t;

-- ② 正确：整段重新去重
select count(distinct visitor_id) as uv_3d
from dwd_traffic_page_view
where dt between '2026-10-01' and '2026-10-03';

-- ③ 近似：HyperLogLog（Spark 3.5，rsd=0.05）
select approx_count_distinct(visitor_id, 0.05) as uv_hll
from dwd_traffic_page_view
where dt between '2026-10-01' and '2026-10-03';
```

**预期结果**：

| 算法 | 值 | 说明 |
| --- | --- | --- |
| 10-01 UV | 3 | v1, v2, v3 |
| 10-02 UV | 3 | v2, v3, v4 |
| 10-03 UV | 2 | v1, v4 |
| 日 UV 相加 | 8 | ❌ 重复计算了 v1/v2/v3/v4 |
| 3 日真实 UV | 4 | ✅ v1, v2, v3, v4 |
| HLL 近似 | 4（可能 4±1） | 小基数下误差比例大，**待验证** |

> [!danger] 「UV 相加」是报表里最常见的错误
> 因为它**看起来完全合理**：每天 3 万人，一周就是 21 万人。实际上可能只有 8 万人。
> 防御手段只有一个：**DWS 层不要产出「可加的 UV」这种字段**，只产出明细或 bitmap/sketch；汇总层要么重算，要么 merge sketch。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 两份报表 GMV 差 5% | 一个下单口径、一个支付口径 | 按 `order_id` 全外连接对比差异订单 | 拆成三个指标编码，字典写死使用场景 |
| GMV 每月 1 号莫名变小 | 净额口径按退款发生期归属，上月退款冲了本月 | 看退款时间分布 | 明确归属期，或改用支付口径对外 |
| 订单数比明细行数少一半 | 明细表 `count(order_id)` 没去重 | `count(*)` vs `count(distinct order_id)` | 指标只从汇总层取，或强制 `distinct` |
| 转化率算出 > 100% | 分子分母人群不同源 | 检查两边 where 的时间字段和过滤条件 | 统一 cohort，用同一张事实表圈人 |
| 日 UV 加起来 ≠ 周 UV | `count(distinct)` 不可加 | 对比 `sum(日UV)` 和整周去重 | 周 UV 重新扫描明细，或 merge HLL sketch |
| 大促当天 UV 任务跑 3 小时 | `count(distinct)` 单点 shuffle + 热点 | 看 stage 的 shuffle 数据量和 task 倾斜 | 改 `approx_count_distinct`，或预聚合 bitmap |
| 新客数突然掉 60% | 业务把「新客」从注册改成了首单 | 对比口径变更记录 | 升版本 + 双跑 + 公告，历史数据不重算只标注 |
| 同比数据不可比 | 数据源换了（含运费/含税） | 血缘 + 新旧表并行对账 | 换源必须回归测试，差异 > 0.5% 不上线 |
| 每天 00:00~08:00 数据缺失 | 时区没统一（UTC vs 东八区） | 看时间字段的小时分布 | 存储统一时区，展示层转换 |
| 报表里转化率显示 0 而不是 "-" | 分母为 0 时 `0/0` 返回 NULL，被前端转成 0 | 看分母为 0 的分组 | 分母为 0 时返回 NULL，前端显示 "-" |

## 五、面试追问

> [!question] 1. GMV 怎么定义？
> **一句话答法**：先反问口径——下单口径（按下单时间、剔取消单）、支付口径（按支付时间、支付成功）、净额口径（支付减退款）。我们对外用支付口径，财务结算用净额，活动复盘用下单口径。
> **追问陷阱**：「为什么不全用支付口径」——活动复盘要看「用户下了多少」，未支付的订单也反映意愿；财务要看「实际收到多少钱」，必须扣退款。场景不同，口径不能统一。

> [!question] 2. 转化率怎么算？分母是谁？
> **一句话答法**：先确认是哪一步转化。点击率分母是曝光，下单转化率分母是访问 UV，支付转化率分母是下单买家数；分子分母必须同源、同过滤、同时间窗口（同 cohort）。
> **追问陷阱**：「跨天支付的用户算不算转化」——算，cohort 口径按下单时间圈人，看他最终有没有支付；按支付时间过滤分子会漏掉跨天支付，转化率虚低。

> [!question] 3. UV 能不能相加？
> **一句话答法**：不能。`count(distinct)` 的结果跨天、跨渠道、跨品类都不可加，因为同一个人会被重复计数；要算周期 UV 必须对整段明细重新去重，或者合并 HLL/bitmap sketch。
> **追问陷阱**：「那日报表里的周累计 UV 怎么出」——单独跑一个周任务重算，不能靠日表累加；数据量大就用 HLL sketch 预聚合，查询时 merge。

> [!question] 4. 口径不一致怎么治理？
> **一句话答法**：三步——① 建指标字典，把五要素写死；② 指标只在 DWS 层算一次，报表禁止直连明细重算；③ 加口径回归测试（固定输入 → 期望输出），改 SQL 必须跑通。
> **追问陷阱**：「字典谁来维护、怎么保证更新」——指标 owner 维护，新增指标必须走评审，变更必须升版本 + 公告 + 双跑。

> [!question] 5. 指标字典怎么设计？
> **一句话答法**：十二个字段——编码、中英文名、业务定义、计算公式、数据源表、统计粒度、过滤条件、时间口径、负责人、更新频率、版本、生效日期。核心是「业务定义用业务语言写，公式用 SQL 写，两者必须能互相验证」。
> **追问陷阱**：「业务定义和计算公式有什么区别」——业务定义给业务方看（不含 SQL），公式给开发看；两者不一致就说明口径没对齐。

> [!question] 6. 退款要不要扣 GMV？
> **一句话答法**：看场景。对外披露/增长考核用支付口径不扣；财务结算/利润分析用净额口径扣。关键是**同一个指标名只能对应一种口径**，并且净额口径必须声明退款归属期（原单期还是退款发生期）。
> **追问陷阱**：「按原单期归属会有什么问题」——历史数据会变，月报出了以后还可能被改，所以财务口径通常按退款发生期，经营分析按原单期，两套都要有。

> [!question] 7. 原子指标、派生指标、复合指标怎么区分？
> **一句话答法**：能拆成两个指标运算的是复合；去掉时间周期和修饰词后只剩「业务过程+度量+聚合」的是派生，剩下的核是原子。
> **追问陷阱**：「为什么要分这么细」——原子指标管复用（全公司几十个），派生管业务组合（几百个），复合管分析（比率）；不分层就会每个需求重写一遍 SQL，口径必然漂移。

> [!question] 8. 同比环比为什么会失真？
> **一句话答法**：口径漂移。五大成因：业务定义变了、数据源换了、SQL 实现不一致、时区/时间边界不同、去重逻辑不同。任何一种都会让两个时间段的数不可比。
> **追问陷阱**：「怎么发现」——口径回归测试 + 变更记录 + 日环比突变告警；纯靠人看报表发现不了。

> [!question] 9. 复购率怎么算？有几种算法？
> **一句话答法**：至少三种——① 复购用户数/支付用户数（最常用）；② 复购订单数/总订单数；③ (总订单数-买家数)/买家数。差别在「按人还是按单」，字典里必须写死，还要写清时间窗口（7 日/30 日/自然月）。
> **追问陷阱**：「窗口怎么定」——按业务复购周期定（快消 7 日、家电 1 年），并且窗口内必须**首单之后**的订单才算复购，不能把首单算进去。

> [!question] 10. `count(distinct)` 大基数怎么办？
> **一句话答法**：三条路——① 换 `approx_count_distinct`（HLL，误差约 5%，适合 UV）；② 预聚合 bitmap/sketch，查询时 merge；③ 缩小去重范围（先按维度过滤再 distinct）。
> **追问陷阱**：「HLL 能用于财务对账吗」——不能，误差不可接受；对账必须精确去重，宁可跑慢。

> [!question] 11. 新指标上线怎么验收？
> **一句话答法**：三件事——与旧口径/人工核算对账（差异 < 0.5%）、跑口径测试用例（固定输入期望输出）、灰度观察一周（日环比无异常突变）。
> **追问陷阱**：「对不上但业务说新口径对怎么办」——那就升版本、双跑一个月、公告下游，不能直接覆盖旧指标。

## 六、自测题

> [!question] 1.（单选）下面哪个是**原子指标**？
> A. `1d_支付_订单金额`
> B. `pay_order_amount`（支付过程 + 订单金额 + sum）
> C. 支付转化率
> D. `7d_新客_支付买家数`

> [!question] 2.（单选）10-01 UV=3、10-02 UV=3、10-03 UV=2，其中 v1/v2/v3/v4 有跨天重复，三天真实 UV 最可能是？
> A. 8
> B. 6
> C. 4
> D. 无法确定

> [!question] 3.（判断）比率类指标可以直接对每天的比率求平均得到周比率。

> [!question] 4.（场景设计）业务说「上周 GMV 跌了 20%」，你去排查，发现数据正常。请列出至少 4 个可能导致「数字变了但业务没变」的口径原因，并说明每个怎么验证。

> [!question] 5.（场景设计）设计「新客 7 日复购率」这个指标：写出它的原子/派生/复合拆解、完整字典字段（至少 8 个）、以及 SQL 实现思路。说明分子分母分别怎么圈人、时间窗口怎么定。

> [!success]- 答案与解析（点击展开）
> **1. B**
> 原子指标只有「业务过程 + 度量 + 聚合」，不含时间周期和修饰词。A、D 是派生（带 `1d`/`7d` 和修饰词），C 是复合。
>
> **2. C**
> 三天访客集合是 {v1,v2,v3,v4}，去重后 4 人。8 是「日 UV 相加」的错误答案——这正是 `count(distinct)` 不可加的经典表现。
>
> **3. 错误**
> 必须回到「总分子 / 总分母」重算。例：10-01 是 10/100=10%，10-02 是 50/1000=5%，平均 7.5%，真实是 60/1100=5.45%。这是辛普森悖论。
>
> **4. 参考思路**
> | 可能原因 | 验证方法 |
> | --- | --- |
> | 口径从支付改成下单（或反过来） | 查指标字典版本变更记录；用两种口径各算一遍 |
> | 数据源换了（新表含/不含运费、含/不含税） | 血缘对比；新旧表同窗口并行跑，看差异是否恒定比例 |
> | 退款归属期改了（原单期 → 退款发生期） | 对比退款时间分布；看历史月份是否被重算 |
> | 时区/时间边界改了（`<=` 改成 `<`，或 UTC 改东八区） | 看首尾两天的数据量是否异常；检查时间字段小时分布 |
> | 去重逻辑改了（`user_id` → `device_id`，或剔除刷单） | 对比去重键；看差异是否集中在某类用户 |
> | 上游补数/重跑导致分区被覆盖 | 查调度记录和分区更新时间；对比 `count(*)` |
>
> **排查顺序**：先确认「是数据变了还是口径变了」——用同一份快照、同一段 SQL 重跑，如果数没变，就是口径/数据源问题；如果数变了，才是数据问题。
>
> **5. 参考拆解**
> ```
> 新客 7 日复购率
> ├── 分子：7d_新客复购_支付买家数
> │    └── 原子：pay_buyer_cnt（支付过程 + 买家 + count distinct）
> │    └── 修饰词：新客（首单在窗口内）+ 复购（窗口内支付订单数 ≥ 2）
> └── 分母：7d_新客_支付买家数
>      └── 同一批新客，窗口内至少支付 1 次
> → 复合：分子 ÷ 分母
> ```
> **字典关键字段**：
> | 字段 | 值 |
> | --- | --- |
> | 指标编码 | `7d_新客复购_支付买家数_div_7d_新客_支付买家数` |
> | 业务定义 | 统计周期内首单的新客，在其首单后 7 日内支付 ≥ 2 次的买家占比 |
> | 统计粒度 | 用户 |
> | 过滤条件 | 剔除测试单、刷单、退款单（可选） |
> | 时间口径 | 首单时间圈 cohort，复购订单按支付时间落在首单后 7×24 小时内 |
> | 版本 | v1 |
>
> **SQL 思路**：
> ```sql
> with first_order as (           -- 每个用户的首单时间（新客判定）
>     select user_id, min(pay_time) as first_pay_time
>     from dwd_trade_payment
>     where pay_status = 'SUCCESS' and dt <= '${bizdate}'
>     group by user_id
> ),
> cohort as (                     -- 窗口内首单的新客
>     select user_id, first_pay_time
>     from first_order
>     where first_pay_time >= '2026-10-01 00:00:00'
>       and first_pay_time <  '2026-10-08 00:00:00'
> ),
> repurchase as (                 -- 首单后 7 日内支付 >= 2 次
>     select c.user_id
>     from cohort c
>     join dwd_trade_payment p
>       on c.user_id = p.user_id
>      and p.pay_status = 'SUCCESS'
>      and p.pay_time >= c.first_pay_time
>      and p.pay_time <  date_add(c.first_pay_time, 7)
>     group by c.user_id
>     having count(distinct p.order_id) >= 2
> )
> select
>     (select count(*) from repurchase) / (select count(*) from cohort) as repeat_rate_7d;
> ```
> **两个易错点**：① 窗口必须是「首单时间 + 7 天」而不是「自然周」，否则周一和周日下单的新客观察期长度不同；② 复购订单必须包含首单（`>= first_pay_time`），否则「支付 2 次」实际是「首单 + 复购 2 次」= 3 次。
