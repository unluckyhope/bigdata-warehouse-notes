# 02-04 三类事实表

> [!abstract] 一句话结论
> 三类事实表的区别不是「存什么」，而是**「什么时候写、写几次、能不能改」**：事务表事件发生就追加、只增不改；周期快照按期拍全量、每期一行；累积快照一个流程一行、被反复 update。
> 本质：**事务表存「变化量」，快照表存「状态量」；变化量可加，状态量半可加。**
> 选错的代价不是表难看，而是指标算错且无法回溯——用事务表算库存就是最经典的翻车。

---

## 一、心智模型：三个问题定形状

```
① 什么时候写？  事件发生时 / 周期到点 / 流程推进一步时
② 写几次？      一次 / 每期一次 / 同一行被写 N 次
③ 能不能改？    不能（append-only）/ 不能（只追加新期）/ 必须能（upsert）
```

| 三问 | 事务事实表 | 周期快照事实表 | 累积快照事实表 |
| --- | --- | --- | --- |
| 什么时候写 | 事件发生那一刻 | 固定周期到点 | 流程每推进一步 |
| 写几次 | 一次 | 每期一批新行 | 同一行 N 次 |
| 能不能改 | 不能 | 不能（只追加新期） | 必须能 |

「能不能改」是第一性原理，它决定**存储引擎、写入语法、幂等策略**：不能改 → 普通外部表 + 分区覆盖，成本最低；必须改 → 上 ACID / Delta / Hudi（compaction、小文件、并发写的代价），或每天全表重算。

事实表 = **外键 + 度量 + 粒度声明 + 可选退化维度**。只有粒度不能事后改：度量能加列、维度能加外键、分区能重建，但粒度错了（订单行表混进订单级优惠），所有下游指标都要重写。

**可加性**是三类事实表存在的根本原因：

| 类型 | 定义 | 例子 | 正确聚合 |
| --- | --- | --- | --- |
| 可加 additive | 任意维度都能 `sum` | 金额、件数、次数 | `sum()` |
| 半可加 semi-additive | 跨维度可加，**跨时间不可加** | 库存、余额、会员数 | 期末值 / 日均值 |
| 不可加 non-additive | 任何维度都不能直接 `sum` | 单价、比率、去重人数 | 拆分子分母再算 |

「10-01 库存 120、10-02 库存 100、10-03 库存 90」，`120+100+90=310` 没有业务含义；但三个仓库的库存相加有意义。**流量 vs 存量**是判断可加性最快的方法。

> [!tip] 生产写法
> 半可加指标的定义里必须显式写「时间聚合方式」：期末值 / 期初值 / 日均值。只写「库存」两个字的指标，迟早会被 `sum` 成天文数字。

## 二、核心知识点

### 2.1 事务事实表：一行一个事件，只增不改

事件每发生一次追加一行。**主键 = 事件唯一标识**：单据号（`order_id`）、单据 + 行号（`order_id + item_seq`）、流水号（`txn_id`）。**粒度 = 最细原子事件**，聚合留到 DWS。

```sql
insert overwrite table dwd.dwd_fact_order_item_txn partition (dt = '2026-10-03')
select oi.order_id, oi.item_seq, oi.sku_id, oi.qty, oi.item_amount,
       o.create_time as order_create_time,      -- 业务时间作为字段
       current_timestamp() as etl_time
from ods.ods_order_item oi
join ods.ods_order o on oi.order_id = o.order_id
where oi.dt = '2026-10-03';
```

> [!important] 两个时间：业务时间 vs 入库时间
> **业务时间**（`order_create_time`）算时长、做同期对比；**入库时间**（`dt` 分区）做增量、重跑、生命周期。
> **分区必须按入库时间**。按业务时间分区的话，10-01 下单、10-03 才同步的订单无处可放——补进 10-01 要重跑历史，补进 10-03 又和分区语义矛盾。

**三个变体**：① 标准事务表（度量恒正）；② 可撤销事务表（退款追加负数，`sum` 自动抵消，原始交易永远可查）；③ 无事实事实表（无度量，见 2.6）。

```sql
-- ✅ 退款用负值追加，原支付记录不动
insert into dwd.dwd_fact_payment_txn
select refund_id, order_id, -refund_amount, 'REFUND', refund_time, '2026-10-04'
from ods.ods_refund where dt = '2026-10-04';
```

这样「订单净收款 = `sum(amount)`」永远成立，不需要 `case when status='REFUNDED' then -x` 这种容易漏条件的写法。迟到数据补写对应入库日期分区即可，但要在调度层记录影响范围。

### 2.2 周期快照事实表：按期给状态拍全量照

固定周期对某类实体的**状态**拍一次全量。**主键 = `(快照日期, 实体键)`**，如 `(dt, sku_id, warehouse_id)`。**粒度 = 实体 × 周期**。

> [!warning] 不要每天从历史全量重放
> `dt <= 当前` 的写法随天数线性变慢。正确做法是 **今日快照 = 昨日快照 + 今日净变化**，用 `full outer join` 兜住「昨日有今日无」「今日新增」两种情况。这也是周期快照必须有「期初」概念的原因——它不是冗余，而是增量的锚点。

**四条设计要点**：① **每期必须有一行，状态没变也要有**（库存 0 也写 `stock_qty=0`，否则「多少 SKU 缺货」会因缺行算错）；② **只存期末不存期初**（期初 = 上期期末，存两份必然自相矛盾）；③ **快照要能独立回答问题**，不要指望再 join 事务表补；④ **分区键用 `dt`**，不用 `snapshot_time`，避免同一天多时间点的歧义。

场景：库存日快照、余额日快照、购物车日快照、会员等级月快照、应收账龄、商品价格日快照。价格最容易被忽略：只在 `dim_product` 存当前价，「10-01 的 GMV」就会算错。

### 2.3 累积快照事实表：一个流程一行，被反复 update

一行代表一个**有明确起止的流程实例**（订单、工单、理赔、贷款、物流单），每推进一步更新这一行的里程碑字段。**主键 = 流程实例 id**，不是 `(order_id, dt)`——加了日期就变成周期快照。**行数 = 流程实例数，不随天数增长**。

| 落地方式 | 做法 | 适用 |
| --- | --- | --- |
| 全表重算覆盖 | 每天从全量事件重放，`insert overwrite` 整表 | 千万级以内，最稳、绝对幂等 |
| 增量 merge | `merge into` 按 `order_id` upsert | 上亿级，且引擎支持 ACID/Delta/Hudi |

> [!important] 分区键只能是「流程创建日期」
> 按「更新日期」分区的话，10-01 下单、10-05 签收的订单会在 update 时从 `dt=2026-10-01` 移到 `dt=2026-10-05`。分区表不支持跨分区 update，只能 delete + insert，代价极高且重跑易重复。**按 `create_dt` 分区**，行永远不动。

| 列 | 含义 | 备注 |
| --- | --- | --- |
| `create_time` | 下单 | 流程起点，非空 |
| `pay_time` / `ship_time` / `receive_time` | 支付 / 发货 / 签收 | 未达成为 NULL |
| `cancel_time` | 取消 | 可能与支付并存（付后取消） |
| `refund_time_first` / `refund_time_last` / `refund_cnt` | 首次 / 末次退款 / 次数 | 可重复里程碑的压缩表达 |
| `current_status` | 当前状态 | 状态机节点 |
| `pay_lag_sec` / `ship_lag_sec` / `receive_lag_sec` / `total_lag_sec` | 各段及全流程时长 | 派生列，由时间戳算出 |

**既存时间戳又存 lag**：时间戳是事实，lag 是派生。事实必须留，否则口径变了无法重算；lag 用来固化口径、减少下游重复计算，只能由时间戳派生，**不能反向**。

> [!warning] lag 的三个细节
> ① **单位用秒不用天**——用天会把 23 小时和 1 小时都算成 1 天；② **未达成填 NULL 不填 0**——填 0 会把「还没支付」算成「0 秒支付成功」；③ **算时长用 `unix_timestamp(b)-unix_timestamp(a)`**，`datediff` 跨零点就算 1 天。

### 2.4 三张表的完整对比

| 维度 | 事务事实表 | 周期快照事实表 | 累积快照事实表 |
| --- | --- | --- | --- |
| 回答的问题 | 发生了什么、多少次 | 某时点状态是什么 | 走到哪一步、每步多久 |
| 主键 | 事件 id（或 单据号+行号） | `(快照日期, 实体键)` | 流程实例 id |
| 粒度 | 最细原子事件 | 实体 × 周期 | 一个流程实例 |
| 行数增长 | 随事件数线性增长 | 实体数 × 期数 | 流程实例数，不随天数增长 |
| 写入方式 | `insert` / 分区覆盖 | `insert overwrite` 分区 | `merge` / 全表重算 |
| 能否修改 | 不能（append-only） | 不能（只追加新期） | 必须能（update） |
| 可加性 | 全可加 | 半可加 | 度量可加，时长不可加 |
| 更新频率 | 一次性 | 每期一次 | 每推进一步一次 |
| 迟到数据 | 补分区即可 | 重算该期快照 | 重放该流程全量事件 |
| 幂等策略 | 分区覆盖 | 分区覆盖 | 主键 upsert / 整表重算 |
| 典型场景 | 订单明细、支付流水、退款 | 库存、余额、价格日快照 | 订单全流程、工单、理赔 |
| 典型查询 | 某天 GMV、活动参与次数 | 某天库存、月末余额 | 平均支付时长、履约周期 |

> [!tip] 一句话记忆
> 事务表是**流水账**，周期快照是**每天一张照片**，累积快照是**一个人的简历**。流水账能算出任何东西但慢且依赖完整性；照片查得快但只反映那一刻；简历只有一份，但每次跳槽都要改。

### 2.5 非单调流程：回退、多次退款、重复支付

累积快照的教科书假设是「流程单调向前」，真实业务几乎不满足：

| 情况 | 例子 | 冲击 |
| --- | --- | --- |
| 流程回退 | 已发货→退款关闭、已签收→退货 | `current_status` 倒退，后续时间戳永远为空 |
| 重复里程碑 | 多次退款、多次换货 | 单个 `refund_time` 装不下 |
| 重复支付 | 支付两次，原路退回一笔 | `pay_time` 记哪次？金额怎么冲抵 |
| 流程重开 | 关闭后重新激活工单 | 同一 id 出现第二段生命周期 |

**策略一：首次 + 末次 + 计数**。`refund_time_first` / `refund_time_last` / `refund_cnt`。能答「多久发生第一次退款」「退款几次」，不能答「第 2 次和第 1 次间隔多久」。

**策略二：可重复里程碑拆独立事务表（生产推荐）**。建 `dwd_fact_refund_txn(refund_id, order_id, refund_seq, refund_amount, refund_time, dt)`，一次退款一行；累积快照只留 `first/last/cnt` 冗余。

> [!important] 本节最重要的一条设计原则
> **累积快照负责「流程总览」，事务表负责「可重复事件明细」。**
> 判断标准：**这个里程碑在一个流程里可能出现几次？** 只可能一次 → 放累积快照；可能多次 → 拆事务表。
> 不要用 `refund1_time`、`refund2_time` 硬撑——字段会无限膨胀，每加一种事件就要改表结构。

**策略三：状态机版本化**。每次变更写一行 `dwd_fact_order_status_log(order_id, from_status, to_status, change_time, dt)`，回退次数 = `to_status` 序号小于 `from_status` 的记录数。

**回退后时间戳清不清空？** 两种口径二选一写进字典：**首次达成**保留首次 `receive_time`、另加 `return_time`（衡量履约效率）；**当前状态**清空 `receive_time`、置 `RETURNED`（衡量当前进度）。

> [!danger] 绝不要复用同一字段表达两种含义
> 见过最坑的设计：`receive_time` 在退货时被置空，导致「历史履约时长」每天重跑结果都不同。正确做法是 `first_receive_time` 和 `last_receive_time` 两个字段，谁也别覆盖谁。

**乱序与迟到事件**：merge 时不能用 `coalesce`，否则先到的脏值永久占位。

```sql
-- ✅ 取更早的非空值，结果与到达顺序无关
pay_time = case when t.pay_time is null then s.pay_time
                when s.pay_time is null then t.pay_time
                else least(t.pay_time, s.pay_time) end
```

> [!warning] Hive 的 `least` 遇 NULL 返回 NULL
> `least(null, '2026-10-01')` 在 Hive 里是 `NULL`，所以三段判空不能省。这个写法是**幂等重放**的关键：无论事件以什么顺序、重放几次，结果一致。

### 2.6 无事实事实表：记录「发生过」和「覆盖关系」

没有度量列，只有外键 + 时间，**行数本身就是度量**。两种形态：**事件型**（活动参与 `(user_id, activity_id, dt)`、页面曝光）和**覆盖型**（促销覆盖商品、库存覆盖 `(sku_id, warehouse_id, dt)`、课程覆盖班级），主键都是「全部外键 + dt」。

**为什么有用**：普通事实表只能答「发生了多少次」，答不了「为什么没发生」。有货未售、参与未下单、促销覆盖转化率——这些分母全部来自覆盖表。

```sql
select c.sku_id
from dws.dws_fact_stock_coverage c
left anti join (
    select distinct sku_id from dwd.dwd_fact_inventory_txn
    where dt = '2026-10-02' and direction = 'OUT'
) s on c.sku_id = s.sku_id
where c.dt = '2026-10-02';
```

> [!tip] 生产写法
> 覆盖表不要按「全量实体 × 全量天」存（100 万 SKU × 365 天 = 3.65 亿行/年）。三种压缩：① 只记「有覆盖关系」的（有货、在促销）；② 区间化（`start_date`/`end_date`，本质是拉链表）；③ 只对重点对象建表。要按天做漏斗就必须每天一行；只做区间归属，用区间表。

### 2.7 事实表的四种退化

**① 度量塞进维度表**：`dim_product.unit_cost`、`dim_user.balance`。维度表只有当前值，答不了「10-01 成本多少」，成本变化还会覆盖历史毛利。→ 成本进商品成本快照，余额进余额日快照。

**② 维度属性塞进事实表**：`fact_order` 放 `product_name`、`user_city`。行宽爆炸，且属性无法追溯——是下单时的城市还是当前的？→ 只放外键，确需时点快照的命名 `user_city_at_order`。

**③ 一张表混多粒度**：订单行 + 订单级优惠。3 行订单、30 元优惠，`sum` 后变 90。→ 拆表，或分摊到行并记录算法。

**④ 自然键当外键、没有维表**：无法做 SCD，用户改名后历史订单跟着变。→ 至少存「自然键 + 代理键」双键。

### 2.8 选型口诀

**有起止看进度 → 累积快照；看每次变化 → 事务表；看某时点状态 → 周期快照；只看有没有发生 → 无事实事实表。**

同一个业务过程可以有多张事实表：订单域典型 5 张（订单行事务、支付流水、退款流水、订单全流程累积快照、库存日快照），不是冗余，是**不同问题需要不同形状**（见 [[02-07 一致性维度与总线矩阵]]）。

## 三、动手实验

### 3.1 建表造数

```sql
create table dwd.dwd_fact_inventory_txn (
    txn_id string, sku_id string, warehouse_id string,
    direction string comment 'IN/OUT', qty int comment '恒正',
    txn_time timestamp, dt string
) partitioned by (dt string) stored as orc;

insert into dwd.dwd_fact_inventory_txn partition (dt = '2026-10-01') values
('T001','A','W1','OUT', 30, timestamp('2026-10-01 10:00:00')),
('T002','B','W1','OUT', 10, timestamp('2026-10-01 11:00:00')),
('T003','A','W1','IN',  50, timestamp('2026-10-01 15:00:00'));

insert into dwd.dwd_fact_inventory_txn partition (dt = '2026-10-02') values
('T004','A','W1','OUT', 20, timestamp('2026-10-02 09:30:00')),
('T005','C','W1','OUT',  5, timestamp('2026-10-02 10:00:00')),
('T006','B','W1','IN', 100, timestamp('2026-10-02 14:00:00'));

insert into dwd.dwd_fact_inventory_txn partition (dt = '2026-10-03') values
('T007','A','W1','OUT', 10, timestamp('2026-10-03 08:00:00')),
('T008','B','W1','OUT', 20, timestamp('2026-10-03 09:00:00')),
('T009','C','W1','IN',  30, timestamp('2026-10-03 16:00:00'));

create table dws.dws_fact_inventory_snapshot (
    sku_id string, warehouse_id string, stock_qty int, dt string
) partitioned by (dt string) stored as orc;

insert into dws.dws_fact_inventory_snapshot partition (dt = '2026-09-30') values
('A','W1',100),('B','W1',50),('C','W1',20);
```

手工核对：A 期初 100，三天净变化 `+20 -20 -10 = -10` → 期末 **90**；B `-10 +100 -20` → **120**；C `0 -5 +30` → **45**。

### 3.2 实验一：用事务表算库存，错在哪

```sql
-- A：三天事务数量直接相加，当「库存」
select sku_id, sum(qty) from dwd.dwd_fact_inventory_txn
where dt between '2026-10-01' and '2026-10-03' group by sku_id;

-- B：只加出库，当「销量」
select sku_id, sum(case when direction='OUT' then qty else 0 end)
from dwd.dwd_fact_inventory_txn
where dt between '2026-10-01' and '2026-10-03' group by sku_id;

-- C：带符号求和，得到「净变化量」
select sku_id, sum(case when direction='IN' then qty else -qty end)
from dwd.dwd_fact_inventory_txn
where dt between '2026-10-01' and '2026-10-03' group by sku_id;
```

| 口径 | A | B | C | 正确期末 |
| --- | --- | --- | --- | --- |
| 结果 | 110 / 130 / 35 | 60 / 30 / 5 | -10 / +70 / +25 | 90 / 120 / 45 |

**读结果**：① 口径 A 是**出入库总吞吐**（A 的 30+50+20+10=110），和真实库存 90 只差 20，**看起来「差不多对」，所以最危险**——它没有业务含义，换一天差多少完全随机；② 口径 B 是**销量**，业务上说「A 库存 60」，实际是「A 卖了 60」；③ 口径 C 是**净变化量**，`期初 100 + (-10) = 90` 才对，单独看 C 等于把期初丢了。

> [!danger] 更隐蔽的错：跨天累计忘了先按天聚合
> A 在 10-01 有 2 笔事务，`sum(qty) over (order by txn_time ...)` 会产生 2 行中间库存（70、120）。下游取到第一笔之后的 70 就错了。**必须先按 `(sku_id, dt)` 聚合，再跨天累计。**

**再深一层**：事务表根本回答不了「有货但没卖」。10-02 有出库的是 A、C；B 当天有货 140 件但没卖，事务表里**根本没有 B 的行**。

### 3.3 实验二：周期快照与半可加性

```sql
insert overwrite table dws.dws_fact_inventory_snapshot partition (dt = '2026-10-01')
select coalesce(y.sku_id, t.sku_id), coalesce(y.warehouse_id, t.warehouse_id),
       coalesce(y.stock_qty, 0) + coalesce(t.net_qty, 0), '2026-10-01'
from (select * from dws.dws_fact_inventory_snapshot where dt = '2026-09-30') y
full outer join (
    select sku_id, warehouse_id,
           sum(case when direction='IN' then qty else -qty end) as net_qty
    from dwd.dwd_fact_inventory_txn where dt = '2026-10-01'
    group by sku_id, warehouse_id
) t on y.sku_id = t.sku_id and y.warehouse_id = t.warehouse_id;
```

把 `dt` 依次换成 10-02、10-03（昨日快照同步换），得到 A：120 → 100 → 90，B：40 → 140 → 120，C：20 → 15 → 45。

```sql
-- ❌ 无意义：三天库存相加 → A=310
select sku_id, sum(stock_qty) from dws.dws_fact_inventory_snapshot
where dt between '2026-10-01' and '2026-10-03' group by sku_id;

-- ✅ 有意义：三天日均库存 → A=103.33
select sku_id, avg(stock_qty) from dws.dws_fact_inventory_snapshot
where dt between '2026-10-01' and '2026-10-03' group by sku_id;
```

**漏拍一天的后果**：删掉 10-02 分区，`count(*)` 从 3 变 2，日均被算成 `(120+90)/2=105`，正确 103.33。所以快照任务**无数据也必须写分区**，结束前校验当日 `count(*) > 0`，为 0 直接告警。

```sql
create table ods.ods_order_event (
```

**Spark 3.5 + Delta**（按 `create_dt` 分区）：

```sql
create table if not exists dws.dws_fact_order_flow_acc (
    order_id string, user_id bigint, create_time timestamp, pay_time timestamp,
    ship_time timestamp, receive_time timestamp, cancel_time timestamp,
    refund_time_first timestamp, refund_time_last timestamp, refund_cnt int,
    current_status string, pay_lag_sec bigint, total_lag_sec bigint,
    create_dt string, etl_time timestamp
) using delta partitioned by (create_dt);

-- source 是「该订单截至当前的全量事件聚合」，不是当日增量
merge into dws.dws_fact_order_flow_acc t
using (
    select order_id, max(user_id) as user_id,
        min(case when event_type='CREATE'  then event_time end) as create_time,
        min(case when event_type='PAY'     then event_time end) as pay_time,
        min(case when event_type='SHIP'    then event_time end) as ship_time,
        min(case when event_type='RECEIVE' then event_time end) as receive_time,
        min(case when event_type='CANCEL'  then event_time end) as cancel_time,
        min(case when event_type='REFUND'  then event_time end) as refund_time_first,
        max(case when event_type='REFUND'  then event_time end) as refund_time_last,
        sum(case when event_type='REFUND'  then 1 else 0 end)   as refund_cnt,
        max_by(event_type, event_time)                          as current_status
    from ods.ods_order_event where dt <= '2026-10-03'
    group by order_id
) s on t.order_id = s.order_id
when matched then update set
    t.pay_time     = case when t.pay_time is null then s.pay_time
                          when s.pay_time is null then t.pay_time
                          else least(t.pay_time, s.pay_time) end,
    t.ship_time    = case when t.ship_time is null then s.ship_time
                          when s.ship_time is null then t.ship_time
                          else least(t.ship_time, s.ship_time) end,
    t.receive_time = case when t.receive_time is null then s.receive_time
                          when s.receive_time is null then t.receive_time
                          else least(t.receive_time, s.receive_time) end,
    t.cancel_time = s.cancel_time,
    t.refund_time_first = s.refund_time_first,
    t.refund_time_last  = s.refund_time_last,
    t.refund_cnt        = s.refund_cnt,          -- 覆盖，不是累加
    t.current_status    = s.current_status,
    t.etl_time          = current_timestamp()
when not matched then insert (
    order_id, user_id, create_time, pay_time, ship_time, receive_time, cancel_time,
    refund_time_first, refund_time_last, refund_cnt, current_status,
    pay_lag_sec, total_lag_sec, create_dt, etl_time
) values (
    s.order_id, s.user_id, s.create_time, s.pay_time, s.ship_time, s.receive_time, s.cancel_time,
    s.refund_time_first, s.refund_time_last, s.refund_cnt, s.current_status,
    unix_timestamp(s.pay_time) - unix_timestamp(s.create_time),
    unix_timestamp(s.receive_time) - unix_timestamp(s.create_time),
    date_format(s.create_time, 'yyyy-MM-dd'), current_timestamp()
);
```

> [!danger] `refund_cnt` 绝不能写 `t.refund_cnt + s.refund_cnt`
> source 是当日增量时重跑一次就翻倍；即使 source 是全量聚合，`+=` 也会在重放时累加。**累积快照里所有计数类字段，都必须由 source 全量重算后直接覆盖。**

**Hive 3.x ACID 等价写法**：

```sql
set hive.support.concurrency = true;
set hive.txn.manager = org.apache.hadoop.hive.ql.lockmgr.DbTxnManager;
set hive.enforce.bucketing = true;
set hive.exec.dynamic.partition.mode = nonstrict;

create table dws.dws_fact_order_flow_acc_acid (
    order_id string, user_id bigint, create_time timestamp, pay_time timestamp,
    ship_time timestamp, receive_time timestamp, refund_cnt int,
    current_status string, create_dt string
) clustered by (order_id) into 16 buckets
stored as orc
tblproperties ('transactional' = 'true');

merge into dws.dws_fact_order_flow_acc_acid t
using ( /* 同上，按 order_id 聚合全量事件 */ ) s
on t.order_id = s.order_id
when matched then update set
    t.pay_time = s.pay_time, t.ship_time = s.ship_time,
    t.receive_time = s.receive_time, t.refund_cnt = s.refund_cnt,
    t.current_status = s.current_status
when not matched then insert values (
    s.order_id, s.user_id, s.create_time, s.pay_time, s.ship_time,
    s.receive_time, s.refund_cnt, s.current_status, s.create_dt
);
```

| 引擎 / 表格式 | MERGE | 前提 | 代价 |
| --- | --- | --- | --- |
| Hive 3.x ACID | ✅ | ORC + 分桶 + `transactional=true`；不能设 `transactional_properties=insert_only` | 小文件多、需 compaction、查询要合 delta |
| Hive 普通外部表 | ❌ | — | 只能 `insert overwrite` 全表重算 |
| Spark + Hive 表 | ❌ | Spark 不能写 Hive ACID 表 | 同上 |
| Spark + Delta / Iceberg / Hudi | ✅ | Delta 2.x+ / Iceberg 0.13+ / Hudi 0.10+ | 需 OPTIMIZE、rewrite manifests、compaction |

> [!warning] 参数默认值以自己集群为准
> 上面四个 `set` 是 Hive 3.x 的常见组合，不同发行版（CDP / HDP / 自建）默认值不同，`hive.txn.manager` 的类名也可能有差异——上线前用 `set -v` 实际确认，不要照抄。

**预期结果**（普通 Hive 表 `insert overwrite` 全表重算即可复现，逻辑同上）：

| order_id | pay_time | receive_time | refund_cnt | current_status | total_lag_sec |
| --- | --- | --- | --- | --- | --- |
| O1 | 10-01 10:05 | 10-03 14:00 | 0 | RECEIVE | 187200 |
| O2 | 10-01 20:10 | NULL | 0 | SHIP | NULL |
| O3 | NULL | NULL | 0 | CANCEL | NULL |
| O4 | 10-03 11:02 | NULL | 1 | REFUND | NULL |

**读结果**：O1 全流程 52 小时；O2 在途，`total_lag` 必须 NULL（填 0 会严重低估平均履约时长）；O3 未支付即取消，`pay_lag` 为 NULL，**不能把取消时间当支付时间**；O4 支付后退款，`refund_cnt=1` 但 `pay_time` 保留——「支付过又退了」和「从未支付」是两种事实。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 库存数和实际对不上，差值没有业务含义 | 用事务表 `sum(qty)` 当库存，得到的是总吞吐 | 对比 `sum(qty)` 与快照表，看差值是否随日期乱跳 | 库存类指标一律走周期快照 |
| 某天快照整段缺失 | 上游无数据，任务「空跑成功」没写分区 | `select dt, count(*) group by dt` 看连续性 | 输入改「昨日快照 + 今日增量」，强制写行 + 告警 |
| 累积快照历史订单少了一半 | 全表重算但 source 只取当日增量 | 对比每日 `count(distinct order_id)` 趋势 | source 改全量事件重放，或改 `merge` |
| 快照表出现重复行 | 用 `insert into` 追加，重跑即重复 | `count(*)` vs `count(distinct 主键)` | 改 `insert overwrite` 静态分区 |
| 库存/余额被 `sum` 成天文数字 | 半可加指标跨时间求和 | 看指标 SQL 是否 `sum` 跨多个 dt | 改期末值/日均值，指标字典写清 |
| 累积快照分区暴涨、同一订单跨多个分区 | 按更新日期分区，update 导致行移动 | `group by order_id having count(distinct 分区)>1` | 改按 `create_dt` 分区 |
| 重放后时间戳变晚或变空 | 用 `coalesce`，先到的脏值占位 | 重放同一批两次对比结果 | 改 `case + least` 取更早非空值 |
| 退款次数重跑后翻倍 | `refund_cnt = t.refund_cnt + s.refund_cnt` | 重跑同一天看计数 | source 全量重算后覆盖赋值 |
| 期初 ≠ 上期期末 | 同时存了期初和期末两套值 | `lag(期末)` 与期初对比 | 只存期末，期初由上期推导 |
| 事实表行宽几十 KB，扫描极慢 | 商品名、用户城市等属性塞进事实表 | `desc formatted` 看字段类型 | 属性移回维表，只留外键 |
| 订单级优惠把 GMV 算高 | 一张表混了行级和订单级两种粒度 | 对比 `sum(item_amount)` 与 `sum(pay_amount)` | 拆表，或分摊到行并记录算法 |
| 覆盖表一年几亿行 | 按「全量实体 × 全量天」存 | 估算 `实体数 × 天数` | 只存有覆盖关系的，或改区间表 |

## 五、面试追问

> [!question] 1. 三类事实表有什么区别？
> **一句话答法**：事务表一行一个事件、只追加、全可加；周期快照一行一个实体一个周期、记状态、半可加；累积快照一个流程一行、随流程 update、行数不随天数增长。
> **追问陷阱**：「累积快照和周期快照都 update 吗」——周期快照只追加新一期，不 update；累积快照才 update 同一行。

> [!question] 2. 库存表你会怎么设计？
> **一句话答法**：两层——`dwd_fact_inventory_txn` 记每次出入库（append-only、可对账），`dws_fact_inventory_snapshot` 记每日日终库存（`(dt, sku_id, warehouse_id)` 主键、半可加）。查询走快照，对账走事务。
> **追问陷阱**：「快照每天全量重算不慢吗」——用「昨日快照 + 今日净变化」增量推导，并处理「新 SKU 首现」「SKU 下架」两个边界。

> [!question] 3. 订单全流程各环节时长怎么算？
> **一句话答法**：建累积快照，一单一行，每个里程碑一个时间戳列 + 秒级 lag 列，用 `unix_timestamp(b)-unix_timestamp(a)` 算，未达成填 NULL。
> **追问陷阱**：「`avg(pay_lag_sec)` 的分母是什么」——要明确是「已支付订单」还是「全部订单」，后者含未支付会拉长平均值，必须分开出指标。

> [!question] 4. 累积快照能处理流程回退吗？
> **一句话答法**：能，但要三件套：`current_status` 记当前节点、状态流水表记每次变更（算回退次数）、可重复里程碑拆独立事务表。
> **追问陷阱**：「签收后又退货，`receive_time` 清不清空」——看口径：衡量履约效率就保留首次签收，衡量当前进度就清空，绝不能同一字段混用。

> [!question] 5. 无事实事实表用在哪？
> **一句话答法**：记「发生过」和「覆盖关系」，没有度量，行数就是度量。典型是活动参与、促销覆盖商品、库存覆盖，核心价值是提供**分母**。
> **追问陷阱**：「举个必须用它的场景」——「10-02 有货但没卖的商品」，事务表里没有这些行，只能覆盖表 `left anti join` 销售事务。

> [!question] 6. 为什么说周期快照是半可加的？
> **一句话答法**：库存可以跨仓库相加，但不能跨时间相加——「三天库存之和」没有业务含义，只能取期末值或平均。
> **追问陷阱**：「GMV 为什么可加」——GMV 是流量型（区间内累加），库存是存量型（某一时点状态）。

> [!question] 7. 一笔订单多个商品，粒度怎么定？
> **一句话答法**：拆到订单行（`order_id + item_seq`），商品、数量、金额都是行级的；订单级优惠和运费单独一张订单粒度事实表，或按算法分摊到行。
> **追问陷阱**：「订单级优惠直接放行表会怎样」——3 行订单、30 元优惠，`sum` 后变 90。必须拆表或分摊，并记录分摊算法。

> [!question] 8. 累积快照和事务表能互相替代吗？
> **一句话答法**：不能。事务表能重算出累积快照，但成本随数据量增长；累积快照查得快，却丢失可重复事件明细。生产上并存。
> **追问陷阱**：「既然能重算，为什么还存快照」——查询模式不同，且事务表可能缺事件，快照是校验过的可信状态。

> [!question] 9. 事实表要不要分区？按什么分区？
> **一句话答法**：事务表和周期快照按入库日期 `dt` 分区；累积快照按流程创建日期 `create_dt` 分区，绝不按更新日期。
> **追问陷阱**：「累积快照按创建日期分区，查『今天签收的订单』怎么办」——会扫全部分区，需在 `receive_time` 上分桶/索引，或另建状态流水表。

> [!question] 10. 迟到数据和撤销怎么处理？
> **一句话答法**：事务表用正负记账，撤销追加负值不改原记录，迟到数据补写对应入库日期分区；累积快照用全量事件重放 + 取更早非空值（`least`）。
> **追问陷阱**：「为什么不用 `coalesce` 更新时间戳」——先到的值会永久占位，脏数据一旦占位，重放结果不可复现。

## 六、自测题

> [!question] 1.（单选）「账户余额日快照」中的 `balance` 属于哪种可加性？
> A. 全可加　B. 半可加　C. 不可加　D. 取决于账户数量

> [!question] 2.（单选）累积快照事实表的主键应该是？
> A. `(order_id, dt)`　B. `order_id`　C. `(dt, user_id)`　D. `(order_id, status)`

> [!question] 3.（判断）累积快照事实表的行数会随天数增加而增长。

> [!question] 4.（场景设计）优惠券有「领取 → 使用 → 退款（可能多次）→ 过期」四个环节。请设计事实表方案：几张表、各自类型、主键、关键字段，并说明「平均用券时长」和「平均退款次数」分别从哪张表算。

> [!question] 5.（场景设计）某公司用 `dwd_fact_inventory_txn` 直接 `sum(qty)` 出库存报表，A 商品报表值 110、实际 90。请给出定位步骤、根因、修复方案，并说明要回答「10-02 有货但没卖的商品」还需补什么表。

> [!success]- 答案与解析（点击展开）
> **1. B**
> 余额可跨账户相加，不可跨时间相加。口诀：流量可加，存量半可加，比率不可加。
>
> **2. B**
> 累积快照是「一个流程一行」，主键是流程实例 id。加 `dt` 就变成周期快照，同一订单每天一行。
>
> **3. 错误**
> 行数 = 流程实例数，只随新流程产生增长。2020 年的订单今天仍是 1 行，只是字段被更新了。
>
> **4. 参考方案**
> 两张表：`dws_fact_coupon_flow_acc`（累积快照，主键 `coupon_id`，字段 `receive_time/use_time/expire_time/refund_time_first/refund_time_last/refund_cnt/current_status/use_lag_sec/receive_dt`）；`dwd_fact_coupon_refund_txn`（退款事务表，主键 `refund_id`，字段 `coupon_id/refund_seq/refund_time/refund_reason/dt`）。
> - 平均用券时长：累积快照 `avg(use_lag_sec) where use_time is not null`，分母是「已使用的券」。
> - 平均退款次数：按券算 `avg(refund_cnt)`（含零退款），或按退款单算 `count(*)/count(distinct coupon_id)`（不含零退款），必须说清用哪个。
> - 关键：退款是**可重复里程碑**，不能只在快照里放一个 `refund_time`，必须拆事务表 + 留 `first/last/cnt` 冗余。
>
> **5. 定位步骤**
> ① `select sku_id, sum(qty) ... group by sku_id` → A 得 110；② 快照表 `stock_qty` → 90；③ 110 = 30+50+20+10，是**出入库总吞吐**；`sum(signed)` 得 -10，加期初 100 才是 90。
>
> **根因**：把流量型事务当存量型状态用。`sum` 只能回答「吞吐了多少」，回答不了「现在有多少」。
>
> **修复**：建周期快照，每日「昨日快照 + 今日净变化」增量推导；库存报表全部改读快照；事务表只用于对账；加 DQ 校验 `快照(dt) - 快照(dt-1) = 事务净变化(dt)`。
>
> **补什么表**：`dws_fact_stock_coverage`（无事实事实表，`(dt, sku_id, warehouse_id)`，只记 `stock_qty > 0` 的组合），有了它才能 `left anti join` 销售事务。
