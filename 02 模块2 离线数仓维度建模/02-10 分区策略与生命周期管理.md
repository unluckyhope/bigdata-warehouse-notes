# 02-10 分区策略与生命周期管理

> [!abstract] 一句话结论
> 分区不是「建表选项」，而是一次**物理切分决策**，同时决定四件事：**能不能少读（裁剪）、能不能快跑（并行）、能不能删（生命周期）、能不能只重算一片（重跑隔离）**。
> 分区设计错了，这四件事一起失效——查询全表扫、任务跑不动、存储删不掉、出错只能全量重算。所以第一原则不是「按什么字段分」，而是「**这张表三年后怎么被查、怎么被删、怎么被重跑**」。

---

## 一、心智模型：分区是四个能力的开关

```
/warehouse/dwd.db/dwd_trade_order_detail_di/
├── dt=2026-09-30/part-00000.parquet
├── dt=2026-10-01/part-00000.parquet
└── dt=2026-10-02/part-00000.parquet
```

目录名就是分区值。理解这一点，四个能力都能推出来：

| 能力 | 依赖分区的什么性质 | 失效时的表现 |
| --- | --- | --- |
| **裁剪（少读）** | 过滤条件直接作用在分区列，列上无函数 | `where substr(dt,1,7)=...` → 扫全表 |
| **并行（快跑）** | 分区数 ≥ 并行度，单分区大小合理 | 1 个分区 200GB → 1 个 task 跑 3 小时 |
| **生命周期（能删）** | 分区是删除的最小单位，删分区=删目录 | 不分区 → 只能整表删 |
| **重跑（隔离）** | 重跑只覆盖目标分区 | 不分区 → 每次重跑都全表重算 |

> [!important] 一条判断法则
> **一个字段如果既不出现在 90% 查询的过滤条件里，也不承担「按时间删除」的职责，它就不该做分区键。**
> 分区的本质是「用目录名换扫描量」，目录名必须出现在 `where` 里才有价值。

记住一个真实事故：某团队用 `etl_date`（跑批日）分区，上游延迟导致 10-01 的订单在 10-03 才到，重跑后写进了 `etl_date=2026-10-03`。结果 10-01 的 GMV 少一天、10-03 多一天。**分区键选错不是性能问题，是数据正确性问题。**

## 二、核心知识点

### 2.1 分区粒度：日 / 小时 / 月怎么选

判断依据三条，按优先级：

1. **查询的过滤粒度**：90% 的查询按什么时间过滤？按天查就日分区，按小时查才考虑小时分区。
2. **单分区数据量**：压缩后落在 **128MB ~ 1GB**。小于 128MB 切太细，大于 1GB 单 task 处理不动。
3. **分区总数**：单表 **10 万以内**，单日新增 **几百以内**。

| 单日数据量（压缩后） | 建议粒度 | 单分区目标 | 典型表 |
| --- | --- | --- | --- |
| < 1GB | 月分区（或不分区） | 128MB~1GB | 小维表快照、配置表 |
| 1GB ~ 20GB | **日分区** | 128MB~1GB | 订单明细、支付流水 |
| 20GB ~ 100GB | 日分区 + 控文件数 | 256MB~1GB | 埋点、曝光 |
| > 100GB 或需按小时查 | **dt + hour 两级** | 128MB~512MB | 大促日志、实时落地 |

### 2.2 分区键：业务日期 dt vs 处理日期 etl_date

| | 业务日期（`dt`） | 处理日期（`etl_date`） |
| --- | --- | --- |
| 含义 | 数据**所属**的日期 | 数据**被写入**的日期 |
| 重跑 | ✅ 重跑 10-01 仍写进 10-01 | ❌ 重跑写进今天，数据错位 |
| 回补 | ✅ 历史数据落到对应分区 | ❌ 历史数据全堆在今天 |
| 适用 | **绝大多数事实表、维表快照** | 日志采集、一次性导入、审计留痕 |

```sql
-- ✅ 业务日期：10-05 重跑 10-01，结果仍落在 dt=2026-10-01
insert overwrite table dwd.dwd_trade_order_detail_di partition (dt = '2026-10-01')
select ... from ods.ods_order_item where dt = '2026-10-01';

-- ❌ 处理日期：10-05 重跑 10-01，数据进了 dt=2026-10-05
-- 10-01 仍然是错的；10-05 多了一份 10-01 的数据；若 10-05 本身也有数据，两批混在一个分区里再也分不开
insert overwrite table dwd.dwd_trade_order_detail_di partition (dt = '2026-10-05')
select ... from ods.ods_order_item where dt = '2026-10-01';
```

**只有两种情况用处理日期**：① 源端确实没有业务时间（第三方只给拉取时间）；② 审计/留痕表，要求「这批数据哪天灌进来」作为不可变事实。

### 2.3 多级分区：什么时候值得，什么时候是灾难

| 组合 | 适用 | 代价 |
| --- | --- | --- |
| `dt` + `hour` | 日志、曝光、实时落地；查询常精确到小时 | 分区数 ×24，极易小文件 |
| `dt` + `region` | 单日 >100GB 且查询总带地区 | 分区数 × 地区数，跨区聚合变慢 |

**分区数爆炸的算术，必须会算**：

```
dt(365) × hour(24) × province(34) × channel(10) = 2,978,400 个分区/年
```

后果三重且连锁：① **HMS 压力**——每个分区对应 `PARTITIONS` + `SDS` 若干行，300 万分区约几个 GB 元数据（经验值），`get_partitions` 从毫秒变秒级，**每次编译 SQL 都要等**；② **`show partitions` 不可用**——输出几十万行客户端卡死，`msck repair` 跑到超时；③ **NameNode 小文件压力**——300 万个目录，NN 堆内存吃紧（经验值：每 100 万对象约 300~400MB 堆），写入时还起大量 reduce。

> [!danger] 判断「多级分区是否值得」的唯一标准
> **加了这一级，能不能让典型查询少读 50% 以上的数据？** 不能就不要加。
> `province` 只有 34 个值，放在表内做普通列 + parquet 谓词下推，效果往往比做分区更好——不会产生 34 倍小文件，也不会让元数据膨胀 34 倍。**分区是给时间用的，不是给维度用的。**

### 2.4 分区字段的类型与格式

事实标准只有一个：

```sql
partitioned by (dt string comment '业务日期，格式 yyyy-MM-dd')
```

| 写法 | 评价 | 问题 |
| --- | --- | --- |
| `string 'yyyy-MM-dd'` | ✅ 事实标准 | 字典序=时间序，`date_sub` 可直接算，跨引擎一致 |
| `int 20261001` | ⚠️ 不推荐 | 可读性差，与 `date` 互转麻烦，跨表 join 对不上 |
| `string '2026-10-1'`（不补零） | ❌ 禁止 | 字典序错乱：`'2026-10-2' > '2026-10-19'`，区间查询漏数 |
| 同表混用两种格式 | ❌ 禁止 | 任何区间查询都漏数，`show partitions` 一眼看不出 |

写进建模规范的三条（评审逐条查）：

- 分区字段名 `dt`，`string`，`yyyy-MM-dd`，**必须补零**；小时用 `hour` + `HH`；月用 `month` + `yyyy-MM`。
- 分区字段**不要**再作为普通列重复定义：Hive 建表直接报错，Spark 会静默取分区值。
- 禁止在 SQL 里用 `current_date()` / `now()` 生成分区值，日期必须由调度传参 `${biz_date}`。

### 2.5 生命周期：热 / 温 / 冷

先算账（用 02-12 的订单域）：订单明细 600 万行/天 × 365 × 3 年 ≈ 65.7 亿行，parquet + snappy 约 150~250 字节/行 → 约 1~1.6 TB。

| 层 | 时间范围 | 存储 | 格式 | 查询延迟 | 成本 |
| --- | --- | --- | --- | --- | --- |
| **热** | 近 30 天 | SSD / 高性能 HDD | parquet + snappy | 秒级 | 高 |
| **温** | 30~180 天 | 普通 HDD | parquet + snappy | 十秒级 | 中 |
| **冷** | > 180 天 | 对象存储 + 按年合并 | parquet + **zstd** | 分钟级 | 低（约热存储 1/5~1/10，随厂商定价） |

**保留策略的三个输入，缺一不可**：① **合规**——订单/支付/退款通常要求 3 年可查，具体年限以法务和审计口径为准，不要凭感觉写；② **业务**——同比至少 13 个月，复购/生命周期分析可能要 3 年，埋点 6 个月足够；③ **成本**——先把「全留 3 年要多少钱」算出来，再决定哪层降级。

落到层上：ODS 原始 90 天热 + 3 年冷归档（对账依据不能真删）；DWD 事务事实 3 年（热 30 / 温 150 / 冷 2.5 年）；DWS 日汇总 3 年（约为 DWD 的 1/50）；ADS 3 年或永久（体量极小）；ODS 埋点 180 天。

「能重算」不等于「可以不存」：重算 3 年数据需要 3 年的 ODS（你也删了）、当时的逻辑（已改 8 版）、几十小时算力、以及一次不能出错的全量覆盖。**归档成本远低于重算成本。**

### 2.6 归档怎么落地

**手段一：压缩重写（最常用）**

```sql
-- 按月重新分区 + zstd，体积通常降到 snappy 的 50%~70%
set parquet.compression = ZSTD;

insert overwrite table dwd.dwd_trade_order_detail_di_ar partition (month)
select order_id, order_item_id, user_id, sku_id, pay_amount, order_time,
       substr(dt, 1, 7) as month
from dwd.dwd_trade_order_detail_di
where dt >= '2025-01-01' and dt <= '2025-12-31';
```

**手段二：跨存储拷贝（冷归档）**

```bash
# 按分区拷贝，失败可续传；-m 并发，-bandwidth 单位 MB/s
hadoop distcp -m 64 -bandwidth 200 \
  hdfs://ns1/warehouse/dwd.db/dwd_trade_order_detail_di/dt=2025-01-01 \
  oss://archive-bucket/dwd/dwd_trade_order_detail_di/dt=2025-01-01
```

**手段三：按年/月合并分区**——归档表 `partitioned by (month string)`，一年 12 个分区替代 365 个，元数据和存储双降。

归档后必须做三步校验：源表与归档表的 `count(*)`、`sum(pay_amount)` 完全一致，再抽样比对 100 行明细，一致后才允许删源分区。

> [!danger] 归档最常见的错误
> **先删后拷**，或**拷完不校验就删**。distcp 中途失败（网络、权限、版本不一致）数据就永久丢了。
> 正确顺序永远是：**拷贝 → 校验行数+金额 → 抽样比对 → 标记只读 → 观察一周 → 删源分区**。

### 2.7 重跑成本：分区覆盖 vs 全表重算

| 方式 | 影响范围 | 耗时（600 万行/天） | 风险 |
| --- | --- | --- | --- |
| 分区覆盖 `overwrite ... partition(dt='...')` | 1 个分区 | 分钟级 | 低，失败只影响当天 |
| 区间覆盖 `partition(dt)` 动态写多天 | N 个分区 | 与 N 成正比 | 中，Spark STATIC 模式会覆盖全表 |
| 全表重算（不带 partition） | 全部历史 | 数十小时 | 极高，期间数据不可用 |

**为什么必须保证「重跑某天只影响那天」**：① 幂等——跑 1 次和跑 10 次结果一致，调度才敢自动重试；② 隔离——重跑 10-01 不碰 10-02~10-31，否则一次小修变成一次大事故；③ 可并发——补 30 天可以 30 个分区并行，3 小时的事变 10 分钟。

```sql
-- ✅ 幂等
insert overwrite table dwd.dwd_trade_order_detail_di partition (dt = '${biz_date}')
select ... where dt = '${biz_date}';

-- ❌ 非幂等：重跑一次翻倍，两次翻三倍，而且没有主键帮你发现
insert into table dwd.dwd_trade_order_detail_di partition (dt = '${biz_date}')
select ... where dt = '${biz_date}';
```

> [!warning] Spark 的隐藏开关（上线前必须验证）
> `insert overwrite table t partition (dt) select ..., dt from ...` 在默认 `spark.sql.sources.partitionOverwriteMode = STATIC` 下会**覆盖整张表的所有分区**。必须显式 `set spark.sql.sources.partitionOverwriteMode = dynamic;`
> 默认值 STATIC（Spark 3.5 默认行为，具体小版本是否变更**待验证**）。上线前做一次「只重跑 1 天，检查其他日期行数不变」的验证。

### 2.8 分区 vs 分桶 vs 排序：各解决什么问题

| 手段 | 一句话 | 解决什么 | 生效条件 |
| --- | --- | --- | --- |
| **分区** | 按目录切 | 少读、能删、可重跑 | 过滤条件直接作用在分区列 |
| **分桶** | 按 hash 切文件 | join 免 shuffle、稳定采样 | 两表同键、同桶数 |
| **distribute by** | 按 key 分发到 reducer | 控单文件大小、避免小文件 | 写入时一次 shuffle |
| **sort by** | 单 reducer 内排序 | 文件内有序，配合分桶做 merge join | 写入时生效 |
| **Z-order** | 多维空间填充曲线 | 多列组合过滤的局部性 | **仅湖表支持**（Delta/Iceberg/Hudi），Hive 原生不支持 |

组合用法：`dt` 分区负责「少读 + 能删」，写入时 `distribute by shop_id` 负责「控文件大小」，湖表再用 `Z-order(sku_id, user_id)` 加速多维圈选——三者不互斥，但**先把分区做对，再谈另外两个**。

## 三、动手实验

### 3.1 建两级分区表并造数

```sql
drop table if exists tmp.dwd_ord_di;
create table tmp.dwd_ord_di (
  order_id   bigint        comment '订单ID',
  sku_id     bigint        comment '商品ID',
  pay_amount decimal(18,2) comment '实付金额'
)
comment '订单明细（实验用）'
partitioned by (dt string comment '业务日期 yyyy-MM-dd', hour string comment '小时 HH')
stored as parquet
tblproperties ('parquet.compression' = 'SNAPPY');

insert overwrite table tmp.dwd_ord_di partition (dt = '2026-10-01', hour = '00')
select 1, 1001, 99.00 union all select 2, 1002, 199.00;

insert overwrite table tmp.dwd_ord_di partition (dt = '2026-10-02', hour = '00')
select 3, 1003, 299.00 union all select 4, 1004, 399.00;

insert overwrite table tmp.dwd_ord_di partition (dt = '2026-10-03', hour = '00')
select 5, 1005, 499.00;
```

### 3.2 实验一：分区裁剪生效 vs 失效

```sql
-- ✅ 生效：等值 / 区间 / IN
explain select sum(pay_amount) from tmp.dwd_ord_di where dt = '2026-10-02';
explain select sum(pay_amount) from tmp.dwd_ord_di
where dt >= '2026-10-01' and dt <= '2026-10-02';
explain select sum(pay_amount) from tmp.dwd_ord_di
where dt in ('2026-10-01', '2026-10-02');

-- ❌ 失效：套函数 / 隐式转换 / 参与运算
explain select sum(pay_amount) from tmp.dwd_ord_di where substr(dt, 1, 10) = '2026-10-02';
explain select sum(pay_amount) from tmp.dwd_ord_di where cast(dt as date) = '2026-10-02';
explain select sum(pay_amount) from tmp.dwd_ord_di where concat(dt, '') = '2026-10-02';
```

| 引擎 | 生效 | 失效 |
| --- | --- | --- |
| Hive 3.x | `TableScan` 里 `partitions=dt=2026-10-02/hour=00` | 列出所有分区，或 `numPartitions=-1` |
| Spark 3.5 | `PartitionFilters: [isnotnull(dt#12), (dt#12 = 2026-10-02)]` | `PartitionFilters: []` |

### 3.3 实验二：动态分区写入

```sql
-- Hive 3.x：三个参数缺一不可
set hive.exec.dynamic.partition = true;                -- 默认 true
set hive.exec.dynamic.partition.mode = nonstrict;      -- 默认 strict，必须改
set hive.exec.max.dynamic.partitions = 2000;           -- 默认 1000
set hive.exec.max.dynamic.partitions.pernode = 500;    -- 默认 100
set hive.exec.max.created.files = 100000;              -- 默认 100000

-- 分区列必须放 SELECT 最后一列，顺序与 partition() 一致
insert overwrite table tmp.dwd_ord_di partition (dt, hour)
select order_id, sku_id, pay_amount, dt, hour
from tmp.dwd_ord_di_src
where dt >= '2026-10-01' and dt <= '2026-10-03';
```

```sql
-- Spark 3.5：不设这个参数会覆盖全表
set spark.sql.sources.partitionOverwriteMode = dynamic;
insert overwrite table tmp.dwd_ord_di partition (dt, hour)
select order_id, sku_id, pay_amount, dt, hour
from tmp.dwd_ord_di_src
where dt >= '2026-10-01' and dt <= '2026-10-03';
```

### 3.4 实验三：按分区删除与归档

```sql
-- ① 删单分区（元数据 + 数据一起删，最快）
alter table tmp.dwd_ord_di drop if exists partition (dt = '2026-10-03', hour = '00');

-- ② 删区间分区（Hive 支持比较运算符）
alter table tmp.dwd_ord_di drop if exists partition (dt < '2026-10-01');

show partitions tmp.dwd_ord_di;

-- ③ 归档：月分区 + zstd（校验行数金额一致后再删源分区，见 2.6）
set parquet.compression = ZSTD;
insert overwrite table tmp.dwd_ord_di_ar partition (month)
select order_id, sku_id, pay_amount, substr(dt, 1, 7) as month
from tmp.dwd_ord_di where dt < '2026-10-01';
```

> [!warning] Spark 的 `DROP PARTITION` 支持有限
> Spark 3.5 主要支持等值谓词，区间删除建议用 Hive，或删目录后 `MSCK REPAIR TABLE` 同步元数据（具体范围随版本变化，**待验证**）。直接删目录会导致查询报 `FileNotFoundException`。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 月度报表少一天 | 分区键用处理日期，补数写错分区 | 对比 `dt` 与 `min/max(order_time)` | 改业务日期分区，历史数据重分布 |
| 查询扫全表跑几小时 | 分区列套了 `substr`/`cast`/`concat` | `explain` 看 `PartitionFilters` 是否为空 | 改写为分区列直接比较 |
| `show partitions` 卡死 | 分区数上百万 | 查 HMS `PARTITIONS` 表计数 | 减少分区层级，合并小分区 |
| SQL 编译要几十秒 | 元数据分区过多 | 看编译阶段耗时占比 | 同上；HMS 加缓存 |
| 重跑后数据翻倍 | 用了 `insert into` | 对比重跑前后 `count(*)` | 改 `insert overwrite partition` |
| 重跑一天其他天也变了 | Spark `partitionOverwriteMode=STATIC` | 对比其他日期行数 | 设 `dynamic` 并验证 |
| 单分区 200GB 跑不动 | 分区粒度太粗 | `hdfs dfs -du -s -h` | 加二级分区或改小时分区 |
| 单分区几千个小文件 | 动态分区 + 并行度过高 | `hdfs dfs -count` 看 `FILE_COUNT` | `distribute by` 收敛，或事后合并 |
| 归档后数据丢了 | 先删后拷 / 不校验 | 对比归档前后行数金额 | 建立「拷贝-校验-抽样-观察-删除」 |
| 跨年查询漏数 | 分区格式混用 `20261001` / `2026-10-01` | `show partitions` 看格式 | 统一 `yyyy-MM-dd` + 写入校验 |
| 分区日期错一天 | SQL 里用 `current_date()`，时区不一致 | 对比服务器与业务时区 | 调度传参 `${biz_date}` |

## 五、面试追问

> [!question] 1. 一张事实表的分区你怎么设计？
> **一句话答法**：看查询过滤粒度、单分区大小（目标 128MB~1GB）、分区总数（<10 万），分区键用业务日期 `dt string yyyy-MM-dd`；多级分区必须能证明「让典型查询少读一半」。
> **追问陷阱**：「按天和按月都要查，做两级时间分区吗」——不做。日分区 + 月粒度 DWS 汇总表更好，两级分区等于同一份数据存两遍。

> [!question] 2. 为什么不用处理日期（跑批日期）分区？
> **一句话答法**：重跑和回补都会写错分区——重跑 10-01 的数据落到今天，历史数据全堆在一天里，分区语义失效。
> **追问陷阱**：「源端没有业务时间怎么办」——用落库时间分区，同时冗余 `event_time` 字段，等上游补齐后按业务时间重分布。

> [!question] 3. 分区太多会有什么问题？
> **一句话答法**：HMS 元数据膨胀导致编译变慢、`show partitions`/`msck repair` 不可用、NameNode 小文件压力、写入时 reduce 爆炸。
> **追问陷阱**：「怎么量化」——`dt×hour×province×channel` 一年 300 万分区，元数据几个 GB，`get_partitions` 从毫秒变秒级。

> [!question] 4. 历史数据怎么归档？
> **一句话答法**：zstd 压缩重写 → 按月/年合并分区 → distcp 到对象存储 → 校验行数金额 → 抽样比对 → 观察一周 → 删源分区。
> **追问陷阱**：「归档后还能查吗」——走外部表或按需拉回，SLA 从秒级降到分钟级，必须提前和业务约定。

> [!question] 5. 哪些写法会让分区裁剪失效？
> **一句话答法**：分区列套函数、隐式类型转换、参与运算、`like '%xxx'` 前置通配、边界来自子查询。
> **追问陷阱**：「`where dt >= date_sub(current_date(),30)` 会失效吗」——不会，常量折叠后仍是列与常量比较；右边换成子查询才会退化。

> [!question] 6. 动态分区要注意什么？
> **一句话答法**：`mode=nonstrict` 必须开；分区列放 SELECT 最后；控制 `max.dynamic.partitions`；Spark 还要设 `partitionOverwriteMode=dynamic`，否则覆盖全表。
> **追问陷阱**：「动态分区写入很慢怎么优化」——先 `distribute by dt` 收敛 reduce；或改成调度层循环、每天一次静态写入，失败可重试。

> [!question] 7. 分区和分桶的区别？什么时候真的需要分桶？
> **一句话答法**：分区按目录切，解决少读、能删、可重跑；分桶按 hash 切文件，解决 join 免 shuffle 和稳定采样。分区必需，分桶可选。
> **追问陷阱**：「分桶什么场景真有用」——两张大表同键同桶数 join（bucket map join），或 `tablesample` 稳定抽样；其他场景基本负收益。

> [!question] 8. 要重跑一个月的数据，怎么跑？
> **一句话答法**：按天拆 30 个独立任务并行，各自 `insert overwrite` 自己的分区；按 ODS→DWD→DWS→ADS 顺序推进；用调度补数，不手写 30 条 SQL。
> **追问陷阱**：「并行度开多大」——看队列资源和单分区耗时，通常 5~10 并发；一个任务动态写 30 个分区比 30 个任务各写 1 个慢得多。

> [!question] 9. 小文件怎么产生、怎么解决？
> **一句话答法**：动态分区、并行度过高、频繁小批写入；解决靠 `distribute by` 收敛、`maxRecordsPerFile` 控制、定期合并。
> **追问陷阱**：「小文件对查询的影响是什么」——NN 内存 + 每个文件都要打开、读 footer、建 task，启动开销可能比读数据还大。

> [!question] 10. 冷热分层怎么落地，收益怎么算？
> **一句话答法**：按访问频率分层，冷数据 zstd + 对象存储，收益 = 数据量 ×（热单价 - 冷单价），代价是延迟从秒级变分钟级。
> **追问陷阱**：「怎么知道哪些是冷数据」——看查询日志的分区级访问次数，按「90 天内被访问过的分区」定义，比按时间拍脑袋准。

## 六、自测题

> [!question] 1.（单选）下列分区字段定义中最不容易出问题的是？
> A. `dt int`，值 `20261001`
> B. `dt string`，值 `2026-10-1`
> C. `dt string`，值 `2026-10-01`
> D. `dt string`，值 `20261001`

> [!question] 2.（单选）一个分区压缩后的目标大小通常是？
> A. 10MB~50MB　B. 128MB~1GB　C. 5GB~10GB　D. 越大越好

> [!question] 3.（判断）分区数越多查询一定越快，因为能跳过更多数据。

> [!question] 4.（场景设计）埋点日志日增 300GB（压缩后），80% 查询按天、20% 按小时且只查最近 7 天。设计分区方案、单分区估算、生命周期，并说明为什么不按 `province` 再做一级。

> [!question] 5.（场景设计）你接手一张表，发现 `dt` 实际是跑批日期（`max(order_time)` 比 `dt` 早 1~2 天），已积累 2 年数据。给出无损迁移到业务日期分区的步骤、SQL 与校验方法。

> [!success]- 答案与解析（点击展开）
> **1. C**
> `string` + `yyyy-MM-dd` 补零：字典序等于时间序，`date_sub`/`date_add` 直接用，跨引擎一致。A 与 `date` 互转麻烦；B 不补零会字典序错乱（`'2026-10-2' > '2026-10-19'`）；D 与绝大多数表格式不一致，join/union 必踩。
>
> **2. B**
> 128MB~1GB 是 HDFS block 与单 task 处理能力的平衡点。太小说明切太细（元数据和小文件成本超过收益），太大说明单 task 时间长、重试代价大、并发不够。
>
> **3. 错误**
> 收益是「裁剪更多」，成本是「元数据更多、编译更慢、小文件更多、写入 task 更多」。当分区数超出查询能利用的范围（如按 `user_id` 分区），收益为 0 而成本线性上升。
>
> **4. 参考方案**
> **分区**：`dt` + `hour` 两级。日分区覆盖 80% 的按天查询；小时分区覆盖 20% 的按小时查询。
> **单分区估算**：300GB / 24 ≈ 12.5GB/小时，偏大，所以每小时分区用 `distribute by` 控制成 20~50 个 256MB 文件；不做小时分区的话 300GB 的日分区单 task 也跑不动，所以小时分区在这里是**必要**的。
> **生命周期**：近 7 天保留 `dt+hour`（热）；8~180 天合并成 `dt` 一级（减少 24 倍元数据）；180 天以上按月合并 + zstd 转对象存储；超过 1 年直接删。
> **为什么不按 province 分区**：34 × 365 × 24 ≈ 30 万分区/年，元数据压垮 HMS；埋点查询 90% 不带省份过滤，收益接近 0；省份作为普通列 + 谓词下推能拿到大部分收益且不产生小文件。真有「按省看板」需求，应建按省的 DWS 汇总表。
>
> **5. 迁移步骤**
> ① 建同结构新表，`partitioned by (dt string)`；② 按业务时间重分布写入，**按月分批**，每批校验后再跑下一批：
> ```sql
> set hive.exec.dynamic.partition.mode = nonstrict;
> insert overwrite table dwd.dwd_trade_order_detail_di_new partition (dt)
> select order_id, order_item_id, user_id, sku_id, shop_id, pay_amount, order_time,
>        date_format(order_time, 'yyyy-MM-dd') as dt
> from dwd.dwd_trade_order_detail_di
> where dt between '2024-10-01' and '2024-10-31';
> ```
> ③ 校验：两表 `count(*)`、`sum(pay_amount)` 一致；再按 `date_format(order_time,'yyyy-MM-dd')` 聚合后 `full join` 比对逐日行数，差异应为 0 行。
> **④ 切换**：新表并行跑 3~7 天逐日比对 → 下游先切视图 → 再切物理表 → 旧表保留 30 天只读 → 确认无回滚再删。**切换期间禁止双写**，双写必然产生两份不一致，最后没人知道信哪份。
> **⑤ 坑**：`order_time` 为空会落到 `dt=NULL` 分区，必须 `coalesce(order_time, create_time)`；切换前查血缘通知所有下游。
