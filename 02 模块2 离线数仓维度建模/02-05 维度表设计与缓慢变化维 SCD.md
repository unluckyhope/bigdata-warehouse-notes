# 02-05 维度表设计与缓慢变化维 SCD

> [!abstract] 一句话结论
> 维度表是**描述性上下文**（谁、什么、哪里、怎么来的），事实表是**度量**；维度表的核心不是「存属性」，而是**「属性变了，历史事实该看旧值还是新值」**——这就是 SCD 要回答的唯一问题。
> 答「看新值」→ SCD1 覆盖；答「看当时的值」→ SCD2 加版本行；答「只看上一版」→ SCD3 加 `prev_` 列。
> 选错的代价是**历史报表被静默改写**：用户改了地址，去年的订单全跑到新城市去了。

---

## 一、心智模型：维度是上下文，SCD 是时间语义

```
事实表：发生了什么（订单、支付、退款），一行一个事件，可度量
维度表：在哪里发生（谁买的、什么商品、哪个门店、哪一天），一行一个实体
```

维度表的价值在于**约束与分组**：没有 `dim_date`，「按月」只能靠字符串截取；没有 `dim_sku`，「按品类」只能靠商品名猜。维度表也是一致性的载体——所有事实表用同一张 `dim_date`，口径才对齐（见 [02-07 一致性维度与总线矩阵](02-07%20%E4%B8%80%E8%87%B4%E6%80%A7%E7%BB%B4%E5%BA%A6%E4%B8%8E%E6%80%BB%E7%BA%BF%E7%9F%A9%E9%98%B5.md)）。

**SCD（Slowly Changing Dimension）** 处理「维度属性随时间变化」：

| 问题 | 业务口径 | 实现 |
| --- | --- | --- |
| 用户改地址，历史订单关联旧地址还是新地址？ | 看「当时在哪下单」 | SCD2 |
| 商品调价，去年的毛利按哪个成本算？ | 按下单时成本 | SCD2 或成本快照 |
| 会员等级升级，历史订单算哪个等级？ | 按下单时等级 | SCD2 |
| 供应商改名（错别字修正），历史要不要改？ | 要，属于纠错 | SCD1 |

> [!important] SCD 的选择不是技术问题，是指标口径问题
> 同一张 `dim_user`，`city` 用 SCD2（历史地址），`member_level` 用 SCD1（当前等级），完全合法——**不同属性的时间语义可以不同**。
> 所以不要问「这张维表用 SCD 几」，要问「这个属性回答问题时，要 as-was 还是 as-is」。

## 二、核心知识点

### 2.1 键体系：自然键、代理键、持久键

| 键 | 定义 | 例子 | 特点 |
| --- | --- | --- | --- |
| 自然键 / 业务主键 | 源系统给的业务标识 | `user_id`、`order_no`、`sku_code` | 可读、跨系统不一致、可能复用 |
| 代理键 surrogate key | 数仓生成的整型 | `user_sk = 10001` | 无业务含义、稳定、join 快 |
| 持久键 durable key | 跨版本稳定的代理键 | `user_dk = hash(user_id)` | 一个实体一个值，不随版本变 |

SCD2 里一个用户有多个版本，所以需要**两种代理键**：`user_dk`（持久键，一个用户一个）用于把同一实体的所有版本归到一起；`user_sk`（版本代理键，一个版本一个）用于事实表精确关联某个版本。

**代理键的四个作用**：

1. **隔离源系统变更**：源主键从 `int` 改 `string`、或换了业务系统，事实表不用动。
2. **支持 SCD2 多版本**：同一 `user_id` 的 4 个版本必须有 4 个不同的键，自然键做不到。
3. **提升 join 性能**：`bigint` 比 `varchar(64)` 省内存、hash 更快，小维表可广播。
4. **统一跨源编码**：A 系统 `user_id=1001`、B 系统 `uid='U1001'`，在数仓统一成 `user_sk`。

> [!warning] 事实表只存代理键是不够的
> 只存 `user_sk`，一旦维表重跑导致代理键变化，历史事实就全错位。生产上事实表存**「自然键 + 代理键」双键**：代理键用于 join，自然键用于回溯和修复。

### 2.2 代理键怎么生成：四种做法与各自的坑

**① `row_number()`**

```sql
select row_number() over (order by user_id, start_time) as user_sk, ...
```

坑：**重跑会变**。插入一个新用户，后面所有行序号整体后移；SCD2 新增一个历史版本，该用户之后的版本键全变。事实表里的旧 `user_sk` 立刻指向错误的人。

**② `max(sk) + 1`**

```sql
select coalesce(max(user_sk), 0) + row_number() over (order by user_id) as user_sk ...
```

坑：**并发不安全**（两个任务读到同一个 max）、**全表扫描**、**删行后键被复用**。Hive 没有自增序列，`max+1` 只是把数据库的坑搬到了数仓。

**③ hash（推荐）**

```sql
-- 版本键：自然键 + 版本起始时间
cast(conv(substr(md5(concat(user_id, '|', start_time)), 1, 15), 16, 10) as bigint) as user_sk
-- 持久键：只用自然键
cast(conv(substr(md5(cast(user_id as string)), 1, 15), 16, 10) as bigint) as user_dk
```

坑：**会碰撞**。32 位 hash（`crc32`）在约 7.7 万行时碰撞概率就到 50%（生日悖论），绝对不能用。取 MD5 前 15 个十六进制字符是 60 位，百万级可忽略，十亿级要评估。优点是**可重算、与顺序无关、中间插版本不影响其他键**。

**④ `uuid()`**

坑：128 位字符串、不可读、**每次执行都变**，重跑不幂等，只能用于一次性临时表。

> [!tip] 生产推荐
> 小维表（百万级以下）：建**持久映射表** `dim_sk_map(natural_key, version_start, sk, created_at)`，新版本先查映射、查不到再分配，键一旦分配永不改变。
> 大维表：用 **60 位 hash** 做版本键、`hash(自然键)` 做持久键，不维护映射表，靠「可重算」保证幂等。
> 无论哪种，**事实表都保留自然键**，作为代理键出错时的兜底。

### 2.3 SCD1 / SCD2 / SCD3 / SCD4 / SCD6

| 类型 | 做法 | 历史 | 适用 | 电商例子 |
| --- | --- | --- | --- | --- |
| SCD1 | 直接覆盖 | 不保留 | 纠错、无分析价值的属性 | 昵称错别字、商品标题改字 |
| SCD2 | 加版本行（start/end/is_current/version） | 全保留 | 需要 as-was 分析 | 用户地址、商品价格、会员等级 |
| SCD3 | 加 `prev_xxx` 列 | 只留上一版 | 只关心「变化前后」 | 调价前后、等级升降 |
| SCD4 | 拆迷你维度 | 取决于子维 | 属性变化频率差异大 | 用户基础信息（慢）+ 行为标签（快） |
| SCD6 | 1+2+3 混合 | 全保留 + 当前值冗余 | 既要 as-was 又要 as-is 且要快 | 商品维：版本行 + 当前价 + 上一版价 |

**SCD1**：

```sql
insert overwrite table dim.dim_user_scd1
select user_id, user_name, city, update_time
from (
    select *, row_number() over (partition by user_id order by update_time desc) as rn
    from ods.ods_user_change where dt <= '2026-10-03'
) t where rn = 1;
```

**SCD2 表结构**：

```sql
create table dim.dim_user_scd2 (
    user_sk    bigint  comment '版本代理键',
    user_dk    bigint  comment '持久键，跨版本不变',
    user_id    bigint  comment '自然键',
    user_name  string,
    city       string,
    start_time timestamp comment '版本生效时间，闭区间左端',
    end_time   timestamp comment '版本失效时间，开区间右端',
    is_current int     comment '1=当前版本',
    version    int     comment '第几版'
) stored as orc;
```

**SCD3**：

```sql
create table dim.dim_user_scd3 (
    user_id bigint, user_name string,
    city string comment '当前地址',
    prev_city string comment '上一版地址',
    effective_time timestamp comment '当前版本生效时间'
) stored as orc;
```

**SCD4 迷你维度**：把「变化快的属性」拆出去。`dim_user` 只放 `user_id/name/register_channel`（几乎不变），`dim_user_profile` 放 `city/member_level/life_stage`（常变）。好处是主维表小、可广播；坏处是查询多一次 join。

**SCD6 混合**：每行既保留历史版本，又冗余「当前值」（`current_city`）和「上一版」（`prev_city`）。「按当前城市统计」不用再 join 当前行，「按下单时城市统计」直接用版本行。

> [!note] SCD2 和拉链表是什么关系
> SCD2 是**建模概念**（维度表保留版本），拉链表是**存储实现**（用 `start_date/end_date` 把版本压成区间）。SCD2 可以用「每日全量快照 + 版本号」实现，也可以用拉链表实现。
> 维表场景两者几乎等价，区别在：拉链表更强调「每日增量合并」和「查询必须带时间条件」，见 [02-06 拉链表实现（Hive、Spark）](02-06%20%E6%8B%89%E9%93%BE%E8%A1%A8%E5%AE%9E%E7%8E%B0%EF%BC%88Hive%E3%80%81Spark%EF%BC%89.md)。

### 2.4 SCD2 的四个关键细节

**① 时间区间开闭：用 `[start, end)`**

```sql
-- ✅ 半开区间：end_time = 下一个版本的 start_time，无缝无重叠
on o.order_time >= d.start_time and o.order_time < d.end_time

-- ⚠️ 闭区间：end_time = 下一版 start_time - 1 秒，依赖秒级精度
on o.order_time between d.start_time and d.end_time
```

半开区间的三个好处：不用做「减 1 秒」的算术（跨月、闰年、毫秒都可能出错）；`end - start` 直接是时长；相邻版本天然不重叠。**生产统一用半开区间**。

**② 当前行 `end_time` 用 `9999-12-31` 还是 `NULL`**

| 方案 | 查询当前 | 查询某天 | 问题 |
| --- | --- | --- | --- |
| `NULL` | `where end_time is null` | `where start <= t and (end > t or end is null)` | 每处都要写 `or is null`，漏一处丢当前行；`between` 直接用不了 |
| `9999-12-31` | `where is_current = 1` 或 `end_time = '9999-12-31'` | `where start <= t and end > t` | 需要约定哨兵值，不能当真实日期算 |

推荐 **`9999-12-31 23:59:59` + `is_current` 冗余**：查询简单、`between` 可用、分区裁剪友好；`is_current` 让「查当前」不依赖哨兵值。

**③ 同一天多次变更**

| 粒度 | 做法 | 结果 | 风险 |
| --- | --- | --- | --- |
| 时间戳粒度 | 每次变更一行，`start_time` 精确到秒 | 保留全部中间状态 | 版本数膨胀 |
| 日期粒度 | 每天只留最后一次，按天划区间 | 一天一行，简单 | 当天早些时候的订单会关联到当天最后的状态（错） |

生产建议：**源表有精确变更时间就用时间戳粒度**；只有每日全量快照时才用日期粒度，并在指标字典里写明「按天粒度，日内变更不可追溯」。若必须按天又要保留日内变化，用「日期 + 当日序号」做复合版本键。

**④ 维度删除怎么表达**

不要物理删。加一版 `is_deleted = 1` 的墓碑行，`start_time` = 删除时间，`end_time = 9999-12-31`，其余属性保留最后值。这样「删除前的事实」仍能关联有效维度，「删除后」关联墓碑行，可做「注销用户的历史消费」分析。

### 2.5 四种特殊维度

**退化维度（degenerate dimension）**：把单据号直接放事实表，不建维表。`order_no`、`invoice_no`、`tracking_no` 都是典型——有标识但没有描述性属性，单独建表只会多一次 join。

**杂项维度（junk dimension）**：把一堆低基数标志位合成一张维表。

```sql
create table dim.dim_order_junk (
    junk_sk bigint, is_gift int, is_presale int,
    pay_type string, source_channel string
) stored as orc;
-- 2×2×3×3 = 36 行，事实表只存一个 junk_sk
```

注意：**只放低基数、无业务层级关系的标志位**；把 `city` 这种高基数属性塞进去会组合爆炸。

**多值维度 + 桥接表**：一个商品多个标签、一个订单多个负责人。

```
dim_product ──< bridge_product_tag >── dim_tag
             (product_sk, tag_sk, weight)
```

**加权系数是关键**：一个商品有 3 个标签，按标签汇总销售额时该商品会被算 3 次。桥接表加 `weight`（如 `1/3`），汇总时 `sum(amount * weight)`，保证总额不变；如果业务就是要「每个标签都算全额」，`weight=1`，但指标名里必须写清「标签口径不可加总」。

**角色扮演维度（role-playing dimension）**：同一张 `dim_date` 被事实表多次引用——下单、支付、发货。

```sql
select o.order_id, od.date_desc as order_date_desc, pd.date_desc as pay_date_desc
from dwd.dwd_fact_order o
left join dim.dim_date od on o.order_date_sk = od.date_sk
left join dim.dim_date pd on o.pay_date_sk   = pd.date_sk;
```

物理上只有一张 `dim_date`，逻辑上有多个角色。BI 里通常建 `dim_date_order`、`dim_date_pay` 两个视图，避免用户混淆。

### 2.6 维度空值与未知成员

**绝不能让事实表外键为 NULL**。三个原因：`NULL = NULL` 是 UNKNOWN，维表关联不上；`count(distinct user_sk)` 会漏 NULL 行，用户数偏小；BI 工具通常把 NULL 单独分组，报表多出一个「空」类别。

在维表里预置三行哨兵成员：

| 代理键 | 含义 | 使用场景 |
| --- | --- | --- |
| `-1` | 未知（unknown） | 源数据有值但维表找不到（新用户未同步） |
| `-2` | 未定义（not defined） | 源数据该字段为空 |
| `-3` | 不适用（not applicable） | 业务上不该有值（线下订单的 `express_no`） |

```sql
select o.order_id, coalesce(d.user_sk, -1) as user_sk, o.amount
from ods.ods_order o
left join dim.dim_user_scd2 d
  on o.user_id = d.user_id
 and o.order_time >= d.start_time and o.order_time < d.end_time;
```

> [!warning] 哨兵值会造成数据倾斜
> 所有匹配不上的行涌向 `-1`，如果这个桶有几千万行，join 会卡在一个 task。生产上监控 `-1` 占比，超过 1% 说明维表同步有问题，先修同步，而不是靠哨兵兜底。

## 三、动手实验

### 3.1 造数：3 天 4 次变更

```sql
create table ods.ods_user_change (
    user_id bigint, user_name string, city string, update_time timestamp, dt string
) partitioned by (dt string) stored as orc;

insert into ods.ods_user_change partition (dt = '2026-10-01') values
(1001,'张三','北京市朝阳区',timestamp('2026-10-01 09:00:00'));
insert into ods.ods_user_change partition (dt = '2026-10-02') values
(1001,'张三','上海市浦东新区',timestamp('2026-10-02 10:00:00'));
insert into ods.ods_user_change partition (dt = '2026-10-03') values
(1001,'张三','上海市徐汇区',timestamp('2026-10-03 10:00:00')),
(1001,'张三','上海市静安区',timestamp('2026-10-03 18:00:00'));

create table dwd.dwd_fact_order (
    order_id string, user_id bigint, order_time timestamp, amount decimal(18,2), dt string
) partitioned by (dt string) stored as orc;

insert into dwd.dwd_fact_order partition (dt = '2026-10-01') values
('O1',1001,timestamp('2026-10-01 12:00:00'),100.00);
insert into dwd.dwd_fact_order partition (dt = '2026-10-02') values
('O2',1001,timestamp('2026-10-02 20:00:00'),200.00);
insert into dwd.dwd_fact_order partition (dt = '2026-10-03') values
('O3',1001,timestamp('2026-10-03 20:00:00'),300.00);
```

**真实地址**：O1 北京朝阳、O2 上海浦东、O3 上海静安。

### 3.2 SCD1：覆盖，只剩最新

```sql
create table dim.dim_user_scd1 (
    user_id bigint, user_name string, city string, update_time timestamp
) stored as orc;

insert overwrite table dim.dim_user_scd1
select user_id, user_name, city, update_time
from (
    select *, row_number() over (partition by user_id order by update_time desc) as rn
    from ods.ods_user_change where dt <= '2026-10-03'
) t where rn = 1;
```

结果只有一行：`1001 / 张三 / 上海市静安区 / 10-03 18:00`。三个历史时点全部丢失。

### 3.3 SCD2：版本行（核心）

```sql
create table dim.dim_user_scd2 (
    user_sk bigint, user_dk bigint, user_id bigint, user_name string, city string,
    start_time timestamp, end_time timestamp, is_current int, version int
) stored as orc;

insert overwrite table dim.dim_user_scd2
select
    cast(conv(substr(md5(concat(user_id, '|', start_time)), 1, 15), 16, 10) as bigint) as user_sk,
    cast(conv(substr(md5(cast(user_id as string)), 1, 15), 16, 10) as bigint)              as user_dk,
    user_id, user_name, city,
    start_time,
    coalesce(next_start, timestamp('9999-12-31 23:59:59')) as end_time,
    case when next_start is null then 1 else 0 end         as is_current,
    row_number() over (partition by user_id order by start_time) as version
from (
    select user_id, user_name, city, update_time as start_time,
           lead(update_time) over (partition by user_id order by update_time) as next_start
    from ods.ods_user_change where dt <= '2026-10-03'
) v;
```

预期 4 行：

| user_sk | user_id | city | start_time | end_time | is_current | version |
| --- | --- | --- | --- | --- | --- | --- |
| h1 | 1001 | 北京朝阳 | 10-01 09:00 | 10-02 10:00 | 0 | 1 |
| h2 | 1001 | 上海浦东 | 10-02 10:00 | 10-03 10:00 | 0 | 2 |
| h3 | 1001 | 上海徐汇 | 10-03 10:00 | 10-03 18:00 | 0 | 3 |
| h4 | 1001 | 上海静安 | 10-03 18:00 | 9999-12-31 | 1 | 4 |

> [!important] 用 `lead` 而不是自关联
> `lead(update_time)` 一次排序就拿到下一版起始时间，避免自关联的 O(n²)；半开区间 `[start, next_start)` 天然不重叠、无空隙。

**增量合并版**（只处理今天的新版本）：

```sql
-- ① 关闭被新版本替代的当前行
insert overwrite table dim.dim_user_scd2
select d.user_sk, d.user_dk, d.user_id, d.user_name, d.city, d.start_time,
       case when n.user_id is not null then n.start_time else d.end_time end as end_time,
       case when n.user_id is not null then 0 else d.is_current end            as is_current,
       d.version
from dim.dim_user_scd2 d
left join (
    select user_id, min(update_time) as start_time
    from ods.ods_user_change where dt = '2026-10-03' group by user_id
) n on d.user_id = n.user_id and d.is_current = 1;

-- ② 插入今天的新版本（同日多次按时间戳各插一版）
insert into table dim.dim_user_scd2
select
    cast(conv(substr(md5(concat(user_id,'|',update_time)),1,15),16,10) as bigint),
    cast(conv(substr(md5(cast(user_id as string)),1,15),16,10) as bigint),
    user_id, user_name, city, update_time,
    coalesce(lead(update_time) over (partition by user_id order by update_time),
             timestamp('9999-12-31 23:59:59')),
    case when lead(update_time) over (partition by user_id order by update_time) is null then 1 else 0 end,
    row_number() over (partition by user_id order by update_time) + 100  -- 生产要取 max(version)
from ods.ods_user_change where dt = '2026-10-03';
```

> [!warning] 自读自写在 Spark 上可能报错
> 上面的 `insert overwrite dim.dim_user_scd2 select ... from dim.dim_user_scd2` 在 Hive 3 通常可用，Spark 3.5 可能抛 `Cannot overwrite a path that is being read`。生产改为「读旧表 → 写 tmp 表 → 校验 → 覆盖/交换」，同时解决原子性和可回滚。

> [!danger] 这个两步写法不是原子的
> ① 成功、② 失败，就会出现「旧行已关闭、新行没插入」的空档。生产上要么用 `merge`（Delta/Hudi/ACID），要么**整表重算**（维表通常不大），要么把两步放进同一调度事务并加对账。
> 版本号 `+100` 只是演示，真实要 `max(version) + row_number()`，否则重跑会撞号。

### 3.4 SCD3：当前 + 上一版

```sql
create table dim.dim_user_scd3 (
    user_id bigint, user_name string, city string, prev_city string, effective_time timestamp
) stored as orc;

insert overwrite table dim.dim_user_scd3
select user_id,
       max(case when rn = 1 then user_name end)    as user_name,
       max(case when rn = 1 then city end)         as city,
       max(case when rn = 2 then city end)         as prev_city,
       max(case when rn = 1 then update_time end)  as effective_time
from (
    select *, row_number() over (partition by user_id order by update_time desc) as rn
    from ods.ods_user_change where dt <= '2026-10-03'
) t where rn <= 2
group by user_id;
```

结果：`city=上海静安`、`prev_city=上海徐汇`、`effective_time=10-03 18:00`。**北京和浦东都丢了**。

### 3.5 核心对比：同一批历史订单关联三种维表

```sql
-- SCD1：只按自然键
select o.order_id, o.order_time, o.amount, d.city
from dwd.dwd_fact_order o
left join dim.dim_user_scd1 d on o.user_id = d.user_id;

-- SCD2：自然键 + 半开区间
select o.order_id, o.order_time, o.amount, d.city
from dwd.dwd_fact_order o
left join dim.dim_user_scd2 d
  on o.user_id = d.user_id
 and o.order_time >= d.start_time
 and o.order_time <  d.end_time;

-- SCD3：当前版本生效前用 prev，之后用 current
select o.order_id, o.order_time, o.amount,
       case when o.order_time >= d.effective_time then d.city else d.prev_city end as city
from dwd.dwd_fact_order o
left join dim.dim_user_scd3 d on o.user_id = d.user_id;
```

| 订单 | 下单时真实地址 | SCD1 | SCD2 | SCD3 |
| --- | --- | --- | --- | --- |
| O1（10-01 12:00） | 北京朝阳 | 上海静安 ❌ | 北京朝阳 ✅ | 上海徐汇 ❌ |
| O2（10-02 20:00） | 上海浦东 | 上海静安 ❌ | 上海浦东 ✅ | 上海徐汇 ❌ |
| O3（10-03 20:00） | 上海静安 | 上海静安 ✅ | 上海静安 ✅ | 上海静安 ✅ |

**读结果**：

- **SCD1** 把三个订单全改成当前地址，按城市统计历史 GMV 会全部算到上海静安——**历史被静默改写**，且不报错。
- **SCD2** 三个订单各自命中下单时版本，是唯一能回答「当时在哪」的方案。
- **SCD3** 只能回溯一版：O1、O2 都落到 `prev_city=上海徐汇`，因为再往前没存。**SCD3 适合「调价前后对比」，不适合做历史归属。**

> [!tip] 验证 SCD2 没有放大
> ```sql
> select order_id, count(*) as cnt
> from dwd.dwd_fact_order o
> join dim.dim_user_scd2 d
>   on o.user_id = d.user_id
>  and o.order_time >= d.start_time and o.order_time < d.end_time
> group by order_id having count(*) > 1;   -- 应为 0 行
> ```

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 历史订单的城市/等级被改成最新值 | 该属性用了 SCD1 | 对比同一订单不同日期跑出的结果 | 改 SCD2，按订单时间关联版本 |
| 一个用户出现多条 `is_current=1` | 关闭旧行逻辑漏了，或并发写 | `group by user_id having sum(is_current)>1` | 唯一性校验 + 合并前去重 |
| 维表 join 后订单翻倍 | SCD2 区间重叠 | `lag(end_time)` 与 `start_time` 比对 | 半开区间，`end_time = next_start` |
| 查「当前」查不到数据 | 当前行 `end_time` 为 NULL，用了 `between` | 看当前行 `end_time` | 用 `9999-12-31` + `is_current` |
| 代理键重跑后全变，历史事实错位 | 用 `row_number()` 生成 | 重跑维表对比 `user_sk` | 改 hash 或持久映射表 |
| 事实表 join 不上维表，指标偏小 | 外键为 NULL | `count(*) - count(user_sk)` | 预置 `-1/-2/-3` 未知成员 |
| 按标签汇总销售额翻倍 | 多值维度直接 join，没加权 | 对比总额与明细总额 | 桥接表 + `weight=1/n` |
| 维表越来越大，广播 OOM | 所有属性都做 SCD2 | 看版本数分布 | 快变属性拆 SCD4 迷你维度 |
| 同一天两次变更只剩最后一次 | 按天粒度合并 | 检查当天订单归属 | 时间戳粒度或复合版本键 |
| 用户注销后历史订单关联不上 | 维度被物理删除 | `left join` 后属性为 NULL | 打 `is_deleted` 墓碑行 |
| 杂项维度组合爆炸 | 把高基数属性塞进 junk dim | `count(distinct 组合)` | 只放低基数标志位 |
| 同一张 `dim_date` join 两次列名冲突 | 角色扮演没起别名 | 看 SQL | 每次 join 用不同别名/视图 |

## 五、面试追问

> [!question] 1. 用户改了地址，历史订单应该关联旧地址还是新地址？
> **一句话答法**：看指标口径。要回答「当时在哪下单」就关联旧地址，用 SCD2 按订单时间命中版本；要回答「用户现在在哪」就关联新地址，用 SCD1。绝大多数交易分析用前者。
> **追问陷阱**：「为什么不能两种都要」——可以，用 SCD6：版本行保留 as-was，每行再冗余 `current_city` 供 as-is 查询，但要想清楚每个指标用哪一列。

> [!question] 2. SCD2 怎么查当前有效行？
> **一句话答法**：`where is_current = 1`，或 `where end_time = '9999-12-31 23:59:59'`。推荐前者，不依赖哨兵值。
> **追问陷阱**：「为什么不用 `end_time is null`」——`between` 和范围查询会漏掉 NULL 行，每处都要写 `or end_time is null`，漏一处就少数据。

> [!question] 3. 代理键有什么用？为什么不用自然键？
> **一句话答法**：四个作用——隔离源系统变更、支持 SCD2 多版本、提升 join 性能、统一跨源编码。自然键做不到「同一实体多版本」，且类型和编码不稳定。
> **追问陷阱**：「代理键用 row_number 行不行」——不行，重跑或中间插版本会让后续键整体偏移，历史事实立刻错位。要用 hash 或持久映射表。

> [!question] 4. 同一天变更了两次怎么处理？
> **一句话答法**：源表有精确时间就用时间戳粒度，两次各留一版；只有每日快照就按天合并、留最后一次，并在口径里声明「日内变更不可追溯」。
> **追问陷阱**：「按天合并后，当天上午的订单会怎样」——会关联到当天最后的状态，属于已知精度损失。要避免就用「日期 + 当日序号」做复合版本键。

> [!question] 5. 维表重复导致 join 放大，怎么防？
> **一句话答法**：三道防线——加载前对自然键做唯一性校验（`is_current=1` 只能一行）、join 前用 `row_number` 去重、上线后监控「join 前后行数比」。
> **追问陷阱**：「SCD2 本来就有多行，怎么判断是正常还是重复」——按「自然键 + 时间点」判断：任一时点只能命中一行，用区间重叠校验 `start_time < lag(end_time)`。

> [!question] 6. SCD1、SCD2、SCD3 的区别？
> **一句话答法**：SCD1 覆盖不留历史；SCD2 加版本行、保留全部历史；SCD3 加 `prev_` 列、只留上一版。历史深度和存储成本依次是 2 > 3 > 1。
> **追问陷阱**：「SCD3 能不能留三版」——加 `prev2_` 可以，但每加一版就加一列，本质是把 SCD2 的纵向行数换成横向列数，超过 2 版就该用 SCD2。

> [!question] 7. 什么场景用 SCD3 而不是 SCD2？
> **一句话答法**：只关心「变化前后对比」且变化频率低的属性，比如商品调价前后、会员等级升降、费率调整。查询不用带时间条件，一列 `prev` 就够。
> **追问陷阱**：「价格用 SCD2 还是快照」——算「下单时成本/毛利」用 SCD2（按订单时间关联）；算「每日均价、价格带分布」用价格日快照（事实表）。

> [!question] 8. 退化维度是什么？为什么要退化？
> **一句话答法**：把订单号、发票号这类「有标识但没描述属性」的字段直接放事实表，不单独建维表，省一次 join。
> **追问陷阱**：「订单号上有下单渠道、门店，还能退化吗」——那些属性放 `dim_order` 或杂项维度，订单号本身仍可退化；退化的只是「单号」这个标识。

> [!question] 9. 多值维度怎么建模？
> **一句话答法**：用桥接表 `fact ↔ bridge ↔ dim`，桥接表带 `weight` 加权系数，汇总时 `sum(amount * weight)`，保证总额不变。
> **追问陷阱**：「weight 怎么定」——等权分摊用 `1/n`；业务上有一个主标签就用「主标签计全额、其余 `weight=0`」。

> [!question] 10. 角色扮演维度是什么？
> **一句话答法**：同一张物理维表被事实表多次引用，承担不同角色，比如 `dim_date` 同时是下单、支付、发货日期。查询时用不同别名 join。
> **追问陷阱**：「为什么不建三张日期表」——冗余且口径容易漂移；一张表 + 多个视图既保证一致，又让 BI 用户不混淆。

> [!question] 11. 维度表为什么不能用 NULL 做外键？
> **一句话答法**：`NULL = NULL` 是 UNKNOWN，join 不上；`count(distinct)` 会漏；BI 会多出一个「空」分组。要用 `-1/-2/-3` 哨兵成员。
> **追问陷阱**：「哨兵值有什么副作用」——所有异常行涌向 `-1`，会造成数据倾斜；监控占比，超过 1% 先修维表同步。

> [!question] 12. SCD2 和拉链表有什么区别？
> **一句话答法**：SCD2 是建模概念（保留版本），拉链表是存储实现（用 `start_date/end_date` 压成区间）。维表场景两者几乎等价，拉链表更强调每日增量合并和「查询必须带时间条件」。
> **追问陷阱**：「拉链表能不能不做 SCD2」——不能，拉链表就是 SCD2 的一种物理落地；没有版本语义，区间就没有意义。

## 六、自测题

> [!question] 1.（单选）要回答「用户下单时所在城市」，`dim_user.city` 应该用哪种 SCD？
> A. SCD1　B. SCD2　C. SCD3　D. 不需要 SCD

> [!question] 2.（单选）SCD2 中当前行的 `end_time` 推荐用？
> A. `NULL`　B. 当天日期　C. `9999-12-31 23:59:59`　D. 空字符串

> [!question] 3.（判断）代理键可以用 `row_number()` 生成，只要排序字段固定就不会变。

> [!question] 4.（场景设计）商品维表有 `sku_id`、`category`（几乎不变）、`price`（每周变）、`tag`（一个商品多个标签）。请设计维表方案：用哪种 SCD、要不要拆表、多值标签怎么处理，并说明「按品类算历史 GMV」和「按下单时价格算毛利」分别怎么关联。

> [!question] 5.（场景设计）业务反馈「按城市统计的去年 GMV 这个月变了」。请给出排查步骤，说明最可能的根因、如何验证、如何修复，并给出防止复发的建模约束。

> [!success]- 答案与解析（点击展开）
> **1. B**
> 要 as-was，必须保留版本行，按 `order_time` 命中 `[start_time, end_time)`。SCD1 会把历史订单改成当前城市；SCD3 只能回溯一版。
>
> **2. C**
> 用哨兵值让范围查询 `start <= t and end > t` 对当前行也成立；再冗余 `is_current=1` 让「查当前」不依赖哨兵。`NULL` 会让 `between` 漏掉当前行。
>
> **3. 错误**
> 即使排序字段固定，插入一个新版本（尤其是历史版本）也会让后续行序号整体后移。SCD2 会往中间插版本，所以 `row_number` 不适合做持久代理键。
>
> **4. 参考方案**
> - `category` 几乎不变 → 放主维表，SCD1（纠错场景）。
> - `price` 每周变且要算历史毛利 → 拆独立价格维表用 SCD2（`sku_id, price, start_time, end_time, is_current`），或做价格日快照事实表。按下单时价格算毛利就按 `order_time` 关联 SCD2。
> - `tag` 多值 → 桥接表 `bridge_product_tag(product_sk, tag_sk, weight)`，按标签汇总 `sum(amount * weight)`；只做筛选不做汇总时可直接 `exists`，不会放大。
> - 「按品类算历史 GMV」：品类不变直接 join 主维表；若品类也会调整，品类也要 SCD2，否则历史会被重分类。
>
> **5. 排查步骤**
> ① 复现：用去年同一 SQL 跑一遍，对比「去年 GMV 按城市」的差异行。
> ② 看维表：`select user_id, count(*) from dim_user group by user_id having count(*)>1`，确认是否多条当前行。
> ③ 看 SCD 类型：如果 `dim_user` 只有一行/用户且 `city` 是最新值，说明用了 SCD1。
> ④ 看 join 条件：`on o.user_id=d.user_id` 没有时间条件，SCD2 会命中多行 → 金额放大；或命中当前行 → 历史被改写。
>
> **最可能根因**：`city` 用了 SCD1（或 SCD2 但 join 没带时间条件），用户迁移后历史订单被重新归属。
>
> **修复**：`city` 改 SCD2，join 加 `order_time >= start_time and order_time < end_time`；重跑历史指标；对账「新旧总 GMV 应相等，只有城市分布变化」。
>
> **防复发**：① 维表每个属性标注 SCD 类型；② 所有 SCD2 join 强制带时间条件（用视图封装，禁止裸 join）；③ 上线校验「任一时点每自然键只命中一行」；④ 指标变更走评审（见 [02-11 建模评审 Checklist](02-11%20%E5%BB%BA%E6%A8%A1%E8%AF%84%E5%AE%A1%20Checklist.md)）。
