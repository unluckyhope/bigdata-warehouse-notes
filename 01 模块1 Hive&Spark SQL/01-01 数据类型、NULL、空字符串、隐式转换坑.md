# 01-01 数据类型、NULL、空字符串、隐式转换坑

> [!abstract] 一句话结论
> 数仓里「数据对不上」的问题，八成不是逻辑写错，而是**类型和 NULL 在你看不见的地方改了值**。
> 记住三句话：`NULL` 会让比较结果变成 `UNKNOWN`（既不是真也不是假）；Hive 里 `''` 不等于 `NULL`；`string` 和数值比较时会触发隐式转换，可能让分区裁剪和索引直接失效。

---

## 一、心智模型：SQL 引擎的三层，类型在哪一层被「定死」

写 SQL 时你看到的是文本，引擎看到的是三阶段流水线：

| 阶段 | 做什么 | 类型在这里发生了什么 |
| --- | --- | --- |
| 解析 / 语义分析 | 建 AST、解析表、**做类型推断与隐式转换** | 每个表达式的类型在这里**一次性定死**，后续不再改 |
| 逻辑优化 | 谓词下推、列裁剪、分区裁剪、常量折叠 | 依赖上一步的类型信息做判断；类型不对 → 优化直接放弃 |
| 物理执行 | 生成 task、shuffle、逐行计算 | 按已确定的类型做 cast、比较、聚合 |

**关键推论**：一旦解析层把一个 `string` 列和数字做了隐式转换，后面所有优化（尤其是分区裁剪）都会失效——因为优化器看到的不再是「列 = 常量」，而是「cast(列 as double) = 常量」，函数包住了列，裁剪就无从下手。

这就是「类型选错 → 慢 10 倍」的完整因果链，不是玄学。

上表把「解析」和「语义分析」合并成了第一行。拆开看更清楚：**类型在第 ② 步就定死了，而分区裁剪要到第 ③ 步才发生**——顺序决定了裁剪器拿到的，是一个已经被改写过的条件。

## 二、核心知识点

### 2.1 类型体系：先分清「谁存得准、谁存得快」

Hive / Spark SQL 的类型分两大类：

**基本类型（面试常考这几个）**

| 类型 | 范围 / 精度 | 存储 | 什么时候用 |
| --- | --- | --- | --- |
| `tinyint` / `smallint` / `int` / `bigint` | 1/2/4/8 字节整数 | 定长 | 计数、ID。**计数一律 `bigint`**，`int` 上限 21 亿，埋点表迟早爆 |
| `decimal(p,s)` | 精确十进制，p 总位数、s 小数位 | 变长 | **金额、汇率、比例**，必须用它 |
| `double` / `float` | IEEE754 浮点，近似值 | 8 / 4 字节 | 科学计算、埋点数值。**不要存钱** |
| `string` | 任意长度字符串 | 变长 | 默认兜底类型，但别当万能药 |
| `varchar(n)` / `char(n)` | 有长度约束 | 变长 / 定长 | 有明确长度上限的枚举、编码 |
| `boolean` | true / false / NULL | 1 bit | 标志位 |
| `date` | 年月日 | 4 字节 | 只要日期不要时分秒 |
| `timestamp` | 年月日时分秒 + 纳秒 | 12 字节 | 需要精确到秒/毫秒的事件时间 |
| `binary` | 字节数组 | 变长 | 少见，存序列化数据 |

**复杂类型**：`array<T>`、`map<K,V>`、`struct<...>`。后面 01-06 讲 explode 时会重点用。

> [!warning] `decimal` vs `double` 是硬分界线
> `double` 是二进制浮点，`0.1 + 0.2 != 0.3`。金额用 `double` 存，对账时会出现「差 1 分钱」的经典事故。
> 生产铁律：**金额、单价、汇率、折扣率 → `decimal(18,4)` 或 `decimal(20,6)`**；只有埋点里的经纬度、评分这类「不需要精确相等」的才用 `double`。

**`decimal` 的精度溢出**：`decimal(p,s)` 的 `p` 是总位数。`decimal(10,2)` 最大只能存 `99999999.99`。两个 `decimal(10,2)` 相乘，结果类型是 `decimal(21,4)`（p 相加、s 相加），如果目标列是 `decimal(10,2)` 就会截断。累加超过 `p` 位会直接变 `NULL`，**不报错**——这是最阴的一类 bug。

### 2.2 `string` 是万能类型，也是万能坑

Hive 允许 `string` 和几乎所有类型比较、运算，代价是隐式转换：

```sql
-- 你以为：字符串比字符串
where dt = '2026-10-01'

-- 实际：如果 dt 是 string，右边也是 string，没问题
-- 但如果右边写成数字，或者列本身是 int 存了 '20261001'
where dt = 20261001        -- string vs int → 把 string cast 成 double 再比
```

**隐式转换的方向**（Hive 遵循「窄 → 宽」，Spark 更严格）：

```
tinyint → smallint → int → bigint → float → double
                    ↘ decimal ↗
string ←→ 任意数值（双向都能转，最危险）
```

**为什么危险**：`cast('2026-10-01' as double)` 在 Hive 里返回 `NULL`（不报错），于是 `dt = 20261001` 这个条件永远不成立 → **查出来 0 行，但你不报错**。

> [!tip] 排查口诀
> 结果为空但「明明有数据」→ 先查有没有类型不匹配的等值条件。
> 加一句 `select cast(你的条件列 as double)` 看是不是全 NULL。

### 2.3 NULL 的三值逻辑：不是「空」，是「未知」

SQL 的布尔运算有**三个值**：`TRUE` / `FALSE` / `UNKNOWN`。`NULL` 参与的任何比较都得到 `UNKNOWN`。

| 表达式 | 结果 | 说明 |
| --- | --- | --- |
| `NULL = NULL` | `UNKNOWN` | 所以不能用 `=` 判断 NULL |
| `NULL != NULL` | `UNKNOWN` | 同上 |
| `NULL > 5` | `UNKNOWN` | 任何比较都是 UNKNOWN |
| `NULL + 1` | `NULL` | 算术运算被 NULL 传染 |
| `NULL AND FALSE` | `FALSE` | **特例**：FALSE 能压过 UNKNOWN |
| `NULL AND TRUE` | `UNKNOWN` | |
| `NULL OR TRUE` | `TRUE` | **特例**：TRUE 能压过 UNKNOWN |
| `NULL OR FALSE` | `UNKNOWN` | |

**`WHERE` 只保留结果为 `TRUE` 的行**，`FALSE` 和 `UNKNOWN` 都被过滤掉。这一条解释了大量「为什么我的数据少了」。

```sql
-- 想查「状态不是已完成」的记录
where status != 'DONE'        -- ❌ status 为 NULL 的行会被丢掉
where status != 'DONE' or status is null   -- ✅ 正确写法
where nvl(status,'') != 'DONE'             -- ✅ 也可以，但注意语义
```

### 2.4 `''` 和 `NULL` 不是一回事（Hive 视角）

这是 Hive 和 Oracle/MySQL 最大的语义分歧之一：

| 引擎 | `''` 是什么 | `'' is null` |
| --- | --- | --- |
| Oracle | 就是 `NULL` | `TRUE` |
| MySQL | 空字符串，和 NULL 不同 | `FALSE` |
| **Hive / Spark** | **空字符串，长度 0，非 NULL** | **`FALSE`** |

所以在 Hive 里：

```sql
select '' is null;                 -- false
select length('') ;                -- 0
select nvl('', 'x');               -- ''（空串不是 NULL，nvl 不生效！）
select coalesce('', 'x');          -- ''（同理）
```

> [!danger] 最高频的生产事故
> 上游用 `nvl(phone, '')` 清洗，你以为空值都变成了空串，于是下游用 `phone is null` 判空 → **永远查不到**。
> 反过来，如果上游把空串写成 `NULL`，下游用 `phone = ''` 判空 → 也永远查不到。
> **约定必须写进规范**：数仓内部统一「空值 = NULL，禁止用空串表示缺失」，且落表时用 `nullif(trim(col), '')` 把空串转成 NULL。

```sql
-- 推荐的清洗写法：去空格 + 空串转 NULL
select nullif(trim(phone), '') as phone from ods.user;
```

### 2.5 聚合函数怎么处理 NULL

| 函数 | 对 NULL 的处理 | 结果 |
| --- | --- | --- |
| `count(*)` | 数**行数**，不看列 | 包含 NULL 行 |
| `count(1)` | 同上（恒真常量） | 与 `count(*)` 等价 |
| `count(col)` | 只数 `col is not null` 的行 | **会少** |
| `count(distinct col)` | 忽略 NULL，且 NULL 不计入 | 去重后非空数 |
| `sum(col)` | 忽略 NULL；**全 NULL 时返回 NULL**（不是 0） | 注意 |
| `avg(col)` | 分母是**非 NULL 行数**，不是总行数 | 与「sum/count(*)」不同 |
| `max/min` | 忽略 NULL；全 NULL 返回 NULL | |
| `first_value/last_value` | **不忽略**，会取到 NULL | 窗口里特别注意 |

> [!example] `avg` 的经典陷阱
> 10 行数据，其中 5 行 `amount` 为 NULL，其余 5 行都是 100。
> - `avg(amount)` = 500 / 5 = **100**
> - `sum(amount) / count(*)` = 500 / 10 = **50**
> 两个都对，取决于业务口径「NULL 算不算 0」。**口径必须和业务方确认后写进注释**，别自己猜。

`sum` 全 NULL 返回 NULL 这点，会导致下游 `a + sum(x)` 整列变 NULL。防御写法：

```sql
select coalesce(sum(amount), 0) as total_amount from t;
```

### 2.6 NULL 在 GROUP BY / JOIN / DISTINCT / 排序里的行为

| 场景 | 行为 | 后果 |
| --- | --- | --- |
| `GROUP BY col` | **所有 NULL 归为同一组** | 不会每行一组，会聚成一组 |
| `GROUP BY` 多列中含 NULL | 按「NULL 等于 NULL」处理 | 与 `=` 的行为相反，容易记混 |
| `JOIN ... ON a.k = b.k` | `NULL = NULL` 为 UNKNOWN → **不匹配** | 左右表的 NULL 行互相 join 不上 |
| `DISTINCT` | 所有 NULL 视为**一个**值 | `distinct` 后只剩一行 NULL |
| `ORDER BY col` | Hive 默认 NULL 最小（升序在最前）；Spark 默认 NULL 最小，可用 `NULLS LAST` 调整 | 排序结果两端不一致 |
| `IN (子查询含 NULL)` | `x IN (1,2,NULL)` → 若 x 不在 (1,2) 中，结果是 UNKNOWN 而非 FALSE | **NOT IN + 子查询含 NULL = 永远空结果** |

> [!danger] `NOT IN` 遇 NULL 的经典血案
> ```sql
> -- 想找「不在黑名单里的用户」
> select * from dwd.user
> where user_id not in (select user_id from dim.blacklist);
> ```
> 只要 `blacklist.user_id` 里有一个 NULL，整个 `NOT IN` 就返回空集——因为对任意 `user_id`，`user_id <> NULL` 是 UNKNOWN，`NOT IN` 要求全部为 TRUE，UNKNOWN 直接判死。
> **修复**：`where user_id not in (select user_id from dim.blacklist where user_id is not null)`，或改用 `left join ... where b.user_id is null`（anti join）。

### 2.7 隐式转换让分区裁剪失效（本节最重要的生产结论）

分区裁剪发生在**逻辑优化阶段**，它只认一种模式：`分区列 <op> 常量`。

```sql
-- ✅ 能裁剪：直接对分区列做常量比较
where dt = '2026-10-01'
where dt between '2026-10-01' and '2026-10-31'
where dt >= '2026-10-01'          -- 字符串比较，字典序 = 日期序（格式必须 yyyy-MM-dd）

-- ❌ 不能裁剪：函数包住了分区列
where substr(dt,1,7) = '2026-10'
where date_format(dt,'yyyyMM') = '202610'
where cast(dt as date) = '2026-10-01'

-- ❌ 不能裁剪：类型不匹配触发隐式 cast
where dt = 20261001               -- dt 是 string → cast(dt as double)，包住了列
```

**裁剪失效的代价**：假设表有 3 年分区、每天 100GB，本该扫 1 天 100GB，实际扫 3 年 ≈ 100TB。在按扫描量计费的环境里这是真金白银。

> [!tip] 正确的「按月查」写法
> 不要对分区列用函数，而是**把函数用在常量侧**，或者显式列出分区：
> ```sql
> -- 方式一：范围条件（推荐）
> where dt >= '2026-10-01' and dt < '2026-11-01'
>
> -- 方式二：LIKE 前缀（Hive 支持前缀裁剪，部分版本支持）
> where dt like '2026-10%'
>
> -- 方式三：动态生成分区列表后拼 SQL（脚本层解决）
> ```

### 2.8 整数溢出与类型提升

```sql
select 2147483647 + 1;        -- int 溢出，Hive 返回 NULL（Spark 返回 NULL 或抛错，看配置）
select cast(2147483647 as bigint) + 1;   -- 正确
```

**生产建议**：
- 计数、ID、金额累加 → 一律 `bigint` / `decimal`
- 除法注意：Hive 里 `int / int` 结果是 `double`，不是 `int`。想要整数除法用 `div` 或 `cast(... as int)`
- `sum(bigint)` 在极大数据量下也可能溢出（9.2e18），概率极低但存在

## 三、动手实验：一次把坑全踩一遍

### 3.1 建表 + 造数

```sql
-- 实验表：故意用 string 存日期和金额，模拟脏数据
drop table if exists tmp.type_lab;
create table tmp.type_lab (
    id          int,
    dt          string      comment '分区风格日期，但这里当普通列',
    phone       string,
    amount_str  string      comment '金额存成了字符串',
    amount_dec  decimal(18,4),
    amount_dbl  double,
    status      string
) stored as parquet;

insert into tmp.type_lab values
(1, '2026-10-01', '13800000001', '100.10', 100.1000, 100.10, 'DONE'),
(2, '2026-10-02', '',            '200.20', 200.2000, 200.20, 'DONE'),
(3, '2026-10-03', null,          '300.30', 300.3000, 300.30, null),
(4, '2026-10-04', '13800000004', null,     null,     null,   'DONE'),
(5, '2026-10-05', '13800000005', '0',      0.0000,   0.0,    null);
```

### 3.2 实验一：`''` 与 `NULL` 的差异

```sql
select
    count(*)                                   as total_rows,      -- 5
    count(phone)                               as cnt_phone,       -- 3（'' 和 NULL 都不算非空？不，'' 算非空！）
    sum(if(phone is null, 1, 0))               as cnt_null,        -- 1（只有 id=3）
    sum(if(phone = '', 1, 0))                  as cnt_empty,       -- 1（id=2）
    sum(if(nvl(phone,'X') = 'X', 1, 0))        as cnt_nvl_x        -- 1（nvl 对 '' 无效！）
from tmp.type_lab;
```

**预期结果解读**：
- `cnt_phone = 4`：`''` 被认为是非 NULL，`count(phone)` 会数它
- `cnt_null = 1`：只有显式 `null` 的那行
- `cnt_empty = 1`：空串单独统计
- `cnt_nvl_x = 1`：`nvl('', 'X')` 返回 `''`，证明 nvl 不把空串当 NULL

> [!success] 这一组数说明
> 「判空」必须用 `is null`，不能用 `= ''`；「清洗空值」必须用 `nullif(trim(x),'')`，不能用 `nvl`。

### 3.3 实验二：decimal vs double 的精度差

```sql
select
    sum(amount_dec)  as sum_dec,
    sum(amount_dbl)  as sum_dbl,
    sum(amount_dec) - sum(amount_dbl) as diff
from tmp.type_lab;
```

再做一个更狠的对比：

```sql
select
    0.1 + 0.2                    as dbl_calc,        -- 0.30000000000000004
    cast(0.1 as decimal(10,2)) + cast(0.2 as decimal(10,2)) as dec_calc  -- 0.30
;
```

**结论**：金额走 `decimal`，比较、累加、对账都不会出偏差。

### 3.4 实验三：`NOT IN` 遇 NULL

```sql
-- 造一张含 NULL 的"黑名单"
drop table if exists tmp.blacklist_lab;
create table tmp.blacklist_lab (phone string);
insert into tmp.blacklist_lab values ('13800000001'), (null);

-- ❌ 错误写法：结果为空
select * from tmp.type_lab
where phone not in (select phone from tmp.blacklist_lab);

-- ✅ 写法一：过滤子查询里的 NULL
select * from tmp.type_lab
where phone not in (select phone from tmp.blacklist_lab where phone is not null);

-- ✅ 写法二：anti join（生产更推荐，可读性和性能都更好）
select a.*
from tmp.type_lab a
left join tmp.blacklist_lab b on a.phone = b.phone
where b.phone is null;
```

> [!note] 为什么 anti join 更好
> 除了避开 NULL 语义坑，anti join 在 Spark 里能被优化成 `BroadcastHashJoin`（左表大右表小时），而 `NOT IN` 子查询在部分版本会退化成 `BroadcastNestedLoopJoin`，复杂度 O(n*m)。

### 3.5 实验四：隐式转换导致全 NULL

```sql
select
    dt,
    cast(dt as double) as dt_as_double,     -- 全 NULL
    (dt = 20261001)    as cmp_result        -- 全 NULL / false
from tmp.type_lab;
```

再看执行计划（Spark）：

```sql
explain extended
select * from tmp.type_lab where dt = 20261001;
-- 观察 Filter 节点：条件被改写成 cast(dt#xx as double) = 2.0261001E7
-- 如果 dt 是分区列，这一步会让 PartitionPruning 直接放弃
```

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 金额对账差几分钱 | 用 `double`/`float` 存金额，浮点误差累积 | `sum(a) - sum(b)` 看差值是否落在 1e-10 量级 | 全链路改 `decimal(18,4)`，禁止 `double` 存金额 |
| 查询结果为空但表里有数据 | 等值条件类型不匹配，隐式 cast 成 NULL | 单独 `select cast(条件列 as 目标类型) limit 10` | 条件两侧显式同类型，字符串加引号 |
| 任务扫描量突然涨 10 倍 | 分区列被函数包裹 / 类型不匹配，裁剪失效 | 看执行计划有没有 `PartitionFilters`；看 `input size` | 改写为 `dt >= 'x' and dt < 'y'` |
| `count(col)` 和 `count(*)` 差很多 | 列里有大量 NULL 或空串 | `count(*) - count(col)` 量化缺口 | 明确口径；需要算「有值的行」才用 `count(col)` |
| 上游改字段类型后下游全 NULL | 隐式转换失败返回 NULL 而不报错 | 数据质量校验加「非空率骤降」告警 | 建表强约束类型；加 DQ 规则 |
| `nvl` 清洗后判空查不到 | Hive 中 `''` 不是 NULL | `select '' is null` 验证 | 改用 `nullif(trim(x),'')` |
| 空串和 NULL 混存，去重结果偏多 | 两者被当成不同值 | `group by col` 看是否有两行（NULL 和 空串） | 入仓统一 `nullif(trim(x),'')` |
| 累加值突然变 NULL | `decimal` 精度溢出，或 `sum` 全 NULL | 检查 `decimal(p,s)` 的 p 是否够 | 放大 p；`coalesce(sum(x),0)` |
| `NOT IN` 子查询返回空 | 子查询结果含 NULL | `select count(*) from (子查询) where col is null` | 过滤 NULL 或改 anti join |
| 排序结果与 MySQL 不一致 | NULL 排序默认位置不同 | 对比两端 `order by` 结果 | 显式写 `NULLS LAST` / `NULLS FIRST` |
| 除法结果多出小数 | `int / int` 自动提升为 `double` | 看结果类型 | 用 `div` 或 `cast(x as int)` 取整 |

## 五、面试追问

> [!question] 1. `count(*)`、`count(1)`、`count(col)` 有什么区别？
> **一句话答法**：`count(*)` 和 `count(1)` 数行数，结果完全一致；`count(col)` 只数 `col is not null` 的行，遇到 NULL 会跳过。
> **追问陷阱**：面试官可能接着问「性能上 `count(1)` 比 `count(*)` 快吗」——答案是**在现代优化器里没有区别**，`count(*)` 会被改写成 `count(1)`，别答「`count(1)` 快」这种十年前的结论。

> [!question] 2. Hive 里 `''` 和 `NULL` 一样吗？
> **一句话答法**：不一样。Hive 中 `''` 是长度 0 的非 NULL 字符串，`'' is null` 返回 false；Oracle 里两者等价。
> **追问陷阱**：接着会问「那 `nvl('','x')` 返回什么」——返回 `''`，因为 nvl 只判 NULL。正确清洗是 `nullif(trim(x),'')`。

> [!question] 3. 为什么 `where col != 'A'` 会丢数据？
> **一句话答法**：`col` 为 NULL 时 `NULL != 'A'` 是 `UNKNOWN`，`WHERE` 只保留 TRUE，所以这些行被过滤掉了。
> **追问陷阱**：「那 `where col != 'A' or col is null` 就够了吗」——语义上够了，但要确认业务上 NULL 到底算不算「不等于 A」，有些场景 NULL 应该单独归类。

> [!question] 4. 分区裁剪为什么会被函数打断？
> **一句话答法**：裁剪只识别 `分区列 <op> 常量` 这种形式，一旦函数包住列（`substr`、`date_format`、隐式 `cast`），优化器无法反推分区范围，只能全表扫。
> **追问陷阱**：「那 `where dt like '2026-10%'` 能裁剪吗」——Hive 支持前缀 LIKE 裁剪，但**不是所有版本和所有引擎都支持**，Spark 对 `like` 的裁剪支持有限，稳妥写法还是范围条件。

> [!question] 5. `avg` 和 `sum/count(*)` 什么时候不一样？
> **一句话答法**：列里有 NULL 时不一样。`avg` 的分母是非 NULL 行数，`count(*)` 是总行数。
> **追问陷阱**：「业务要「人均消费」，NULL 该不该算 0」——这是口径问题，必须和业务确认，不能技术拍板。

> [!question] 6. `decimal(10,2)` 存 1 亿会怎样？
> **一句话答法**：`p=10` 表示总位数 10 位，`99999999.99` 是上限，1 亿会溢出。
> **追问陷阱**：「溢出是报错还是 NULL」——Hive/Spark 默认行为是返回 `NULL`（部分配置下抛错），所以是**静默数据错误**，比报错更危险。

> [!question] 7. 两张表 join，key 都是 NULL，能 join 上吗？
> **一句话答法**：不能。`ON a.k = b.k` 中 `NULL = NULL` 是 `UNKNOWN`，不满足 join 条件。
> **追问陷阱**：「那怎么让 NULL 匹配上」——用 `nvl(k, '未知')` 或 `coalesce(k, -1)` 造一个哨兵值，但要评估这个「未知」桶会不会造成数据倾斜。

> [!question] 8. `group by` 时多个 NULL 会分成多组吗？
> **一句话答法**：不会，所有 NULL 归为同一组。这点和 `=` 的行为相反，`group by` 内部把 NULL 视为相等。
> **追问陷阱**：「那 `distinct` 呢」——同理，多个 NULL 只保留一行。

> [!question] 9. 字符串和数字比较，Hive 会怎么处理？
> **一句话答法**：把字符串 cast 成 `double` 再比较。转不动的（如 `'2026-10-01'`）变成 NULL，条件恒不成立。
> **追问陷阱**：「为什么是 double 不是 int」——Hive 的类型提升规则里，string 与数值比较统一提升到 double，这也意味着大整数（超过 2^53）比较会丢精度。

> [!question] 10. 怎么在数仓规范里彻底避免 NULL 和空串的混用？
> **一句话答法**：三道防线——ODS 层原样保留；DWD 层统一 `nullif(trim(x),'')` 把空串转 NULL；建表注释里明确「NULL 表示缺失，空串不允许出现」，并用数据质量规则（非空率、空串率）监控。
> **追问陷阱**：「历史数据怎么办」——一次性刷数 + 加校验，刷数前先在影子表验证行数和金额分布一致。

> [!question] 11. `where` 里 `NULL AND FALSE` 和 `NULL OR TRUE` 分别是什么？
> **一句话答法**：分别是 `FALSE` 和 `TRUE`。这是三值逻辑里两个「短路」特例，其余组合涉及 NULL 都是 `UNKNOWN`。
> **追问陷阱**：面试官可能让你推 `NOT NULL` ——结果是 `UNKNOWN`，不是 `TRUE`。

> [!question] 12. 如果上游把 `dt` 从 `string` 改成 `date`，下游会有什么连锁反应？
> **一句话答法**：三类问题——① 原来 `dt = '2026-10-01'` 仍可跑，但 `dt = '20261001'` 会失败或返回空；② 分区裁剪行为变化；③ 与 `string` 类型的分区路径拼接可能不一致，导致读不到数据。
> **追问陷阱**：「怎么平滑迁移」——双写新旧字段 → 下游逐个切换 → 校验一致后下线旧字段，别一把梭。

## 六、自测题

> [!question] 1.（单选）Hive 中执行 `select nvl('', 'default')`，结果是？
> A. `'default'`
> B. `''`
> C. `NULL`
> D. 报错

> [!question] 2.（单选）表 `t` 有 100 行，`col` 列有 30 个 NULL、10 个空串。`count(col)` 的结果是？
> A. 100
> B. 70
> C. 60
> D. 90

> [!question] 3.（判断）在 Hive 中，`select * from t where dt = 20261001` 如果 `dt` 是 `string` 类型且格式为 `yyyy-MM-dd`，会返回 0 行但不报错。

> [!question] 4.（场景设计）你要统计「每个城市的日均客单价」，`amount` 列有 15% 是 NULL。业务方说「NULL 就是没消费，应该算 0」。请写出 SQL，并说明为什么不能直接用 `avg(amount)`。

> [!question] 5.（场景设计）上游埋点表的 `user_id` 有 3% 是空串 `''`、2% 是 NULL。你要做「活跃用户去重数」，发现结果比预期多了约 3%。请分析原因并给出修复方案，要求修复后口径可解释。

> [!success]- 答案与解析（点击展开）
> **1. B**
> `nvl` 只判断 NULL，空串不是 NULL，原样返回。这是 Hive 与 Oracle 最大的语义差异之一。
>
> **2. C**
> `count(col)` 只数非 NULL 行：100 - 30 = 70。**注意空串算非 NULL**，所以不会被排除——正确答案是 70。
> 若题目问的是「非空且非空串」，则是 60，但 `count(col)` 本身不做空串过滤。
>
> **3. 正确**
> `string` 与 `int` 比较时，Hive 把 `string` cast 成 `double`。`cast('2026-10-01' as double)` 返回 NULL，条件恒为 `UNKNOWN`，`WHERE` 过滤掉所有行 → 0 行，无报错。
>
> **4. 参考 SQL**
> ```sql
> select
>     city,
>     sum(coalesce(amount, 0)) / count(distinct user_id) as arpu,
>     sum(coalesce(amount, 0)) / count(*)                as avg_per_order
> from dwd.order_detail
> where dt between '2026-10-01' and '2026-10-31'
> group by city;
> ```
> **为什么不能直接用 `avg(amount)`**：`avg` 的分母是「`amount` 非 NULL 的行数」，会把 15% 的 NULL 行直接排除在分母外，得到的是「有消费记录的订单均价」，不是「含零消费的客单价」。业务口径要求 NULL 算 0，就必须 `coalesce(amount,0)` 后再算。
> 另外要区分「客单价 = GMV / 下单用户数」还是「GMV / 订单数」，这是两个不同指标，别混。
>
> **5. 原因**
> `count(distinct user_id)` 里，空串 `''` 是一个**合法的非 NULL 值**，所有空串用户被当成**同一个用户**计入一次；NULL 则被 `count(distinct)` 忽略。所以多出来的不是 3% 的用户，而是「空串被算成了 1 个用户」——但如果上游是 `group by user_id` 再 count，空串这一组会额外贡献一行。
> **修复**
> ```sql
> -- 方案一：入仓时清洗（推荐，治本）
> -- DWD 层：nullif(trim(user_id), '') as user_id
>
> -- 方案二：查询时兜底（治标）
> select count(distinct user_id) as uv
> from dwd.user_active
> where nullif(trim(user_id), '') is not null;
> ```
> **口径可解释性**：修复后应能回答「UV = 有有效 user_id 的去重用户数，空串与 NULL 均视为无效」，并把这个定义写进指标字典。
