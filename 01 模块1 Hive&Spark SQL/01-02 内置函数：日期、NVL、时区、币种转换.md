# 01-02 内置函数：日期、NVL、时区、币种转换

> [!abstract] 一句话结论
> 内置函数是数仓日常写得最多的东西，但**真正决定数据对不对的只有三组**：日期截断与加减（跨月、跨年、时区边界）、空值兜底（`nvl` / `coalesce` / `nullif` 三者的语义差别）、金额换算（汇率要用哪天的、精度怎么保）。
> 这一节的目标不是背函数表，而是**建立「口径 → 函数 → 边界」的映射**：同一个指标换个函数写法，结果可能差一个数量级。

---

## 一、心智模型：日期在数仓里的三种「身份」

新手最容易犯的错，是把「日期」当成一个东西。实际上数仓里日期至少有三种身份，混用就会出错：

| 身份 | 存什么 | 典型列 | 正确操作 |
| --- | --- | --- | --- |
| **分区键**（partition key） | 字符串 `yyyy-MM-dd` | `dt` | 只能做字符串比较 / 范围过滤，**不能做函数运算**（会破坏裁剪） |
| **业务时间**（event time） | `timestamp`，带时区语义 | `event_time`、`create_time` | 可以做 `date_trunc`、加减、时区转换 |
| **日历维度**（date dim） | `date` 类型，无时分秒 | `stat_date` | 与维度表 join，做同比环比 |

> [!important] 核心原则
> **分区键永远当字符串用，业务时间永远当 timestamp 用。**
> 需要「按分区键算日期」时，先把常量侧算好再比较（`where dt = date_sub(current_date, 1)` 这种写法要注意：右侧是常量表达式，可以提前求值，裁剪通常还能生效；但 `where dt = date_format(date_sub(current_date,1),'yyyy-MM-dd')` 就更明确）。

---

## 二、核心知识点

### 2.1 日期函数：先分清「截断」和「加减」

**截断类**（把时间归到某个粒度的起点）：

| 需求 | Hive 写法 | Spark 3.x 写法 | 说明 |
| --- | --- | --- | --- |
| 取日期部分 | `to_date(ts)` | `to_date(ts)` | 丢掉时分秒 |
| 取月初 | `trunc(ts, 'MM')` | `trunc(ts, 'MM')` / `date_trunc('MONTH', ts)` | `trunc` 返回 string，`date_trunc` 返回 timestamp |
| 取周一 | `trunc(ts, 'MM')` 不行，用 `date_sub(next_day(ts,'MO'), 7)` | `date_trunc('WEEK', ts)` | Spark 的 `date_trunc('WEEK')` 默认周一为起点 |
| 取小时 | `date_format(ts,'yyyy-MM-dd HH')` | `date_trunc('HOUR', ts)` | 前者返回 string，后者返回 timestamp |
| 格式化成字符串 | `date_format(ts, 'yyyyMMdd')` | `date_format(ts, 'yyyyMMdd')` | 注意格式串大小写：`MM` 是月，`mm` 是分 |

**加减类**：

| 需求 | 写法 | 坑 |
| --- | --- | --- |
| 加减天数 | `date_add(d, n)` / `date_sub(d, n)` | 参数是 `date` 或 `string`，`timestamp` 会先被转成 `date`，**时分秒丢失** |
| 加减月份 | `add_months(d, n)` | 1月31日 + 1个月 = 2月28/29日，**会截断到月末** |
| 加减秒/分/时 | 用 `unix_timestamp` + 算术，或 Spark 的 `ts + interval 1 hour` | Hive 不支持 `interval` 语法（3.x 部分支持），可移植性差 |
| 日期差 | `datediff(end, start)` | 返回天数，**只算日期部分**，不看时分秒 |
| 月份差 | `months_between(end, start)` | 返回 double，如 1.5 表示一个半月 |

> [!warning] `add_months` 的月末陷阱
> `add_months('2026-01-31', 1)` = `2026-02-28`。
> 如果你在算「会员到期日」，1月31日开一个月会员，到期日变成 2月28日，用户少用 3 天。业务上要确认：是「自然月」还是「30 天」。这类问题必须写进需求评审。

> [!warning] `datediff` 忽略时分秒
> `datediff('2026-10-02 00:00:01', '2026-10-01 23:59:59')` = **1**，不是 0。
> 算「停留时长」必须用秒级差值：`unix_timestamp(end) - unix_timestamp(start)`。

### 2.2 空值处理三件套：`nvl` / `coalesce` / `nullif`

这三个函数名字像，语义完全不同，必须分清：

| 函数 | 签名 | 行为 | 典型用途 |
| --- | --- | --- | --- |
| `nvl(a, b)` | 两参数 | `a is null` → 返回 `b`，否则返回 `a` | 单列兜底 |
| `coalesce(a, b, c, ...)` | 多参数 | 返回**第一个非 NULL** 的值 | 多列优先级兜底 |
| `nullif(a, b)` | 两参数 | `a = b` → 返回 `NULL`，否则返回 `a` | **把空串/哨兵值转成 NULL** |

```sql
-- nvl：只能兜一层
select nvl(coupon_amount, 0) from t;

-- coalesce：多级兜底，常用于「取第一个有值的字段」
select coalesce(mobile, phone, backup_phone, '未知') as contact from t;

-- nullif：反向操作，把"假空值"变成真 NULL
select nullif(trim(remark), '') as remark from t;      -- 空串 → NULL
select nullif(status, '-1') as status from t;           -- 哨兵值 → NULL
```

**三者组合的标准清洗模板**（建议直接抄进项目）：

```sql
-- 目标：去空格 → 空串转 NULL → 兜默认值
coalesce(nullif(trim(col), ''), '未知') as col_clean
```

> [!danger] `coalesce` 的隐性性能问题
> `coalesce` 会**依次求值**，如果参数里有子查询或 UDF，可能被重复计算。
> 更隐蔽的是：`coalesce(a, b)` 在 `where` 里可能导致谓词无法下推。生产上如果 `a` 是大表字段、`b` 是常量，优先在子查询里先 `nvl` 好，再做过滤。

**`if` / `case when` 的选择**：

```sql
-- 二选一：用 if，简洁
select if(status = 'DONE', 1, 0) as is_done from t;

-- 多分支：用 case when，可读性好
select
    case
        when amount >= 1000 then '高'
        when amount >= 100  then '中'
        when amount is null then '未知'   -- 必须显式处理 NULL，否则落 else
        else '低'
    end as level
from t;
```

> [!warning] `case when` 的 NULL 陷阱
> `case when amount > 100 then 'A' else 'B' end`，当 `amount is null` 时 `amount > 100` 是 `UNKNOWN`，走 `else` 分支 → 归到 `'B'`。
> 如果业务上「未知」应该单独一类，**必须显式写 `when amount is null then '未知'`，且放在最前面**。

### 2.3 字符串函数：高频 + 易错

| 需求 | 写法 | 坑 |
| --- | --- | --- |
| 拼接 | `concat(a, b, c)` / `concat_ws('-', a, b)` | `concat` 遇 NULL **整体返回 NULL**；`concat_ws` 会**跳过 NULL** |
| 截取 | `substr(s, start, len)` | **start 从 1 开始**（不是 0）；负数表示从末尾数 |
| 长度 | `length(s)` | 返回**字符数**，不是字节数；中文算 1 |
| 字节长度 | `length(encode(s,'UTF-8'))` | 判断是否有中文/特殊字符时用 |
| 去空格 | `trim(s)` / `ltrim` / `rtrim` | 只去**半角空格**，全角空格 `　` 和 `\t` 去不掉 |
| 替换 | `regexp_replace(s, pattern, repl)` | 正则贪婪匹配，注意转义 |
| 分割 | `split(s, ',')` → array | 空串 `split('', ',')` 返回 `[""]`，不是空数组 |
| 取数组元素 | `arr[0]` / `arr[size(arr)-1]` | **下标从 0 开始**（和 `substr` 相反！） |
| 正则提取 | `regexp_extract(s, pattern, group_idx)` | 提取不到返回**空串**，不是 NULL |
| 判断包含 | `instr(s, sub) > 0` / `s like '%x%'` | `like` 前后都通配无法用索引/裁剪 |
| JSON 解析 | `get_json_object(s, '$.key')` | 键不存在返回 NULL；嵌套数组要用 `$[0].key` |

> [!danger] `concat` 遇 NULL 全变 NULL
> ```sql
> select concat('a', null, 'c');        -- NULL
> select concat_ws('-', 'a', null, 'c'); -- 'a-c'
> ```
> 拼接地址、姓名时用 `concat`，只要有一个字段是 NULL，整列变 NULL。**生产统一用 `concat_ws`，或先 `nvl` 每个字段**。

> [!tip] `substr` 从 1 开始，数组从 0 开始
> 这是 SQL 里最容易记混的一对。记法：**字符串是人读的（1 起），数组是程序读的（0 起）**。

### 2.4 时区：数仓里最容易被忽略的「隐形炸弹」

**先建立一个事实**：`timestamp` 在 Hive/Spark 里**不带时区信息**，它只是一个「本地时间」的数值。带时区的是 `timestamp with local time zone`（Hive 有，Spark 支持有限）。

**三种常见时区问题**：

**问题一：数据落库时的时区不一致**

```sql
-- 上游 Java 服务用 System.currentTimeMillis() 写的是 UTC 毫秒
-- 落库时如果直接 from_unixtime(ts/1000)，得到的是「服务器本地时区」的时间
select from_unixtime(1696118400);                       -- 依赖集群时区配置
select from_utc_timestamp(from_unixtime(1696118400), 'Asia/Shanghai');  -- 显式转
```

**问题二：`current_date` / `now()` 依赖集群时区**

集群 `hive.local.timezone` 或 Spark 的 `spark.sql.session.timeZone` 配置不同，同一个任务在不同环境跑出来的「今天」可能差一天。

> [!important] 生产铁律
> **不要用 `current_date` 做分区写入的判断**，除非你确认过集群时区。
> 正确做法：调度系统传入 `dt` 参数，SQL 里用 `${bizdate}` 或 `'${dt}'`，**让时间从外部进来，而不是从数据库里取**。

**问题三：跨时区的业务口径**

跨境电商场景，订单时间要同时保留「用户本地时间」和「平台统一时间（UTC+8）」：

```sql
select
    order_id,
    create_time                                    as local_time,      -- 用户本地时间
    from_utc_timestamp(create_time, 'Asia/Shanghai') as bj_time,      -- 统一到北京时间
    from_utc_timestamp(create_time, 'UTC')            as utc_time      -- 统一到 UTC
from dwd.order;
```

**时区转换函数对照**：

| 函数 | 作用 | 注意 |
| --- | --- | --- |
| `from_utc_timestamp(ts, tz)` | 把 ts 当作 UTC，转成 tz 时区 | 入参被**假定**为 UTC，如果实际是本地时间会算错 |
| `to_utc_timestamp(ts, tz)` | 把 ts 当作 tz 时区，转成 UTC | 与上面互逆 |
| `unix_timestamp(ts, fmt)` | 字符串 → 秒级时间戳 | **按集群时区解释**，跨环境可能差 8 小时 |
| `from_unixtime(sec, fmt)` | 秒级时间戳 → 字符串 | 同上 |

> [!warning] 最阴的一类 bug
> `unix_timestamp('2026-10-01 00:00:00')` 在 UTC 集群返回 `1790812800`，在东八区集群返回 `1790784000`（差 28800 秒 = 8 小时）。
> 如果你的任务在测试集群（UTC）和生产集群（Asia/Shanghai）跑，**同一份数据算出来的日期分区会差一天**。
> 排查方法：`select current_timestamp(), unix_timestamp('2026-10-01 00:00:00')` 在两个环境各跑一次对比。

### 2.5 币种与汇率换算：口径比函数更重要

汇率换算本身是一行乘法，**难的是「用哪天的汇率」**。

**四种汇率口径**（必须先和业务确认）：

| 口径 | 用什么汇率 | 适用场景 | 特点 |
| --- | --- | --- | --- |
| 交易时汇率 | 下单那一刻的汇率 | 财务对账、退款 | 最准，但要存快照 |
| 日终汇率 | 当日 24:00 的汇率 | 日粒度报表 | 同一天所有订单统一 |
| 月度平均汇率 | 当月每日汇率的均值 | 月度经营分析 | 平滑波动，但不可追溯 |
| 固定预算汇率 | 年初定死的汇率 | 预算、KPI 考核 | 可对比性强，但偏离实际 |

> [!important] 核心设计：汇率快照表
> **绝对不要在 SQL 里写死汇率，也不要 join 一张「当前汇率」表**。
> 正确做法是建一张**按日分区的汇率快照表**，每次换算都 join 对应日期的汇率：
> ```sql
> -- dim.exchange_rate_snapshot
> -- dt, from_currency, to_currency, rate
> ```

**标准换算 SQL**：

```sql
-- 把订单金额统一换算成人民币（CNY）
select
    o.order_id,
    o.currency,
    o.amount,
    r.rate,
    cast(o.amount * r.rate as decimal(18,4)) as amount_cny
from dwd.order o
left join dim.exchange_rate_snapshot r
    on  o.currency   = r.from_currency
    and r.to_currency = 'CNY'
    and r.dt          = o.dt          -- 用订单所在日的汇率
;
```

**三个必须处理的边界**：

1. **汇率缺失**：小币种可能某天没汇率 → `left join` 后 `rate` 为 NULL → 金额变 NULL。修复：`coalesce(r.rate, 1)` 或往前找最近一天的汇率（`last_value ... ignore nulls` 或自关联取 `max(dt)`）。
2. **精度**：`amount` 是 `decimal(18,4)`，`rate` 是 `decimal(18,8)`，相乘结果 `decimal(36,12)`，落表要显式 cast，否则可能溢出。
3. **正反向汇率**：表里只存了 `USD→CNY`，要算 `CNY→USD` 得取倒数。取倒数会产生精度损失，**能用正向就别用倒数**。

```sql
-- 兜底：找不到当日汇率时，取最近一次的历史汇率
select
    o.order_id,
    o.amount * coalesce(r.rate, r2.rate) as amount_cny
from dwd.order o
left join dim.exchange_rate_snapshot r
    on o.currency = r.from_currency and r.to_currency = 'CNY' and r.dt = o.dt
left join (
    -- 每个币种最近一次有效汇率
    select from_currency, to_currency, rate
    from (
        select *, row_number() over (partition by from_currency, to_currency order by dt desc) as rn
        from dim.exchange_rate_snapshot
        where rate is not null
    ) t where rn = 1
) r2 on o.currency = r2.from_currency and r2.to_currency = 'CNY'
;
```

## 三、动手实验

### 3.1 日期函数的边界实验

```sql
select
    add_months('2026-01-31', 1)              as m1,        -- 2026-02-28
    add_months('2026-03-31', -1)             as m2,        -- 2026-02-28
    datediff('2026-10-02 00:00:01', '2026-10-01 23:59:59') as d1,  -- 1（不是 0！）
    unix_timestamp('2026-10-02 00:00:01') - unix_timestamp('2026-10-01 23:59:59') as d2,  -- 2 秒
    trunc('2026-10-25', 'MM')                as month_start,   -- 2026-10-01
    date_sub(next_day('2026-10-25','MO'), 7) as week_monday    -- 2026-10-19
;
```

**验证点**：`datediff` 只看日期部分，`unix_timestamp` 差值才是真实秒差。

### 3.2 `concat` vs `concat_ws` 实验

```sql
select
    concat('北京', null, '朝阳')      as c1,   -- NULL
    concat_ws('', '北京', null, '朝阳') as c2,   -- 北京朝阳
    concat_ws('-', '北京', '', '朝阳')  as c3    -- 北京--朝阳（空串不跳过！）
;
```

**验证点**：`concat_ws` 只跳过 NULL，**不跳过空串**。所以空串必须先 `nullif` 掉。

### 3.3 时区实验（在不同集群各跑一次）

```sql
select
    current_timestamp()                          as now_ts,
    unix_timestamp('2026-10-01 00:00:00')        as ts_sec,
    from_unixtime(1790784000)                    as back_to_str,
    from_utc_timestamp('2026-10-01 00:00:00', 'Asia/Shanghai') as utc_to_bj
;
```

**验证点**：`ts_sec` 在不同时区集群结果不同；`from_utc_timestamp` 是显式转换，结果稳定。

### 3.4 汇率换算实验

```sql
drop table if exists tmp.rate_lab;
create table tmp.rate_lab (dt string, from_currency string, to_currency string, rate decimal(18,8));
insert into tmp.rate_lab values
('2026-10-01','USD','CNY',7.10000000),
('2026-10-02','USD','CNY',7.12000000),
('2026-10-01','EUR','CNY',7.80000000);
-- 注意：2026-10-02 没有 EUR，用来验证"汇率缺失"

drop table if exists tmp.order_lab;
create table tmp.order_lab (order_id int, dt string, currency string, amount decimal(18,4));
insert into tmp.order_lab values
(1,'2026-10-01','USD',100.0000),
(2,'2026-10-02','USD',100.0000),
(3,'2026-10-02','EUR',100.0000);   -- 该日无 EUR 汇率

select
    o.order_id, o.dt, o.currency, o.amount, r.rate,
    cast(o.amount * r.rate as decimal(18,4)) as amount_cny
from tmp.order_lab o
left join tmp.rate_lab r
    on o.currency = r.from_currency and r.to_currency = 'CNY' and o.dt = r.dt
order by o.order_id;
```

**预期**：`order_id=3` 的 `rate` 和 `amount_cny` 都是 NULL —— 这就是必须做兜底的原因。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 日期分区差一天 | 集群时区不同，`current_date`/`unix_timestamp` 结果不同 | 两个环境各跑 `select current_timestamp()` 对比 | 时间从调度参数传入，不用 `current_date` |
| 拼出来的地址整列为空 | `concat` 遇 NULL 返回 NULL | `select concat('a',null)` 验证 | 改 `concat_ws` 或先 `nvl` |
| `substr` 取出来少一位 | 误以为下标从 0 开始 | 检查 start 参数 | `substr(s, 1, n)` 才是从头取 |
| 会员到期日少几天 | `add_months` 月末截断 | 用 1月31日测试 | 业务确认「自然月 vs 30天」；必要时按天加 |
| 停留时长算成整数天 | 用 `datediff` 算时长 | 对比 `unix_timestamp` 差值 | 时长用秒级差值，天数才用 `datediff` |
| 金额换算后变 NULL | 汇率表当日无该币种记录 | `left join` 后 `count(rate)` vs `count(*)` | 兜底最近汇率；或标记为「待换算」 |
| 换算金额和财务对不上 | 汇率口径不一致（日终 vs 交易时） | 抽查几笔订单人工核对 | 明确口径并写入指标字典 |
| `case when` 分组少了「未知」 | NULL 走 else 分支被合并 | `group by` 看是否缺一类 | 显式 `when col is null then '未知'` 放最前 |
| 中文长度算错 | `length` 是字符数不是字节数 | `select length('中文'), length(encode('中文','UTF-8'))` | 需要字节长度时显式 `encode` |
| `regexp_extract` 判空失效 | 提取不到返回空串，不是 NULL | `select regexp_extract('abc','(\\d+)',1) = ''` | 用 `nullif(regexp_extract(...), '')` |
| 全角空格去不掉 | `trim` 只去半角空格 | `select length(trim('　a　'))` | `regexp_replace(s, '\\s+', '')` 或显式替换全角 |

## 五、面试追问

> [!question] 1. `nvl`、`coalesce`、`nullif` 有什么区别？
> **一句话答法**：`nvl` 两参数，判 NULL 兜底；`coalesce` 多参数，返回第一个非 NULL；`nullif` 是反向的，把指定值转成 NULL（常用于空串转 NULL）。
> **追问陷阱**：「`nvl` 和 `coalesce` 性能有差异吗」——`coalesce` 参数多时会依次求值，如果参数是复杂表达式会有额外开销；单列兜底用 `nvl` 更直观。

> [!question] 2. 怎么把空串和 NULL 统一处理？
> **一句话答法**：`nullif(trim(col), '')`，把「去空格后为空」的值转成 NULL，再用 `coalesce` 兜默认值。
> **追问陷阱**：「为什么不直接 `nvl`」——Hive 里 `nvl('', 'x')` 返回 `''`，空串不是 NULL，`nvl` 不生效。

> [!question] 3. `datediff` 和 `unix_timestamp` 差值有什么区别？
> **一句话答法**：`datediff` 只比较日期部分，忽略时分秒；`unix_timestamp` 差值才是真实的时间间隔（秒）。
> **追问陷阱**：「算用户停留时长用哪个」——必须用秒级差值，`datediff` 会把 2 秒算成 1 天。

> [!question] 4. `add_months('2026-01-31', 1)` 结果是什么？为什么？
> **一句话答法**：`2026-02-28`。因为 2 月没有 31 日，函数会截断到当月最后一天。
> **追问陷阱**：「这对会员到期日有什么影响」——1月31日买一个月会员，实际只用到2月28日，少 3 天，业务上要确认是「自然月」还是「30天」。

> [!question] 5. 数仓里时区问题一般出在哪几个环节？
> **一句话答法**：三个环节——① 数据接入（上游是 UTC 毫秒还是本地时间）；② 计算（`unix_timestamp`/`current_date` 依赖集群时区）；③ 展示（BI 层再转一次导致重复偏移）。
> **追问陷阱**：「怎么保证跨环境一致」——统一用 UTC 存储，展示层按时区转换；调度参数显式传 `dt`，不依赖 `current_date`。

> [!question] 6. `from_utc_timestamp` 和 `to_utc_timestamp` 分别做什么？
> **一句话答法**：`from_utc_timestamp(ts, tz)` 把 ts 当作 UTC 转成 tz 本地时间；`to_utc_timestamp(ts, tz)` 把 ts 当作 tz 本地时间转成 UTC。
> **追问陷阱**：「如果 ts 本来就是本地时间，用 `from_utc_timestamp` 会怎样」——会多偏移一次，得到错误结果。**必须先确认入参的真实时区**。

> [!question] 7. 汇率换算有哪几种口径？你们生产用哪种？
> **一句话答法**：交易时汇率、日终汇率、月均汇率、固定预算汇率四种。对账用交易时汇率，日报用日终，月度分析可用月均。
> **追问陷阱**：「为什么不能直接在 SQL 里写死汇率」——汇率会变，写死后历史数据无法重算，且违反可追溯原则。必须用按日分区的快照表。

> [!question] 8. 汇率表里某个币种某天缺数据，怎么处理？
> **一句话答法**：三级兜底——当日汇率 → 最近一次历史汇率（`row_number` 取最新）→ 标记为待换算并告警，不要静默填 1。
> **追问陷阱**：「填 1 有什么问题」——会让金额看起来正常但实际错误，比 NULL 更危险，因为下游不会发现。

> [!question] 9. `concat` 和 `concat_ws` 遇到 NULL 分别怎样？
> **一句话答法**：`concat` 只要有一个 NULL 就返回 NULL；`concat_ws` 跳过 NULL 但**不跳过空串**。
> **追问陷阱**：「那空串怎么处理」——先 `nullif(trim(x),'')` 转 NULL，`concat_ws` 才会跳过。

> [!question] 10. `substr` 和数组下标为什么一个从 1 开始一个从 0 开始？
> **一句话答法**：这是 SQL 标准的历史遗留，字符串函数遵循 SQL 标准（1 起），数组/集合遵循编程语言惯例（0 起）。没有统一规律，只能记。
> **追问陷阱**：「`substr('abc', 0, 2)` 返回什么」——Hive 里返回 `'ab'`（0 被当作 1），Spark 里返回 `'a'`（0 表示从开头算但长度算 1）。**跨引擎行为不一致，别依赖**。

> [!question] 11. 金额换算后精度怎么保证？
> **一句话答法**：金额用 `decimal(18,4)`，汇率用 `decimal(18,8)`，相乘结果 `decimal(36,12)`，落表前显式 `cast` 到目标精度，避免隐式截断。
> **追问陷阱**：「四舍五入还是截断」——`cast` 是**截断**，`round` 才是四舍五入。财务口径通常要求 `round` 到分。

> [!question] 12. 如果让你设计一张汇率维表，你会怎么设计？
> **一句话答法**：按日分区（`dt`），字段 `from_currency`、`to_currency`、`rate`、`rate_type`（区分日终/月均）、`update_time`；主键是 `(dt, from_currency, to_currency, rate_type)`；只存正向汇率，需要反向时在应用层取倒数并标注精度损失。
> **追问陷阱**：「为什么要有 `rate_type`」——不同口径的汇率要能同时存在，否则一张表只能服务一种场景。

## 六、自测题

> [!question] 1.（单选）Hive 中 `select concat_ws('-', 'a', null, '', 'd')` 的结果是？
> A. `'a--d'`
> B. `'a-d'`
> C. `NULL`
> D. `'a--d-'`

> [!question] 2.（单选）`datediff('2026-10-02 00:00:01', '2026-10-01 23:59:59')` 的结果是？
> A. 0
> B. 1
> C. 2
> D. NULL

> [!question] 3.（判断）`add_months('2026-01-31', 1)` 返回 `2026-03-03`（顺延到下个月）。

> [!question] 4.（场景设计）跨境电商日报需要「当日 GMV（人民币）」，订单表有 `currency` 和 `amount`（原币），汇率表 `dim.exchange_rate_snapshot` 按日分区。某天 JPY 的汇率缺失。请写出 SQL，并说明如何处理缺失汇率，以及为什么不能 `coalesce(rate, 1)`。

> [!question] 5.（场景设计）数据开发发现同一个任务在测试集群（UTC）和生产集群（Asia/Shanghai）跑出的分区数据量差 1 天。请给出至少 3 个可能原因和对应的排查方法。

> [!success]- 答案与解析（点击展开）
> **1. A**
> `concat_ws` 跳过 NULL（`null`），但**空串 `''` 不跳过**。所以结果是 `a` + `-` + `''` + `-` + `d` = `'a--d'`。
>
> **2. B**
> `datediff` 只比较日期部分：`2026-10-02` vs `2026-10-01`，差 1 天。虽然实际只差 2 秒。
>
> **3. 错误**
> `add_months` 是**截断到目标月最后一天**，返回 `2026-02-28`，不是顺延到 3 月。
>
> **4. 参考 SQL**
> ```sql
> select
>     sum(cast(o.amount * coalesce(r.rate, r2.rate) as decimal(18,4))) as gmv_cny,
>     sum(if(r.rate is null and r2.rate is null, 1, 0))                  as cnt_missing_rate
> from dwd.order o
> left join dim.exchange_rate_snapshot r
>     on o.currency = r.from_currency and r.to_currency = 'CNY'
>    and r.dt = o.dt and r.rate_type = 'EOD'
> left join (
>     select from_currency, to_currency, rate
>     from (
>         select *, row_number() over (partition by from_currency, to_currency order by dt desc) rn
>         from dim.exchange_rate_snapshot
>         where to_currency = 'CNY' and rate is not null and rate_type = 'EOD'
>     ) t where rn = 1
> ) r2 on o.currency = r2.from_currency and r2.to_currency = 'CNY'
> where o.dt = '2026-10-15'
> group by 1;
> ```
> **为什么不能 `coalesce(rate, 1)`**：JPY→CNY 的真实汇率约 0.048，填 1 会让这笔订单的 GMV 放大 20 倍，而且**下游不会发现异常**（金额看起来是个正常数字）。正确做法是「兜底最近汇率 + 单独统计缺失笔数并告警」，让问题可见。
>
> **5. 三个可能原因**
> ① **`current_date` / `now()` 依赖集群时区**：UTC 集群的「今天」比东八区晚 8 小时，凌晨调度时会差一天。排查：两个环境各跑 `select current_timestamp(), current_date()`。
> ② **`unix_timestamp(字符串)` 按集群时区解释**：同一字符串在不同时区返回的时间戳差 28800 秒，落成分区就差一天。排查：`select unix_timestamp('2026-10-01 00:00:00')` 对比。
> ③ **`from_unixtime` 输出依赖时区**：上游存 UTC 秒，下游直接 `from_unixtime` 得到的是集群本地时间。排查：抽一条已知时间的记录，看两端格式化结果。
> ④（补充）**调度参数时区**：调度系统的 `$[yyyy-MM-dd-1]` 按调度服务器时区算，和计算集群时区不一致。
> **统一修复**：所有时间从调度参数传入、统一 UTC 存储、展示层转换。
