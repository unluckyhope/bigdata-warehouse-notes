# 01-06 窗口函数与帧边界

> [!abstract] 一句话结论
> 窗口函数 = **保留明细行**的同时做聚合。它和 `GROUP BY` 的本质区别是：`GROUP BY` 把一组压成一行，窗口函数把「组内的计算结果」贴回每一行。
> 真正决定结果对不对的不是函数名，而是 **`OVER()` 里的三件套**：`PARTITION BY`（怎么分组）、`ORDER BY`（组内怎么排）、**帧（frame）**（取组内的哪一段）。**90% 的窗口函数用错，错在帧上。**

---

## 一、心智模型：窗口是「滑动的取景框」

把每一行想象成站在时间轴上，`OVER()` 定义了一个「取景框」：

```
PARTITION BY city     → 先按城市把人分成几队（队伍之间互不可见）
ORDER BY dt           → 每队内按日期排队
ROWS BETWEEN ...      → 从当前位置往前/往后看多少行

当前行 ▼
┌───┬───┬───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │   帧 = 前 2 行 到 当前行
└───┴───┴───┴───┴───┴───┘
        └───────┘
        取景框（3 行）
```

**三个层次的作用**：

| 子句 | 作用 | 省略时 |
| --- | --- | --- |
| `PARTITION BY` | 把数据分桶，桶间独立计算 | 全表一个桶 |
| `ORDER BY` | 桶内排序，决定「当前行」的位置 | 无序，帧默认是整个分区 |
| 帧（`ROWS`/`RANGE`） | 决定参与计算的行范围 | **有 ORDER BY 时默认 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`**（累计），无 ORDER BY 时默认整个分区 |

> [!danger] 最容易被忽略的默认行为
> `sum(x) over (partition by city order by dt)` **不加帧**时，默认是「从第一行到当前行」的**累计求和**，不是整个分区的总和！
> 想要整个分区的总和，必须写 `over (partition by city)`（不带 order by）或显式 `rows between unbounded preceding and unbounded following`。
> 这个默认值坑过无数人。

## 二、核心知识点

### 2.1 三类窗口函数

| 类别 | 函数 | 特点 |
| --- | --- | --- |
| **聚合类** | `sum` / `count` / `avg` / `max` / `min` | 在窗口内做聚合，结果贴回每行 |
| **排序类** | `row_number` / `rank` / `dense_rank` / `ntile` / `percent_rank` | 必须配合 `ORDER BY` |
| **偏移类** | `lag` / `lead` / `first_value` / `last_value` / `nth_value` | 取当前行前后第 N 行的值 |

### 2.2 三种排序函数的区别（必考）

数据：`[100, 100, 90, 80]`

| 函数 | 结果 | 规则 |
| --- | --- | --- |
| `row_number()` | 1, 2, 3, 4 | **永远连续唯一**，相同值也分先后（顺序不确定） |
| `rank()` | 1, 1, 3, 4 | 相同值同名次，**后续名次跳跃**（跳过 2） |
| `dense_rank()` | 1, 1, 2, 3 | 相同值同名次，**后续名次连续**（不跳） |

```sql
select
    name, score,
    row_number()  over (order by score desc) as rn,
    rank()        over (order by score desc) as rk,
    dense_rank()  over (order by score desc) as drk
from tmp.score_lab;
```

> [!tip] 怎么选
> - **取 TopN 且不关心并列** → `row_number`（结果唯一，不会多出行）
> - **取 TopN 且并列都要** → `rank` 或 `dense_rank`（会多出行）
> - **「第几名」的展示** → `dense_rank`（第 1、1、2 名，符合直觉）
> - **分页/去重** → `row_number`（必须唯一，否则去重不干净）

> [!warning] `row_number` 的「不确定」
> `row_number() over (order by score desc)` 中，两个 100 分的谁排第一是**不确定的**（取决于数据到达顺序）。
> 如果业务要求「分数相同按时间先后」，必须写全排序键：`order by score desc, create_time asc`。
> 生产上去重时**必须保证排序键唯一**，否则每次跑结果不同。

### 2.3 帧（Frame）：本节的核心

帧的语法：

```sql
OVER (
    PARTITION BY ...
    ORDER BY ...
    {ROWS | RANGE} BETWEEN <起点> AND <终点>
)
```

**起点/终点的五种写法**：

| 写法 | 含义 |
| --- | --- |
| `UNBOUNDED PRECEDING` | 分区第一行 |
| `n PRECEDING` | 当前行往前 n 行/单位 |
| `CURRENT ROW` | 当前行 |
| `n FOLLOWING` | 当前行往后 n 行/单位 |
| `UNBOUNDED FOLLOWING` | 分区最后一行 |

**`ROWS` vs `RANGE`（最关键的区别）**：

| | `ROWS` | `RANGE` |
| --- | --- | --- |
| 计数单位 | **物理行数** | **ORDER BY 列的值** |
| 重复值处理 | 每行独立计数 | **相同值的行算同一「位置」，一起纳入** |
| 支持 `n PRECEDING` 吗 | ✅ 任意 n | ⚠️ 仅当 ORDER BY 是数值/日期类型时 |
| 结果确定性 | 高（按行） | 受重复值影响 |

> [!example] 一个例子看懂区别
> 数据（按 `dt` 排序）：
> ```
> dt          amount
> 10-01       100
> 10-02       200
> 10-02       300     ← 和上一行 dt 相同
> 10-03       400
> ```
>
> ```sql
> -- ROWS：严格按"前 1 行"
> sum(amount) over (order by dt rows between 1 preceding and current row)
> -- 结果：100, 300, 500, 700
> --       (100) (100+200) (200+300) (300+400)
>
> -- RANGE：按"dt 值往前 1 个单位"（这里是 1 天）
> sum(amount) over (order by dt range between 1 preceding and current row)
> -- 结果：100, 500, 500, 900
> --       10-02 两行都取 [10-01, 10-02] = 100+200+300 = 500
> --       10-03 取 [10-02, 10-03] = 200+300+400 = 900
> ```
>
> **RANGE 把相同 `dt` 的行当成一个整体**，这正是「按日期累计」的正确语义。

> [!success] 什么时候用 RANGE
> - **累计指标**（YTD、MTD）：`range between unbounded preceding and current row`，保证同一天的多条记录看到相同的累计值
> - **滑动窗口**（近 7 天）：`range between 6 preceding and current row`（日期类型下 = 近 7 天）
> - **移动平均**：同上
>
> **什么时候用 ROWS**
> - **按行取前后 N 条**（如「上一条订单」「下两条记录」）
> - **分页、去重**（配合 `row_number`）
> - **`lag`/`lead` 的默认行为**（本身就是按行偏移）

### 2.4 常用窗口模式速查

| 需求 | 写法 |
| --- | --- |
| 分组累计求和 | `sum(x) over (partition by k order by dt rows between unbounded preceding and current row)` |
| 分组总和（贴到每行） | `sum(x) over (partition by k)` |
| 分组占比 | `x / sum(x) over (partition by k)` |
| 移动平均（近 7 行） | `avg(x) over (partition by k order by dt rows between 6 preceding and current row)` |
| 近 7 天（按日期） | `sum(x) over (partition by k order by dt range between 6 preceding and current row)` |
| 组内排名 | `row_number() over (partition by k order by x desc)` |
| 组内 TopN | 套子查询后 `where rn <= N` |
| 上一行的值 | `lag(x, 1) over (partition by k order by dt)` |
| 环比（与上一行比） | `x - lag(x,1) over (...)` 或 `x / lag(x,1) over (...) - 1` |
| 同比（与去年同期比） | `lag(x, 12) over (partition by k order by month)`（月份连续时可用） |
| 首次出现 | `first_value(x) over (partition by k order by dt)` |
| 最后一次出现 | `last_value(x) over (partition by k order by dt rows between unbounded preceding and unbounded following)` |
| 分组去重（保留最新） | `row_number() over (partition by k order by update_time desc) = 1` |
| 连续登录天数 | `dt - row_number() over (partition by user_id order by dt)` 分组计数 |

> [!danger] `last_value` 的默认帧陷阱
> `last_value(x) over (partition by k order by dt)` 的默认帧是 `RANGE UNBOUNDED PRECEDING AND CURRENT ROW`，也就是「从第一行到当前行」——此时 `last_value` 拿到的就是**当前行自己**，不是分区最后一行！
> **必须显式写** `rows between unbounded preceding and unbounded following` 才能取到真正的最后一行。
> 这是窗口函数里最经典的坑之一，`first_value` 反而没这个问题（因为它取的就是帧的第一行）。

### 2.5 `lag` / `lead` 的细节

```sql
lag(expr, offset, default)  over (partition by k order by dt)
```

- `offset` 默认 1，可以为负（等价于 `lead`）
- `default` 默认 NULL，**建议显式给默认值**，否则边界行参与运算会变 NULL
- `lag` 不看帧，只按 `ORDER BY` 的位置偏移

```sql
-- 环比增长率，边界行给 0 而不是 NULL
select
    dt, gmv,
    lag(gmv, 1, 0) over (order by dt) as prev_gmv,
    case
        when lag(gmv, 1) over (order by dt) is null then null   -- 第一天没有环比
        when lag(gmv, 1) over (order by dt) = 0 then null       -- 分母为 0
        else round((gmv - lag(gmv,1) over (order by dt)) / lag(gmv,1) over (order by dt), 4)
    end as growth_rate
from tmp.daily_gmv;
```

> [!warning] 日期不连续时的 `lag` 陷阱
> `lag` 取的是「上一行」，不是「上一天」。如果数据里 10-03 缺失，10-04 的 `lag` 拿到的是 10-02 的值，你以为是「环比昨天」，实际是「环比前天」。
> **修复**：先补齐日期骨架（用日期维度表 `left join`），再做 `lag`。

```sql
-- 补日期骨架的标准写法
select
    d.dt,
    coalesce(f.gmv, 0) as gmv,
    lag(coalesce(f.gmv, 0)) over (order by d.dt) as prev_gmv
from dim.date d
left join tmp.daily_gmv f on d.dt = f.dt
where d.dt between '2026-10-01' and '2026-10-31';
```

### 2.6 窗口 vs `GROUP BY`：什么时候用哪个

| 场景 | 用 `GROUP BY` | 用窗口 |
| --- | --- | --- |
| 只要汇总结果 | ✅ | 也可以但浪费 |
| 汇总值要贴回明细行 | ❌（需要 join 回去） | ✅ |
| 组内排名 / TopN | ❌ | ✅ |
| 累计 / 环比 / 同比 | ❌ | ✅ |
| 去重取最新 | ❌ | ✅（`row_number`） |

```sql
-- 需求：每个订单的金额 + 该城市的平均金额 + 与平均的差值
-- ❌ 用 group by 要 join 回去
select o.*, c.avg_amt, o.amount - c.avg_amt as diff
from dwd.order o
join (select city, avg(amount) as avg_amt from dwd.order group by city) c on o.city = c.city;

-- ✅ 用窗口一步到位
select
    order_id, city, amount,
    avg(amount) over (partition by city) as avg_amt,
    amount - avg(amount) over (partition by city) as diff
from dwd.order;
```

> [!note] 窗口的代价
> 窗口函数需要对数据按 `PARTITION BY + ORDER BY` 排序，这是一次 **shuffle + sort**，开销不小。
> 如果 `PARTITION BY` 的 key 基数很大（如按 `order_id` 分区），每个分区只有 1~2 行，窗口几乎没有意义但代价很高。
> **判断标准**：分区平均行数 < 10 时，考虑是否真的需要窗口。

### 2.7 高级用法：滑动窗口与去重

**连续 N 天活跃**（经典的「连续登录」问题）：

```sql
-- 思路：日期 - row_number = 常数 → 连续段
select user_id, count(*) as continuous_days
from (
    select user_id, dt,
           date_sub(dt, row_number() over (partition by user_id order by dt)) as grp
    from (select distinct user_id, dt from dwd.user_login) t
) t2
group by user_id, grp
having count(*) >= 3;
```

**原理**：连续日期的 `dt - 序号` 是常数。一旦断档，这个差值就变了，于是可以用它分组。

| user | dt | rn | dt - rn | 组 |
| --- | --- | --- | --- | --- |
| A | 10-01 | 1 | 09-30 | g1 |
| A | 10-02 | 2 | 09-30 | g1 |
| A | 10-03 | 3 | 09-30 | g1 |
| A | 10-05 | 4 | 10-01 | g2 |

**滑动窗口求「近 3 天累计」**：

```sql
select
    dt,
    gmv,
    sum(gmv) over (order by dt range between 2 preceding and current row) as gmv_3d
from tmp.daily_gmv;
```

**去重取最新（最常用的窗口写法）**：

```sql
select * from (
    select *,
           row_number() over (partition by user_id order by update_time desc, id desc) as rn
    from ods.user_snapshot
    where dt = '2026-10-01'
) t where rn = 1;
```

> [!important] 去重的三个要点
> 1. **排序键必须能唯一确定一行**：`order by update_time desc` 如果时间有重复，加 `id desc` 兜底
> 2. **必须限定分区**：`where dt = ...` 否则跨分区去重会拿错数据
> 3. **`rn=1` 要放在外层**：窗口不能直接在 `WHERE` 里用

### 2.8 窗口函数的执行与优化

窗口在物理计划里是一个独立节点（`Window`），通常包含：
1. 按 `PARTITION BY` 做 shuffle（`Exchange hashpartitioning`）
2. 分区内按 `ORDER BY` 排序（`Sort`）
3. 逐行计算窗口值

**优化手段**：

| 问题 | 手段 |
| --- | --- |
| 多个窗口函数用了不同的 `PARTITION BY` | 会触发多次 shuffle，尽量统一 |
| 窗口 key 基数极大 | 考虑是否真需要窗口 |
| 窗口前数据量大 | 先在子查询里过滤/聚合，减少参与窗口的行数 |
| 单分区数据倾斜 | 对 `PARTITION BY` key 加盐（但会破坏语义，慎用） |

```sql
-- ❌ 两个窗口不同分区 → 两次 shuffle
select
    sum(x) over (partition by city order by dt) as a,
    sum(x) over (partition by category order by dt) as b
from t;

-- ✅ 如果能接受，统一分区键，一次 shuffle
```

### 3.1 建表造数（含重复日期，用于验证 ROWS vs RANGE）

```sql
drop table if exists tmp.win_lab;
create table tmp.win_lab (city string, dt string, amount decimal(10,2), user_id bigint);
insert into tmp.win_lab values
('北京','2026-10-01',100.00,1),
('北京','2026-10-02',200.00,1),
('北京','2026-10-02',300.00,2),   -- 与上一行同一天
('北京','2026-10-03',400.00,1),
('上海','2026-10-01',50.00, 3),
('上海','2026-10-02',60.00, 3);
```

### 3.2 实验一：ROWS vs RANGE

```sql
select
    city, dt, amount,
    sum(amount) over (partition by city order by dt
                      rows between 1 preceding and current row)  as rows_sum,
    sum(amount) over (partition by city order by dt
                      range between 1 preceding and current row) as range_sum
from tmp.win_lab
where city = '北京'
order by dt, amount;
```

**预期结果**：

| dt | amount | rows_sum | range_sum |
| --- | --- | --- | --- |
| 10-01 | 100 | 100 | 100 |
| 10-02 | 200 | 300 | 600 |
| 10-02 | 300 | 500 | 600 |
| 10-03 | 400 | 700 | 900 |

**解读**：
- `rows_sum`：严格按物理行，10-02 的第二行取「上一行 200 + 当前 300 = 500」
- `range_sum`：按 dt 值，两行 10-02 都取「10-01 ~ 10-02」的全集 = 100+200+300 = 600

> [!success] 这个实验一定要亲手跑
> 只看文字很难建立直觉，跑一次看到 `500` 和 `600` 的差别，你以后写累计指标就不会再错。

### 3.3 实验二：默认帧的陷阱

```sql
-- 三种写法对比
select
    dt, amount,
    -- A：有 order by 无帧 → 默认累计
    sum(amount) over (partition by city order by dt) as default_sum,
    -- B：无 order by → 整个分区
    sum(amount) over (partition by city) as partition_sum,
    -- C：显式指定整分区
    sum(amount) over (partition by city order by dt
                      rows between unbounded preceding and unbounded following) as explicit_total
from tmp.win_lab
where city = '北京'
order by dt, amount;
```

**预期**：`default_sum` 是累加的 100, 300, 600, 1000；`partition_sum` 和 `explicit_total` 都是 1000。

### 3.4 实验三：`last_value` 的坑

```sql
select
    dt, amount,
    first_value(amount) over (partition by city order by dt) as fv_default,
    last_value(amount)  over (partition by city order by dt) as lv_default,   -- 错！
    last_value(amount)  over (partition by city order by dt
                              rows between unbounded preceding and unbounded following) as lv_fixed
from tmp.win_lab
where city = '北京'
order by dt, amount;
```

**预期**：`lv_default` 每行都等于当前行的 `amount`（因为帧只到当前行），`lv_fixed` 全是最后一行的值。

### 3.6 实验五：连续登录天数

```sql
drop table if exists tmp.login_lab;
create table tmp.login_lab (user_id string, dt string);
insert into tmp.login_lab values
('A','2026-10-01'),('A','2026-10-02'),('A','2026-10-03'),
('A','2026-10-05'),('A','2026-10-06'),
('B','2026-10-01'),('B','2026-10-03');

select user_id, min(dt) as start_dt, max(dt) as end_dt, count(*) as days
from (
    select user_id, dt,
           date_sub(dt, row_number() over (partition by user_id order by dt)) as grp
    from (select distinct user_id, dt from tmp.login_lab) t
) t2
group by user_id, grp
having count(*) >= 2
order by user_id, start_dt;
```

**预期**：A 有两段（10-01~10-03 共 3 天；10-05~10-06 共 2 天），B 没有连续段。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 累计值最后一行 ≠ 总和 | 默认帧是 `UNBOUNDED PRECEDING TO CURRENT ROW` | 对比 `sum over (partition by k)` | 显式写帧或去掉 `order by` |
| `last_value` 拿到当前行 | 默认帧不含后续行 | 单独 select 看结果 | 加 `rows between unbounded preceding and unbounded following` |
| 累计值在重复日期上「跳变」 | 用了 `ROWS` 而非 `RANGE` | 检查是否有重复 `dt` | 累计类指标用 `RANGE` |
| 去重结果每次不同 | `row_number` 的排序键不唯一 | 多次执行对比 | 排序键加唯一列兜底（如 `id`） |
| 环比算错 | 日期不连续，`lag` 取到的是「上一条」不是「昨天」 | 检查日期是否连续 | 补日期骨架后再 `lag` |
| 窗口报错「不能用于 WHERE」 | 窗口在 SELECT 阶段求值 | 报错信息 | 套子查询后过滤 |
| 窗口任务极慢 | 多次 shuffle / 分区数过多 | `explain` 看 `Window` 节点数量 | 统一 `PARTITION BY`；先聚合再开窗 |
| 窗口 OOM | 单分区数据量过大 | 看 `Window` 节点的内存 | 减少分区内行数（先过滤/聚合） |
| TopN 结果多出行 | 用了 `rank`/`dense_rank`，有并列 | 对比 `row_number` 结果 | 按业务选：唯一用 `row_number` |
| 移动平均首尾不对 | 帧的边界没处理 | 检查前 N 行是否不足 | 用 `coalesce` 兜底或标注「数据不足」 |
| 同比算错 | `lag(x, 12)` 依赖月份连续 | 检查月份是否缺 | 用自关联（按 `dt - 1 year`）而非 `lag` |

## 五、面试追问

> [!question] 1. `row_number`、`rank`、`dense_rank` 的区别？
> **一句话答法**：`row_number` 永远连续唯一；`rank` 并列同名次但跳号（1,1,3）；`dense_rank` 并列同名次不跳号（1,1,2）。
> **追问陷阱**：「取 Top10 用哪个」——看业务是否要并列。要并列用 `rank`（可能超过 10 行），不要并列用 `row_number`。

> [!question] 2. 窗口函数的默认帧是什么？
> **一句话答法**：有 `ORDER BY` 时是 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`（累计），没有 `ORDER BY` 时是整个分区。
> **追问陷阱**：「所以 `sum(x) over (order by dt)` 是累计求和？」——是的，很多人误以为是总和。

> [!question] 3. `ROWS` 和 `RANGE` 的区别？
> **一句话答法**：`ROWS` 按物理行数，`RANGE` 按 `ORDER BY` 列的值。有重复值时，`RANGE` 会把相同值的行当成一个整体一起纳入。
> **追问陷阱**：「累计指标该用哪个」——用 `RANGE`，保证同一天的多条记录看到相同的累计值。

> [!question] 4. `last_value` 为什么常常取不到最后一行？
> **一句话答法**：因为默认帧是「到当前行」，`last_value` 取的是帧的最后一行，也就是当前行自己。要加 `rows between unbounded preceding and unbounded following`。
> **追问陷阱**：「`first_value` 有这个问题吗」——没有，它的帧起点就是分区第一行。

> [!question] 5. 怎么用窗口函数去重？
> **一句话答法**：`row_number() over (partition by 去重键 order by 时间 desc) = 1`，套子查询后过滤。
> **追问陷阱**：「排序键有重复怎么办」——加一个唯一列兜底（如自增 id），否则结果不确定。

> [!question] 6. 怎么算连续登录 N 天？
> **一句话答法**：`dt - row_number() over (partition by user order by dt)` 得到的分组标识，连续日期会得到相同值；按这个标识 `group by` 再 `count` 即可。
> **追问陷阱**：「如果一天有多条登录记录呢」——先去重（`select distinct user_id, dt`），否则 `row_number` 会被打乱。

> [!question] 7. 窗口函数和 `GROUP BY` 能同时用吗？顺序是什么？
> **一句话答法**：能。`GROUP BY` 先执行，窗口在聚合结果上计算。所以可以 `rank() over (order by sum(x) desc)`。
> **追问陷阱**：「那能不能对原始行开窗再聚合」——需要子查询：内层开窗，外层聚合。

> [!question] 8. 窗口函数的性能瓶颈在哪？
> **一句话答法**：主要是 shuffle（按 `PARTITION BY` 重分区）和 sort（按 `ORDER BY` 排序）。多个不同 `PARTITION BY` 的窗口会导致多次 shuffle。
> **追问陷阱**：「怎么优化」——统一分区键、先过滤减少行数、避免高基数的 `PARTITION BY`。

> [!question] 9. 环比和同比分别怎么写？
> **一句话答法**：环比用 `lag(x,1)`，同比用 `lag(x,12)`（月粒度）或自关联 `dt - 1 year`。
> **追问陷阱**：「日期不连续会怎样」——`lag` 取的是「上一条记录」不是「上一天」，会算错。必须先补日期骨架。

> [!question] 10. 什么是「窗口帧」？举一个必须显式指定帧的场景。
> **一句话答法**：帧决定窗口参与计算的行范围。必须显式的场景：① `last_value` 取最后一行；② 移动平均（`rows between 6 preceding`）；③ 固定窗口（如只算当前行前后各 1 行）。
> **追问陷阱**：「`range between 6 preceding` 和 `rows between 6 preceding` 在日期上一样吗」——不一样，前者是「近 7 天」（按日期值），后者是「近 7 行」（按记录数）。

> [!question] 11. `ntile` 是什么？用在哪？
> **一句话答法**：把分区内数据按顺序分成 N 桶，返回桶号。常用于分位数分析、AB 实验分桶。
> **追问陷阱**：「`ntile(4)` 和 `percent_rank` 有什么区别」——`ntile` 是等**行数**分桶，`percent_rank` 是等**排名**归一化，数据分布不均时结果不同。

> [!question] 12. 一条 SQL 里写了 5 个窗口函数，会有几次 shuffle？
> **一句话答法**：取决于 `PARTITION BY` 和 `ORDER BY` 的组合。如果 5 个窗口的分区和排序完全一致，优化器会合并成 1 次 shuffle + 1 次 sort；如果分区键不同，就要多次。
> **追问陷阱**：「怎么确认」——看 `explain` 里 `Window` 和 `Exchange` 节点的数量。

## 六、自测题

> [!question] 1.（单选）`sum(x) over (partition by k order by dt)` 在 Hive 中的语义是？
> A. 每个分区的 x 总和
> B. 按 dt 累计求和
> C. 按 dt 排序后取第一行
> D. 报错，必须指定帧

> [!question] 2.（单选）数据按 `dt` 排序为 `[10-01, 10-02, 10-02, 10-03]`，`sum(x) over (order by dt rows between 1 preceding and current row)` 在第三个行（10-02 第二行）的值是？
> A. 10-01 到 10-03 的总和
> B. 前一行 + 当前行
> C. 所有 10-02 的和
> D. 无法确定

> [!question] 3.（判断）`row_number() over (order by score desc)` 在分数相同时，结果一定按数据插入顺序排列。

> [!question] 4.（场景设计）有一张 `dwd.user_order`（user_id, order_id, amount, dt），要计算「每个用户截至每笔订单的累计消费金额」和「该笔订单占该用户总消费的比例」。请写出 SQL，并说明如果误用 `ROWS` 会有什么问题。

> [!question] 5.（场景设计）报表需要「每个品类每天的 GMV、近 7 天累计 GMV、以及该品类当天的排名」。数据量 2 亿行/天，现在跑得很慢。请写出 SQL 并给出至少 2 条优化建议。

> [!success]- 答案与解析（点击展开）
> **1. B**
> 有 `ORDER BY` 时默认帧是 `RANGE UNBOUNDED PRECEDING AND CURRENT ROW`，即从分区第一行累计到当前行 → 累计求和。
>
> **2. B**
> `ROWS` 按物理行，`1 preceding` 就是前一行。第三行取「第二行 + 第三行」，即两个 10-02 的 x 之和。
> （如果用 `RANGE`，第三行会取「10-01 到 10-02」的全部，即前三行。）
>
> **3. 错误**
> 分数相同时 `row_number` 的先后**不确定**，取决于数据在分区内的物理顺序（受 shuffle、文件切分影响），不保证等于插入顺序。
> 要保证顺序必须加第二排序键。
>
> **4. 参考 SQL**
> ```sql
> select
>     user_id, order_id, amount, dt,
>     sum(amount) over (
>         partition by user_id
>         order by dt
>         rows between unbounded preceding and current row
>     ) as cum_amount,
>     amount / sum(amount) over (partition by user_id) as ratio
> from dwd.user_order;
> ```
> **误用 `ROWS` 的问题**：如果同一个用户同一天有多笔订单，`ROWS` 会让这几笔订单的累计值不同（按行逐个累加），而业务上「截至当天」的累计应该相同。
> 正确做法是用 `RANGE`：
> ```sql
> sum(amount) over (partition by user_id order by dt
>                   range between unbounded preceding and current row) as cum_amount_by_day
> ```
> 这样同一天的多笔订单看到相同的「截至当天累计」。
> **注意**：如果业务要的是「截至这笔订单」（逐笔累加），那 `ROWS` 反而是对的。**取决于口径，必须问清楚**。
>
> **5. 参考 SQL**
> ```sql
> select
>     dt, category, gmv,
>     sum(gmv) over (
>         partition by category
>         order by dt
>         range between 6 preceding and current row
>     ) as gmv_7d,
>     rank() over (partition by dt order by gmv desc) as rk
> from (
>     -- 关键：先聚合到 (dt, category) 粒度，再做窗口
>     select dt, category, sum(amount) as gmv
>     from dwd.order_item
>     where dt between '2026-10-01' and '2026-10-31'
>     group by dt, category
> ) t;
> ```
> **优化建议**
> ① **先聚合再开窗**：2 亿行明细直接开窗代价极高。先 `group by dt, category` 压到「天数 × 品类数」（可能只有几千行），再开窗，数据量差 5~6 个数量级。
> ② **用 `RANGE` 而非 `ROWS`**：`range between 6 preceding` 在日期类型上表示「近 7 天」，语义正确；`rows between 6 preceding` 是「前 6 行」，如果某天缺数据就变成「近 7 个有数据的天」，口径错。
> ③ **两个窗口的 `PARTITION BY` 不同**（一个按 category，一个按 dt），会导致两次 shuffle。但因为数据已被聚合到很小，代价可接受。如果还嫌慢，可以拆成两个子查询分别计算再 join。
> ④ **确保日期连续**：`RANGE` 依赖日期值，如果中间缺天，`range 6 preceding` 仍然只取 7 天内的数据（不会因为缺天而少算），这点比 `ROWS` 安全。
