# 01-03 SQL 执行顺序与常见误区

> [!abstract] 一句话结论
> SQL 的**书写顺序**和**执行顺序**不是一回事。执行顺序是 `FROM → ON → JOIN → WHERE → GROUP BY → HAVING → 窗口 → SELECT → DISTINCT → ORDER BY → LIMIT`，这条链路决定了三件事：**别名在哪里能用、过滤条件放在哪里才生效、`WHERE` 为什么不能过滤聚合结果**。
> 把这条链路背下来，80% 的「为什么结果不对」和「为什么这么慢」都能自己推出来。

---

## 一、心智模型：一条 SQL 的「流水线」

把 SQL 想象成工厂流水线，数据是流水线上的半成品，每个环节只做一件事，做完交给下一环：

```
① FROM / JOIN      取表、做笛卡尔积（先形成"大宽表"）
② ON               在宽表上按连接条件筛掉不匹配的行
③ WHERE            行级过滤（此时还没有分组、没有聚合）
④ GROUP BY         按 key 分桶
⑤ HAVING           对"桶"（分组）做过滤
⑥ 窗口函数         在每个桶内/全局做排序、累计（OVER 里的 PARTITION BY 是独立分桶）
⑦ SELECT           计算输出列、起别名
⑧ DISTINCT         对结果去重
⑨ ORDER BY         全局排序
⑩ LIMIT            截断
```

> [!important] 记住三句话
> 1. **`WHERE` 比 `GROUP BY` 早**，所以 `WHERE` 里不能用聚合函数，也不能用 `SELECT` 里起的别名。
> 2. **`SELECT` 比 `ORDER BY` 早**，所以 `ORDER BY` 里**可以**用别名。
> 3. **窗口函数在 `SELECT` 阶段才求值**，所以它不能出现在 `WHERE` 里，只能包一层子查询再用 `WHERE` 过滤。

## 二、核心知识点

### 2.1 完整执行顺序表（背这张表）

| 序号 | 阶段 | 做什么 | 此时可见的名字 |
| --- | --- | --- | --- |
| 1 | `FROM` | 确定数据源，加载表 / 子查询 / CTE | 表名、表别名 |
| 2 | `ON` | join 的连接条件 | 两表的列 |
| 3 | `JOIN` | 按 ON 结果合并（含 outer join 补 NULL） | 两表的列 |
| 4 | `WHERE` | 行级过滤 | **不能用 SELECT 别名，不能用聚合函数** |
| 5 | `GROUP BY` | 分组 | 可用列名、可用位置序号（部分引擎） |
| 6 | `HAVING` | 分组后过滤 | **可用聚合函数，不能用 SELECT 别名**（Hive 部分版本支持） |
| 7 | 窗口函数 | `OVER()` 计算 | 在 SELECT 列表里求值 |
| 8 | `SELECT` | 投影、计算、起别名 | 别名在这里诞生 |
| 9 | `DISTINCT` | 去重 | |
| 10 | `ORDER BY` | 排序 | **可以用 SELECT 别名** |
| 11 | `LIMIT` | 截断 | |

> [!note] 为什么 `ORDER BY` 能用别名，`WHERE` 不能
> 因为别名是第 8 步（SELECT）才产生的。`WHERE` 在第 4 步执行时，别名还不存在。
> `ORDER BY` 在第 10 步，此时 SELECT 已经算完，别名可用。

### 2.2 误区一：`WHERE` 里用聚合函数

```sql
-- ❌ 报错：WHERE 阶段还没有分组，哪来的 sum
select dept, sum(salary)
from emp
where sum(salary) > 10000
group by dept;

-- ✅ 正确：用 HAVING 过滤分组结果
select dept, sum(salary)
from emp
group by dept
having sum(salary) > 10000;
```

**为什么这样设计**：`WHERE` 是「行级过滤」，它的输入是原始行，输出也是原始行（只是少了些行）；`HAVING` 是「组级过滤」，输入是分组后的聚合结果。两者作用对象不同，不能互换。

> [!tip] 性能上不是「能跑就行」
> `WHERE` 先执行，能提前把数据量降下来；`HAVING` 后执行，是在聚合完之后才过滤。
> 所以**能放 `WHERE` 的条件绝不要放 `HAVING`**：
> ```sql
> -- 好：先在 WHERE 砍掉 90% 数据，再聚合
> select dept, sum(salary) from emp
> where dt = '2026-10-01' and status = 'ACTIVE'
> group by dept having sum(salary) > 10000;
>
> -- 差：先把全量数据聚合，再过滤
> select dept, sum(salary) from emp
> group by dept having sum(salary) > 10000 and max(dt) = '2026-10-01';
> ```

### 2.3 误区二：`WHERE` 里用 SELECT 别名

```sql
-- ❌ 大部分引擎报错：WHERE 阶段别名还不存在
select amount * 1.1 as amount_with_tax
from orders
where amount_with_tax > 100;

-- ✅ 方案一：重复写表达式（推荐，无额外开销）
select amount * 1.1 as amount_with_tax
from orders
where amount * 1.1 > 100;

-- ✅ 方案二：套一层子查询
select * from (
    select amount * 1.1 as amount_with_tax from orders
) t where amount_with_tax > 100;
```

> [!warning] 例外：MySQL 允许 WHERE 用别名
> MySQL 的优化器做了特殊处理，`WHERE` 里能用别名。但 **Hive / Spark / Presto 都不行**。
> 在 MySQL 上写的 SQL 迁到 Hive 会直接报错，这是跨库迁移的高频坑。

### 2.4 误区三：`GROUP BY` 后 `SELECT` 非聚合列

```sql
-- 标准 SQL：报错（dept 不在 group by 里）
select dept, name, sum(salary)
from emp
group by dept;

-- Hive 默认行为：能跑！但结果是"随机取一行"的 name
-- 因为 Hive 默认 hive.groupby.orderby.position.alias / 非标准 group by 是宽松模式
```

> [!danger] Hive 的「宽松模式」是数据事故源头
> Hive 默认允许 `SELECT` 非 `GROUP BY` 列，取值是**该组内任意一行的值**，不确定、不可复现。
> 生产建议：设置 `set hive.groupby.skewindata=false;` 之外，更重要的是**开启严格模式**：
> ```sql
> set hive.mapred.mode = strict;   -- Hive 2.x
> set hive.strict.checks.cartesian.product = true;
> ```
> Spark 3.x 默认就会报错（`AnalysisException`），这是 Spark 比 Hive 更安全的地方。

### 2.5 误区四：`LEFT JOIN` 的过滤条件放错位置

这是**最高频的丢数事故**，值得单独拎出来：

```sql
-- 场景：左表是全部用户，右表是订单，想统计"每个用户的已完成订单数"
-- 但只想要 2026-10 月的订单

-- ❌ 错误写法：把右表的过滤条件放在 WHERE
select u.user_id, count(o.order_id) as cnt
from dim.user u
left join dwd.order o on u.user_id = o.user_id
where o.dt = '2026-10-01'          -- 这一行把 left join 变成了 inner join！
group by u.user_id;

-- ✅ 正确写法：右表过滤条件放在 ON
select u.user_id, count(o.order_id) as cnt
from dim.user u
left join dwd.order o
    on u.user_id = o.user_id
   and o.dt = '2026-10-01'         -- 放在 ON 里，不匹配的补 NULL
group by u.user_id;
```

**为什么**：

- `ON` 在第 2-3 步执行，决定「哪些右表行能匹配上」，匹配不上的右表列补 NULL。
- `WHERE` 在第 4 步执行，此时 `o.dt` 已经是 NULL（对没匹配上的行），`NULL = '2026-10-01'` 是 `UNKNOWN` → **这些行被过滤掉** → left join 退化成 inner join。

**口诀**：**左表的过滤条件放 `WHERE`，右表的过滤条件放 `ON`。**

| 想要的效果 | 条件放哪 |
| --- | --- |
| 保留左表全部行，右表只匹配满足条件的 | `ON` |
| 只要「左右都满足条件」的行（等价 inner join） | `WHERE` |
| 过滤左表本身（如只要活跃用户） | `WHERE` |

### 2.6 误区五：窗口函数不能直接过滤

```sql
-- ❌ 报错：窗口函数在 SELECT 阶段才求值，WHERE 时还没有 rn
select user_id, order_id, row_number() over (partition by user_id order by amount desc) as rn
from dwd.order
where rn = 1;

-- ✅ 套一层子查询
select * from (
    select user_id, order_id,
           row_number() over (partition by user_id order by amount desc) as rn
    from dwd.order
) t
where rn = 1;
```

> [!note] 为什么不能「顺便」在 WHERE 里算
> 窗口函数的语义是「在结果集上开窗」，它需要先知道完整的行集合（分组、排序）。`WHERE` 还没筛完，窗口无从谈起。这是**语义限制**，不是优化器的懒。

### 2.7 误区六：`DISTINCT` 和 `GROUP BY` 混用导致语义错乱

```sql
-- 想统计"有多少个不同的部门有员工"
select count(distinct dept) from emp;              -- ✅ 5

-- 想统计"每个部门有多少个不同职位"
select dept, count(distinct job) from emp group by dept;   -- ✅

-- ❌ 危险：distinct 作用在整行上，不是单列
select distinct dept, job from emp;   -- 去重的是 (dept, job) 组合，不是 dept
```

> [!warning] `count(distinct a, b)` 的行为
> Hive 支持多列 `count(distinct a, b)`，语义是「(a,b) 组合的去重数」。
> 但**不支持** `count(distinct a), count(distinct b)` 在同一层同时算多个 —— 会导致多次 shuffle，性能极差。生产上常用 `size(collect_set(a))` 或先 `group by` 再聚合来优化。

### 2.8 误区七：`UNION` 的列顺序和类型

```sql
-- UNION 按"位置"对齐，不是按列名
select user_id, amount from t1     -- 第1列 user_id，第2列 amount
union all
select amount, user_id from t2;    -- 位置反了！类型还恰好兼容 → 静默错误
```

**规则**：
- `UNION ALL`：按**位置**合并，列名取第一个查询的
- `UNION`：合并后**去重**（等价 `UNION ALL` + `DISTINCT`），有额外 shuffle 开销
- 类型不一致时按「宽类型」提升，`string` + `int` → `string`（或 `double`，看引擎）

> [!tip] 生产规范
> `UNION ALL` 每个分支都显式写列名，且顺序一致；类型不一致时显式 `cast`。不要依赖隐式提升。

### 2.9 执行顺序如何影响「慢」

理解执行顺序，就能理解优化器在做什么：

| 优化手段 | 发生在哪一步 | 依赖什么 |
| --- | --- | --- |
| 分区裁剪 | FROM 之前（逻辑优化） | 分区列上有常量比较 |
| 谓词下推（Predicate Pushdown） | 把 WHERE 条件下推到 FROM 里 | 条件不依赖聚合/窗口 |
| 列裁剪 | SELECT 之前 | 只读用到的列 |
| Map 端聚合（Map-side Aggregation） | GROUP BY 之前 | 聚合函数可分解（sum/count/max） |
| Join 重排序 | JOIN 阶段 | 小表能广播 |
| Limit 下推 | 尽量早 | 无排序、无聚合 |

> [!example] 一个真实例子：为什么加了 `WHERE` 反而更慢
> ```sql
> -- 原 SQL：走分区裁剪，扫 1 天
> select count(*) from dwd.order where dt = '2026-10-01';
>
> -- 改后：分区裁剪失效，扫全表
> select count(*) from dwd.order where date_format(dt,'yyyy-MM-dd') = '2026-10-01';
> ```
> 第二句在 `WHERE` 阶段多了个函数调用，看似只是多算一次，实际上**优化器无法把 `date_format(dt,...)` 反推成分区范围**，于是 FROM 阶段就退化成全表扫描。慢的根因在**第 1 步**，不在 `WHERE` 那一步。

### 2.10 一个完整的推导练习

给你一条 SQL，按执行顺序拆解：

```sql
select
    u.city,
    count(distinct o.order_id) as order_cnt,
    sum(o.amount)              as gmv,
    rank() over (order by sum(o.amount) desc) as rk
from dim.user u
left join dwd.order o
    on u.user_id = o.user_id
   and o.dt between '2026-10-01' and '2026-10-31'
where u.status = 'ACTIVE'
group by u.city
having sum(o.amount) > 10000
order by gmv desc
limit 10;
```

**逐步拆解**：

| 步骤 | 发生什么 | 注意点 |
| --- | --- | --- |
| FROM | 加载 `dim.user` 和 `dwd.order` | `dwd.order` 走分区裁剪（`dt` 范围在 ON 里，但优化器能下推到扫描） |
| ON + JOIN | 按 user_id 关联，右表只保留 10 月订单 | 条件在 ON 里 → left join 语义保持 |
| WHERE | 过滤 `u.status='ACTIVE'` | 左表条件，放 WHERE 正确 |
| GROUP BY | 按 city 分组 | |
| HAVING | 过滤 `sum(amount) > 10000` | 此时已聚合 |
| 窗口 | `rank() over (order by sum(amount) desc)` | 窗口在聚合**之后**，所以能对 `sum` 开窗 |
| SELECT | 输出 city / order_cnt / gmv / rk | `gmv` 别名在这里诞生 |
| ORDER BY | `order by gmv desc` | 能用别名 |
| LIMIT | 取前 10 | |

> [!success] 一个反直觉的点
> `rank() over (order by sum(o.amount) desc)` 是合法的——因为窗口函数在 `GROUP BY` 之后执行，此时 `sum(o.amount)` 已经是「每组一个值」，可以对它排序。
> 但如果写成 `rank() over (order by o.amount desc)`，语义就变成「对原始行排序」，和分组结果对不上，引擎可能报错或给出意外结果。

## 三、动手实验

### 3.1 实验一：验证 `WHERE` 早于 `SELECT`

```sql
drop table if exists tmp.order_lab;
create table tmp.order_lab (order_id int, amount decimal(10,2), dt string);
insert into tmp.order_lab values
(1, 50.00, '2026-10-01'),
(2, 150.00, '2026-10-01'),
(3, 200.00, '2026-10-02');

-- ❌ 报错（Hive/Spark）：Invalid table alias or column reference 'amount_with_tax'
select amount * 1.1 as amount_with_tax
from tmp.order_lab
where amount_with_tax > 100;

-- ✅ 正确
select amount * 1.1 as amount_with_tax
from tmp.order_lab
where amount * 1.1 > 100;
```

**验证点**：报错信息本身就说明「别名在 WHERE 阶段不存在」。

### 3.2 实验二：验证 left join 条件位置

```sql
drop table if exists tmp.user_lab;
create table tmp.user_lab (user_id int, name string);
insert into tmp.user_lab values (1,'A'),(2,'B'),(3,'C');

drop table if exists tmp.order_lab2;
create table tmp.order_lab2 (order_id int, user_id int, amount decimal(10,2), dt string);
insert into tmp.order_lab2 values
(101, 1, 100.00, '2026-10-01'),
(102, 1, 200.00, '2026-11-01'),   -- 11 月，应该被排除
(103, 2, 300.00, '2026-10-05');

-- ❌ 错误：WHERE 过滤右表 → 退化成 inner join，user 3 消失
select u.user_id, u.name, count(o.order_id) as cnt
from tmp.user_lab u
left join tmp.order_lab2 o on u.user_id = o.user_id
where o.dt like '2026-10%'
group by u.user_id, u.name
order by u.user_id;
-- 结果：只有 user 1（cnt=1）、user 2（cnt=1），user 3 丢失

-- ✅ 正确：条件放 ON，user 3 保留，cnt=0
select u.user_id, u.name, count(o.order_id) as cnt
from tmp.user_lab u
left join tmp.order_lab2 o
    on u.user_id = o.user_id
   and o.dt like '2026-10%'
group by u.user_id, u.name
order by u.user_id;
-- 结果：user 1（1）、user 2（1）、user 3（0）
```

**验证点**：两种写法的行数差 1 行，且错误写法丢的正是「没有匹配订单的用户」——这类用户往往是最需要关注的（流失用户）。

### 3.3 实验三：看执行计划验证「窗口在聚合之后」

```sql
explain extended
select city, sum(amount) as gmv,
       rank() over (order by sum(amount) desc) as rk
from tmp.order_lab
group by city;
```

**看什么**：在 Spark 的物理计划里，`Window` 节点一定出现在 `HashAggregate` 之后。如果顺序反了，说明写法有问题。

### 3.4 实验四：`HAVING` vs `WHERE` 的性能差

```sql
-- 造一张大一点的表（用现有表自关联放大）
drop table if exists tmp.big_lab;
create table tmp.big_lab as
select a.order_id * 1000 + b.order_id as id,
       a.amount,
       a.dt
from tmp.order_lab a cross join tmp.order_lab b;

-- A：先过滤再聚合（快）
select dt, sum(amount) from tmp.big_lab
where dt = '2026-10-01'
group by dt;

-- B：先聚合再过滤（慢）
select dt, sum(amount) from tmp.big_lab
group by dt
having dt = '2026-10-01';
```

**看什么**：B 的 `input size` 更大（虽然优化器可能会把 `having dt=...` 下推成 `where`，但**不是所有条件都能下推**，比如 `having sum(x)>100`）。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| `left join` 后左表行数变少 | 右表过滤条件写在 `WHERE`，退化成 inner join | 对比 `left join` 前后 `count(*)` | 右表条件移到 `ON` |
| `where` 用别名报错 | 别名在 SELECT 阶段才产生 | 看报错信息 | 重复写表达式或套子查询 |
| `where sum(x) > 0` 报错 | WHERE 早于 GROUP BY | 报错提示 aggregate not allowed | 改用 `HAVING` |
| 分组后某些列值「随机」 | Hive 宽松模式允许非聚合列 | 对比多次执行结果是否一致 | 补全 `GROUP BY` 列；开严格模式 |
| 加了过滤条件反而更慢 | 条件包了函数，导致裁剪/下推失效 | `explain` 看是否有 `PartitionFilters` | 条件改写为裸列比较 |
| `UNION` 结果列错位 | 按位置对齐，两分支列顺序不一致 | 逐列比对 | 显式写列名且顺序一致 |
| `rank()` 过滤报错 | 窗口函数不能出现在 WHERE | 报错提示 window function not allowed | 套子查询后过滤 |
| `order by` 别名能用但 `group by` 不能 | 执行顺序不同 | — | `GROUP BY` 用原始列名或位置序号 |
| `having` 里用别名，Hive 能跑 Spark 报错 | 各引擎对 HAVING 别名支持不同 | 跨引擎测试 | 统一用聚合表达式，不用别名 |
| 同一条 SQL 在 MySQL 能跑 Hive 报错 | MySQL 放宽了 WHERE 别名限制 | — | 按标准 SQL 写，别依赖方言 |

## 五、面试追问

> [!question] 1. 说出 SQL 的完整执行顺序。
> **一句话答法**：`FROM → ON → JOIN → WHERE → GROUP BY → HAVING → 窗口函数 → SELECT → DISTINCT → ORDER BY → LIMIT`。
> **追问陷阱**：「为什么 SELECT 在 GROUP BY 之后」——因为要先分组才能算聚合值，SELECT 里的 `sum()` 依赖分组结果。

> [!question] 2. 为什么 `WHERE` 不能用聚合函数？
> **一句话答法**：`WHERE` 是行级过滤，执行时还没有分组，聚合值不存在；过滤聚合结果要用 `HAVING`。
> **追问陷阱**：「那 `WHERE count(*) > 1` 换个写法能实现吗」——需要子查询：先 `GROUP BY ... HAVING`，再在外层过滤。

> [!question] 3. `ORDER BY` 能用别名，`WHERE` 为什么不能？
> **一句话答法**：别名在 SELECT 阶段（第 8 步）才产生，`WHERE`（第 4 步）执行时别名还不存在；`ORDER BY`（第 10 步）在 SELECT 之后，所以能用。
> **追问陷阱**：「MySQL 为什么能用」——MySQL 优化器做了特殊处理，不是标准行为，迁到 Hive 会报错。

> [!question] 4. `LEFT JOIN` 中右表的过滤条件放 `ON` 和 `WHERE` 有什么区别？
> **一句话答法**：放 `ON` 保留左表全部行（不匹配补 NULL）；放 `WHERE` 会把 NULL 行过滤掉，left join 退化成 inner join。
> **追问陷阱**：「那左表的过滤条件呢」——左表条件放 `WHERE` 是对的，因为左表本来就要全保留的语义已经被打破了（你要筛左表）。

> [!question] 5. `HAVING` 和 `WHERE` 性能上有区别吗？
> **一句话答法**：有。`WHERE` 先执行，能提前减少参与聚合的数据量；`HAVING` 后执行，是对聚合结果过滤。能放 `WHERE` 的条件不要放 `HAVING`。
> **追问陷阱**：「优化器不会自动下推吗」——简单的 `having dt='x'` 可能被下推，但 `having sum(x)>100` 这种依赖聚合的无法下推。

> [!question] 6. 窗口函数为什么不能在 `WHERE` 里用？
> **一句话答法**：窗口函数在 SELECT 阶段求值，需要完整的行集合（分组+排序）才能算；`WHERE` 执行时行还没筛完，窗口无从计算。这是语义限制。
> **追问陷阱**：「那 `QUALIFY` 是什么」——部分引擎（Snowflake、Spark 3.4+ 支持有限）提供 `QUALIFY` 子句专门过滤窗口结果，但 Hive 不支持，跨引擎不可移植。

> [!question] 7. `DISTINCT` 在哪个阶段执行？和 `GROUP BY` 什么关系？
> **一句话答法**：`DISTINCT` 在 SELECT 之后、ORDER BY 之前执行。语义上 `SELECT DISTINCT a, b` 等价于 `GROUP BY a, b`，但 `DISTINCT` 是对整行去重，`GROUP BY` 可以配合聚合函数。
> **追问陷阱**：「性能上哪个好」——现代优化器里两者执行计划几乎一致，但 `GROUP BY` 可读性和扩展性更好（能加聚合列）。

> [!question] 8. 为什么 `count(distinct a), count(distinct b)` 一起写会慢？
> **一句话答法**：每个 `distinct` 需要独立 shuffle 去重，多个 `distinct` 会导致多次 shuffle 或单次 shuffle 的数据膨胀。
> **追问陷阱**：「怎么优化」——用 `size(collect_set(a))` 一次聚合，或先 `group by` 再在外层 `count`。

> [!question] 9. `UNION` 和 `UNION ALL` 的区别，什么时候用哪个？
> **一句话答法**：`UNION` 合并后去重（有 shuffle 开销），`UNION ALL` 直接拼接。**能确定无重复就用 `UNION ALL`**，性能差一个量级。
> **追问陷阱**：「`UNION` 去重是按列名还是按位置」——按位置，列名取第一个查询的。

> [!question] 10. 一条 SQL 变慢了，你会按什么顺序排查？
> **一句话答法**：先看执行计划找瓶颈节点（Scan / Join / Aggregate / Exchange），再看数据量变化（分区数、行数）、数据倾斜（某些 task 特别慢）、参数配置（并行度、内存）。
> **追问陷阱**：「如果执行计划里 Exchange 特别多」——说明 shuffle 多，要检查 join key 是否合理、能否用 broadcast、能否提前聚合。

> [!question] 11. `GROUP BY` 里的数字（如 `group by 1, 2`）是什么意思？能用吗？
> **一句话答法**：表示按 SELECT 列表的第 1、2 个列分组。能用但不推荐，因为列顺序一变语义就错，且不是所有引擎都支持。
> **追问陷阱**：「`ORDER BY 1` 呢」——同理，表示按第一个输出列排序，比 `GROUP BY` 数字更常见，但仍有可读性问题。

> [!question] 12. 子查询在哪个阶段执行？相关子查询和非相关子查询有什么区别？
> **一句话答法**：非相关子查询（不引用外层列）可以被优化器**提前求值一次**；相关子查询（引用外层列）需要对每行执行一次，性能极差，通常会被改写成 join。
> **追问陷阱**：「举一个相关子查询被改写的例子」——`where x > (select avg(x) from t2 where t2.k = t1.k)` 会被改写成 join + 窗口/聚合。

## 六、自测题

> [!question] 1.（单选）下面哪个子句的执行顺序最靠前？
> A. `WHERE`
> B. `GROUP BY`
> C. `HAVING`
> D. `ORDER BY`

> [!question] 2.（单选）`SELECT a+b AS c FROM t WHERE c > 10` 在 Hive 中会？
> A. 正常执行
> B. 报错：找不到列 c
> C. 返回空结果
> D. 返回全表

> [!question] 3.（判断）`LEFT JOIN` 中把右表的 `WHERE` 条件移到 `ON` 里，结果行数一定不会减少。

> [!question] 4.（场景设计）你要统计「每个城市 10 月的 GMV，且只统计有订单的城市」。现有 `dim.city`（全部城市）和 `dwd.order`（订单）。请分别写出「保留无订单城市」和「只保留有订单城市」两个版本，并说明关键差异在哪一行。

> [!question] 5.（场景设计）同事写了一条 SQL，跑出来比预期慢 10 倍：
> ```sql
> select city, count(*) from dwd.order
> where substr(dt, 1, 7) = '2026-10'
> group by city
> having count(*) > 100;
> ```
> 请指出慢的原因，给出改写版本，并说明改写后执行计划会有什么变化。

> [!success]- 答案与解析（点击展开）
> **1. A**
> 顺序是 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`，`WHERE` 最靠前。
>
> **2. B**
> `WHERE` 执行时别名 `c` 还不存在（别名在 SELECT 阶段产生），Hive/Spark 都会报 `Invalid table alias or column reference`。MySQL 能跑，但那是方言。
>
> **3. 正确**
> 移到 `ON` 后，不满足条件的右表行只是「不匹配」，左表行仍然保留（右表列补 NULL）。行数要么不变，要么变多（如果原来有被 WHERE 过滤掉的行），**不会减少**。
>
> **4. 参考 SQL**
> ```sql
> -- 版本一：保留无订单城市（left join + 右表条件在 ON）
> select c.city, coalesce(sum(o.amount), 0) as gmv
> from dim.city c
> left join dwd.order o
>     on c.city_id = o.city_id
>    and o.dt between '2026-10-01' and '2026-10-31'
> group by c.city;
>
> -- 版本二：只保留有订单城市（inner join 或 left join + 右表条件在 WHERE）
> select c.city, sum(o.amount) as gmv
> from dim.city c
> join dwd.order o
>     on c.city_id = o.city_id
> where o.dt between '2026-10-01' and '2026-10-31'
> group by c.city;
> ```
> **关键差异**：版本一把 `o.dt` 条件放在 `ON`，无订单城市保留且 `gmv=0`；版本二用 `join`（或把条件放 `WHERE`），无订单城市被排除。
> **注意**：版本一里 `coalesce(sum(o.amount), 0)` 是必须的——没有订单的城市 `sum` 返回 NULL，不兜底会显示空而不是 0。
>
> **5. 原因**
> `substr(dt,1,7) = '2026-10'` 把分区列 `dt` 包在了函数里，**分区裁剪失效**，引擎会扫描整张表（可能 3 年数据），而预期只扫 1 个月。
> **改写**
> ```sql
> select city, count(*) as cnt
> from dwd.order
> where dt >= '2026-10-01' and dt < '2026-11-01'
> group by city
> having count(*) > 100;
> ```
> **执行计划变化**：
> - 改写前：`TableScan` 无 `PartitionFilters`，`input size` = 全表大小
> - 改写后：`PartitionFilters: [dt >= 2026-10-01, dt < 2026-11-01]`，`input size` ≈ 1/36
> 另外，改写后的 `where` 是纯列比较，谓词可以下推到扫描层；原来的 `substr` 只能在上层 Filter 节点执行，还会多一次函数调用开销。
