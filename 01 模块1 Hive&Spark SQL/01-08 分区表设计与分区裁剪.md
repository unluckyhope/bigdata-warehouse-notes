# 01-08 分区表设计与分区裁剪

> [!abstract] 一句话结论
> 分区是 Hive/Spark 唯一「便宜且有效」的物理优化手段：**它把「扫描全表」变成「扫描一个目录」**。
> 但分区只在一种情况下有效——`分区列 <op> 常量` 且**列上没有任何函数**。设计上要回答两个问题：**按什么分区**（基数、增长速率、查询模式）和**分区内怎么组织**（分桶、文件大小、压缩格式）。

---

## 一、心智模型：分区 = 目录，分桶 = 文件

```
/user/hive/warehouse/dwd.db/order/
├── dt=2026-10-01/              ← 一级分区（一个目录）
│   ├── part-00000.parquet      ← 文件（分桶后文件名带 bucket 编号）
│   └── part-00001.parquet
├── dt=2026-10-02/
└── dt=2026-10-03/
```

**三个层次的物理组织**：

| 层次 | 物理表现 | 优化效果 | 代价 |
| --- | --- | --- | --- |
| **分区（partition）** | 目录（`dt=xxx`） | **分区裁剪**：不读无关目录 | 分区太多 → 元数据压力、小文件 |
| **分桶（bucket）** | 文件（`bucket_00000`） | **桶裁剪 + 更均匀的 join** | 写入时多一次 hash 计算 |
| **文件内（parquet/orc）** | row group / stripe | **列裁剪 + 谓词下推 + 字典编码** | 需要合适的文件大小 |

> [!important] 核心认知
> **分区裁剪是「元数据级」的优化**——它根本不打开文件，只根据目录名就跳过了。
> 所以它极快、极便宜，但**极其脆弱**：只要 SQL 里对分区列做了任何运算，裁剪就失效，退化成全表扫描。

---

## 二、核心知识点

### 2.1 分区键怎么选（设计决策）

**三条判断标准**：

| 标准 | 说明 | 反例 |
| --- | --- | --- |
| **基数适中** | 分区数控制在几千到几万 | 按 `user_id` 分区 → 几百万个目录，元数据直接崩 |
| **查询必带** | 业务查询几乎都会带这个条件 | 按 `province` 分区，但 90% 查询是全量的 → 白分 |
| **增长可控** | 每天新增分区数可预期 | 按小时分区，一天 24 个，一年 8760 个，可接受；按分钟就完了 |

**常见分区方案**：

| 表类型 | 推荐分区 | 说明 |
| --- | --- | --- |
| 日志/埋点表 | `dt`（天） | 一天一个分区，最常用 |
| 高频实时表 | `dt` + `hour` | 两级分区，注意分区数 = 天数 × 24 |
| 维表（小） | 不分区，或 `dt` 全量快照 | 维表小，分区意义不大 |
| 超大事实表 | `dt` + `region`（可选） | 二级分区要谨慎，容易小文件 |
| 拉链表 | `dt` 快照 | 见模块2 |

> [!danger] 反模式：按高基数字段分区
> ```sql
> -- ❌ 灾难：user_id 有几百万个值 → 几百万个目录
> create table t (amount decimal(10,2)) partitioned by (user_id bigint);
> ```
> 后果：① NameNode 压力爆炸（每个目录+文件都是元数据）；② `show partitions` 卡死；③ 编译 SQL 时元数据查询就要几十秒。
> **规则：分区键的 distinct 值总数控制在 10 万以内，单日新增控制在几百以内。**

### 2.2 静态分区 vs 动态分区

**静态分区**：写入时手动指定分区值（编译期确定）

```sql
-- 静态分区：适合"一次性写入某个确定分区"
insert overwrite table dwd.order partition (dt = '2026-10-01')
select order_id, amount from ods.order where dt = '2026-10-01';
```

**动态分区**：分区值来自数据本身（运行期确定）

```sql
-- 动态分区：适合"一次写入多个分区"
set hive.exec.dynamic.partition = true;
set hive.exec.dynamic.partition.mode = nonstrict;   -- 必须，否则要求至少一个静态分区

insert overwrite table dwd.order partition (dt)
select order_id, amount, dt from ods.order where dt >= '2026-10-01';
--                                     ↑ 分区列必须在 SELECT 的最后
```

> [!warning] 动态分区的三条硬规则
> 1. **分区列必须放在 `SELECT` 的最后一列**，且顺序与 `partition(...)` 一致
> 2. `hive.exec.dynamic.partition.mode` 必须是 `nonstrict`（默认是 `strict`，要求至少一个静态分区）
> 3. 动态分区会为每个分区启动 reduce task，**分区太多会起大量 task**

**关键参数**：

```sql
-- Hive
set hive.exec.dynamic.partition = true;
set hive.exec.dynamic.partition.mode = nonstrict;
set hive.exec.max.dynamic.partitions = 10000;              -- 单任务最大分区数
set hive.exec.max.dynamic.partitions.pernode = 1000;       -- 单节点最大分区数
set hive.exec.max.created.files = 100000;                  -- 最大文件数

-- Spark
set spark.sql.sources.partitionOverwriteMode = dynamic;    -- 动态分区覆盖
set spark.sql.shuffle.partitions = 200;
```

> [!danger] 动态分区的「全表覆盖」事故
> ```sql
> -- 想覆盖 10-01 的分区，结果写成了动态分区
> insert overwrite table dwd.order partition (dt)
> select ..., dt from ods.order;    -- 没有 where 条件！
> ```
> 后果：**整张表的所有分区被覆盖**，历史数据全丢。
> **防御**：
> - 生产 SQL 必须有 `where dt = '${bizdate}'` 之类的限定
> - 关键表开启 Hive 的「禁止全表覆盖」保护，或改用 `insert into`（追加，不删历史）
> - Spark 中 `partitionOverwriteMode=dynamic` 时，`overwrite` 只覆盖「本次写入涉及的分区」，相对安全；但 Hive 的 `insert overwrite ... partition(dt)` 是**先删所有分区再写**

### 2.3 分区裁剪：5 种失效写法（本节最重要）

分区裁剪发生在逻辑优化阶段，它识别的模式非常有限：**`分区列 op 常量`**。

```sql
-- ✅ 能裁剪
where dt = '2026-10-01'
where dt >= '2026-10-01' and dt < '2026-11-01'
where dt in ('2026-10-01', '2026-10-02')
where dt between '2026-10-01' and '2026-10-31'

-- ❌ 失效（函数包裹）
where substr(dt, 1, 7) = '2026-10'
where date_format(dt, 'yyyyMM') = '202610'
where cast(dt as date) = '2026-10-01'
where concat(dt, '') = '2026-10-01'
where coalesce(dt, '') = '2026-10-01'
where nvl(dt, '') = '2026-10-01'

-- ❌ 失效（类型不匹配触发隐式转换）
where dt = 20261001          -- dt 是 string，被 cast 成 double
where dt > 20261001

-- ❌ 失效（运算）
where dt + 1 = '2026-10-02'
where dt || 'x' = '2026-10-01x'

-- ❌ 失效（子查询/变量间接）
where dt = (select max(dt) from t2)    -- 部分版本支持，但不可靠
where dt = current_date                -- 依赖常量折叠，可能不裁剪
```

**失效的代价量化**：

| 场景 | 扫描量 | 耗时 |
| --- | --- | --- |
| 正确裁剪（1 天） | 100 GB | 2 分钟 |
| 裁剪失效（3 年） | 100 TB | 30 小时（且可能跑挂） |

> [!success] 三条改写法则
> 1. **把函数移到常量侧**：`where dt >= '2026-10-01' and dt < '2026-11-01'` 代替 `substr(dt,1,7)='2026-10'`
> 2. **类型必须一致**：分区列是 `string`，条件就写字符串（带引号）
> 3. **前缀 LIKE 可用但慎用**：`where dt like '2026-10%'` 在 Hive 支持前缀裁剪，Spark 支持有限，**跨引擎不保险**

### 2.5 分桶表（bucketing）：原理与适用场景

**分桶做什么**：按 `hash(分桶列) % 桶数` 把数据分到固定数量的文件里。

```sql
create table dwd.user_bucket (
    user_id bigint,
    name    string
)
clustered by (user_id) into 8 buckets
stored as parquet;
```

**分桶的三个作用**：

| 作用 | 原理 | 生效条件 |
| --- | --- | --- |
| **桶裁剪** | `where user_id = 123` → 只读 `hash(123)%8` 对应的那个文件 | 过滤条件是分桶列的等值 |
| **Map-side Join（桶 join）** | 两表按同一列分桶且桶数成倍数 → 对应桶直接 join，无需 shuffle | 两表分桶列相同、桶数成倍数 |
| **采样** | `tablesample(bucket 1 out of 8)` 只读 1/8 数据 | 需要快速探索数据 |

```sql
-- 桶 join（Bucket Map Join）
set hive.optimize.bucketmapjoin = true;
set hive.optimize.bucketmapjoin.sortedmerge = true;

select /*+ mapjoin(b) */ a.*, b.name
from dwd.order_bucket a join dim.user_bucket b on a.user_id = b.user_id;
```

> [!warning] 分桶的代价与坑
> 1. **写入时必须走 MR/Spark 的 bucket 逻辑**：`insert` 时要开 `hive.enforce.bucketing=true`，否则文件数不对
> 2. **桶数不能改**：改了要重建表
> 3. **小表分桶没意义**：分桶的价值在「大表 join 大表时避免 shuffle」，小表直接广播更快
> 4. **Spark 对 Hive 分桶表的支持有限**：Spark 读 Hive 分桶表时，桶信息可能不被识别，导致桶 join 不生效
>
> **现实建议**：**新项目优先用「分区 + 合适文件大小 + 广播 join」，分桶只在明确需要（如超大表 join 超大表、固定采样）时才用。**

### 2.6 分区表的写入模式

| 模式 | SQL | 行为 | 适用 |
| --- | --- | --- | --- |
| 追加 | `insert into table t partition(dt='x')` | 保留原数据，追加 | 增量表 |
| 覆盖（静态） | `insert overwrite table t partition(dt='x')` | **只覆盖指定分区** | 每日全量/增量重跑 |
| 覆盖（动态） | `insert overwrite table t partition(dt) select ..., dt` | Hive：先删所有分区再写；Spark（dynamic 模式）：只覆盖涉及的分区 | 多分区批量写入 |

> [!danger] Hive 与 Spark 的动态分区覆盖行为不同
> - **Hive**：`insert overwrite ... partition(dt)` 会**删除该表的所有分区**，然后写入新数据。如果 SELECT 只产生了 1 个分区的数据，其余分区全部丢失。
> - **Spark**（`partitionOverwriteMode=dynamic`）：只覆盖「本次写入产生数据」的分区，其他分区保留。
>
> 这是跨引擎迁移的高危差异。**Hive 上做动态分区覆盖前，务必确认 SELECT 覆盖了所有需要的分区。**

### 2.7 分区表与小文件

分区表的天然问题是**小文件**：每天一个分区，每个分区 N 个文件，一年就是 365×N 个文件。

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 分区数太多 | 按小时/按高基数列分区 | 减少分区粒度 |
| 单分区文件太多 | reduce 数过多 / 写入并行度高 | `distribute by` 控制文件数 |
| 文件太小（< 128MB） | 上游数据少但并行度高 | 合并小文件 |

```sql
-- 控制输出文件数（Hive）
set hive.merge.mapfiles = true;
set hive.merge.mapredfiles = true;
set hive.merge.size.per.task = 256000000;      -- 256MB
set hive.merge.smallfiles.avgsize = 16000000;  -- 16MB

-- Spark：写入前重分区
insert overwrite table dwd.order partition(dt='2026-10-01')
select /*+ REPARTITION(10) */ ... from ...;

-- 或者用 distribute by 控制（按分区列分发，每个分区内再控制文件数）
select ... from t distribute by dt;
```

> [!tip] 文件大小的经验值
> - HDFS 块大小 128MB，**目标文件大小 128~256MB**
> - 小于 64MB 视为小文件，需要合并
> - 大于 512MB 考虑拆分（单个 task 处理太慢）

### 2.8 分区表的元数据与运维

```sql
-- 查看分区
show partitions dwd.order;
show partitions dwd.order partition (dt='2026-10-01');

-- 添加分区（外部表常用）
alter table dwd.order add if not exists partition (dt='2026-10-01') location '/path/to/data';

-- 修复分区（数据已存在但元数据缺失）
msck repair table dwd.order;

-- 删除分区
alter table dwd.order drop if exists partition (dt='2026-09-01');

-- 查看分区大小
desc formatted dwd.order partition (dt='2026-10-01');
```

> [!warning] 外部表删分区的坑
> - **内部表（managed）**：`drop partition` 会**同时删除数据**
> - **外部表（external）**：`drop partition` 只删元数据，**数据还在 HDFS 上**
> 生产上数仓表**建议用外部表**，防止误删数据。删表/删分区时要明确知道自己在操作哪种表。

## 三、动手实验

### 3.1 建分区表 + 造数

```sql
drop table if exists tmp.part_lab;
create table tmp.part_lab (
    order_id int,
    amount   decimal(10,2),
    user_id  bigint
)
partitioned by (dt string)
stored as parquet;

-- 静态分区写入
insert overwrite table tmp.part_lab partition (dt='2026-10-01')
select 1, 100.00, 101 union all select 2, 200.00, 102;

insert overwrite table tmp.part_lab partition (dt='2026-10-02')
select 3, 300.00, 101 union all select 4, 400.00, 103;

insert overwrite table tmp.part_lab partition (dt='2026-11-01')
select 5, 500.00, 104;

show partitions tmp.part_lab;
```

### 3.2 实验一：对比裁剪生效与失效的扫描量

```sql
-- A：正确裁剪
explain extended
select count(*) from tmp.part_lab where dt = '2026-10-01';
-- 找 TableScan，应有 PartitionFilters: [dt = 2026-10-01]

-- B：函数包裹，裁剪失效
explain extended
select count(*) from tmp.part_lab where substr(dt, 1, 7) = '2026-10';
-- TableScan 无 PartitionFilters，只有 Filter 节点

-- C：类型不匹配
explain extended
select count(*) from tmp.part_lab where dt = 20261001;
-- 应看到 cast(dt as double)，无 PartitionFilters
```

> [!success] 观察要点
> 重点看 `TableScan` 节点的三行：
> - `PartitionFilters`：有值 = 裁剪生效
> - `PushedFilters`：有值 = 谓词下推生效
> - `ReadSchema`：只包含用到的列 = 列裁剪生效

### 3.3 实验二：动态分区写入

```sql
set hive.exec.dynamic.partition = true;
set hive.exec.dynamic.partition.mode = nonstrict;

drop table if exists tmp.part_dyn;
create table tmp.part_dyn (order_id int, amount decimal(10,2))
partitioned by (dt string) stored as parquet;

insert overwrite table tmp.part_dyn partition (dt)
select order_id, amount, dt from tmp.part_lab;   -- 分区列放最后

show partitions tmp.part_dyn;
```

**验证点**：`show partitions` 应该出现 3 个分区（10-01、10-02、11-01）。

### 3.4 实验三：动态分区覆盖的危险性

```sql
-- ⚠️ 危险实验：只写 1 个分区的数据，但用动态分区覆盖
insert overwrite table tmp.part_dyn partition (dt)
select order_id, amount, dt from tmp.part_lab where dt = '2026-10-01';

show partitions tmp.part_dyn;
-- Hive 上：只剩 1 个分区！10-02 和 11-01 的数据没了
```

> [!danger] 这个实验请务必在测试表上做
> 生产上如果对真实表执行，就是一次数据丢失事故。理解这个行为，比记住「要用 insert into」更重要。

### 3.5 实验四：`msck repair` 恢复分区

```sql
-- 模拟：数据在 HDFS 上但元数据丢失（外部表场景）
-- 实际操作用 HDFS 命令往分区目录写文件，然后：
msck repair table tmp.part_dyn;
show partitions tmp.part_dyn;
```

### 3.6 实验五：分桶表

```sql
drop table if exists tmp.bucket_lab;
create table tmp.bucket_lab (user_id bigint, name string)
clustered by (user_id) into 4 buckets
stored as parquet;

set hive.enforce.bucketing = true;
insert overwrite table tmp.bucket_lab
select user_id, name from tmp.dup_user;   -- 用 01-07 造的表

-- 看文件数（应该是 4 个）
dfs -ls /user/hive/warehouse/tmp.db/bucket_lab;

-- 桶裁剪
explain extended select * from tmp.bucket_lab where user_id = 101;
-- 应该看到只读 1 个桶（TableScan 里有 bucket 信息）
```

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 任务扫描量是预期的 100 倍 | 分区列被函数包裹，裁剪失效 | `explain` 看 `PartitionFilters` | 改写为范围条件 |
| 结果为空但分区有数据 | 分区列类型不匹配（`dt = 20261001`） | 检查引号 | 分区列是 string 就加引号 |
| 动态分区写入后历史数据没了 | Hive 的 `insert overwrite partition(dt)` 删所有分区 | `show partitions` 对比 | 改 `insert into` 或限定写入范围 |
| 分区数暴涨 | 按高基数列分区 / 按小时分区 | `show partitions \| wc -l` | 减少分区粒度 |
| 元数据查询极慢 | 分区数过多（> 10 万） | `show partitions` 耗时 | 合并分区；改用分桶 |
| 小文件泛滥 | 分区多 + reduce 多 | `dfs -count` 看文件数 | 合并小文件；`distribute by` |
| 外部表删分区后数据还在 | 外部表只删元数据 | `dfs -ls` 检查 | 明确表类型；需要删数据时手动删 HDFS |
| `msck repair` 很慢 | 分区太多，要遍历所有目录 | — | 改用 `alter table add partition` 精确添加 |
| 分桶表 join 没加速 | 两表桶数不成倍数 / Spark 不识别 Hive 分桶 | `explain` 看是否 `BucketMapJoin` | 统一桶数；或改用广播 join |
| 分区字段在 SELECT 里位置错了 | 动态分区要求分区列在最后 | 报错 `Dynamic partition ... not found` | 调整 SELECT 列顺序 |
| 时间分区跨时区错位 | 用 `current_date` 生成分区值 | 对比集群时区 | 分区值从调度参数传入 |

## 五、面试追问

> [!question] 1. 分区和分桶的区别？
> **一句话答法**：分区是**目录级**切分（按字段值分目录），用于裁剪；分桶是**文件级**切分（按 hash 取模分文件），用于桶裁剪、桶 join、采样。
> **追问陷阱**：「分桶能替代分区吗」——不能。分桶没有目录结构，无法做分区裁剪，且桶数固定不可变。

> [!question] 2. 分区裁剪什么时候失效？
> **一句话答法**：分区列被函数包裹、类型不匹配触发隐式转换、参与运算、或通过变量/子查询间接比较时。
> **追问陷阱**：「`where dt like '2026-10%'` 能裁剪吗」——Hive 支持前缀 LIKE 裁剪，Spark 支持有限，跨引擎不保险。

> [!question] 3. 怎么验证分区裁剪生效了？
> **一句话答法**：`explain extended` 看 `TableScan` 节点的 `PartitionFilters`，有值说明生效；同时看 Spark UI 里 scan 的 files read 数量。
> **追问陷阱**：「`PushedFilters` 里有 dt 算裁剪吗」——不算，那是「全读后过滤」，IO 没省。

> [!question] 4. 动态分区有什么限制？
> **一句话答法**：① 分区列必须在 SELECT 最后；② 需要 `nonstrict` 模式；③ 分区数受 `max.dynamic.partitions` 限制；④ 分区太多会导致大量 task。
> **追问陷阱**：「Hive 的 `insert overwrite partition(dt)` 有什么风险」——会删掉表的所有分区再写，容易误删历史数据。

> [!question] 5. 分区键怎么选？
> **一句话答法**：看三个维度——基数（distinct 值不能太大）、查询模式（查询必带这个条件）、增长速率（每天新增分区数可控）。日志表通常按天分区。
> **追问陷阱**：「按 user_id 分区行不行」——不行，几百万个目录会压垮 NameNode，元数据查询也会超时。

> [!question] 6. 分区数太多有什么问题？
> **一句话答法**：① 元数据压力（NameNode 和 metastore）；② 编译 SQL 时元数据查询慢；③ 小文件多；④ 全表扫描时要打开几万个文件句柄。
> **追问陷阱**：「多少算太多」——经验值：总分区数控制在 10 万以内，单日新增几百以内。

> [!question] 7. 分桶表有什么用？
> **一句话答法**：三个用途——桶裁剪（等值查询只读一个桶）、桶 join（两表同列同桶数，避免 shuffle）、采样（`tablesample`）。
> **追问陷阱**：「生产上用得多吗」——不多。分桶维护成本高（桶数不可变、写入要强制分桶），Spark 支持也不完善，多数场景用广播 join 替代。

> [!question] 8. `insert into` 和 `insert overwrite` 的区别？
> **一句话答法**：`into` 是追加，保留原数据；`overwrite` 是覆盖，**静态分区只覆盖指定分区，动态分区在 Hive 上会删所有分区**。
> **追问陷阱**：「重跑任务用哪个」——用 `overwrite` + 静态分区，保证幂等；用 `into` 重跑会产生重复数据。

> [!question] 9. 内部表和外部表的区别？删分区时行为有何不同？
> **一句话答法**：内部表删表/删分区会删数据；外部表只删元数据，数据留在 HDFS。
> **追问陷阱**：「生产上用哪种」——数仓表建议外部表，防止误删；临时表/中间表用内部表。

> [!question] 10. 小文件怎么产生？怎么治理？
> **一句话答法**：产生原因——分区多、reduce 多、写入并行度高、上游数据量小但并行度大。治理——`distribute by` 控制文件数、合并小文件参数、写入前 `repartition`、定期 `merge` 任务。
> **追问陷阱**：「文件多大合适」——128~256MB（对齐 HDFS 块大小）。

> [!question] 11. `msck repair table` 做了什么？什么时候用？
> **一句话答法**：扫描 HDFS 目录，把「存在但元数据没有」的分区补进 metastore。用于外部表、手工往 HDFS 写数据的场景。
> **追问陷阱**：「分区很多时有什么问题」——会遍历所有目录，很慢；改用 `alter table add partition` 精确添加。

> [!question] 12. 分区表写入时怎么保证幂等？
> **一句话答法**：用 `insert overwrite` + 静态分区（`partition(dt='${bizdate}')`），重跑覆盖同一分区，结果一致。
> **追问陷阱**：「动态分区怎么保证」——Spark 开 `partitionOverwriteMode=dynamic`（只覆盖涉及的分区）；Hive 上慎用动态覆盖，或用临时表 + `alter table exchange partition`。

## 六、自测题

> [!question] 1.（单选）下面哪个 `WHERE` 条件能触发分区裁剪（`dt` 是 string 分区列）？
> A. `where substr(dt,1,7) = '2026-10'`
> B. `where dt = 20261001`
> C. `where dt between '2026-10-01' and '2026-10-31'`
> D. `where cast(dt as date) = '2026-10-01'`

> [!question] 2.（单选）Hive 中执行 `insert overwrite table t partition(dt) select a, b, dt from src where dt='2026-10-01'`，表原有 10 个分区，执行后剩几个？
> A. 10
> B. 11
> C. 1
> D. 0

> [!question] 3.（判断）分桶表可以完全替代分区表，因为分桶也能做数据裁剪。

> [!question] 4.（场景设计）你的订单表按 `dt`（天）分区，已有 3 年数据（约 1000 个分区），单分区 100GB。业务要查「2026 年 10 月整月的数据」。请写出正确的 SQL，并说明如果用 `substr(dt,1,7)='2026-10'` 会有什么后果（量化）。

> [!question] 5.（场景设计）你需要设计一张埋点事件表，每天约 50 亿条记录、500GB。查询模式：① 90% 是按天查某类事件；② 5% 是按用户 ID 查某用户的行为；③ 5% 是跨月分析。请给出分区方案、文件格式、以及是否用分桶，并说明理由。

> [!success]- 答案与解析（点击展开）
> **1. C**
> A 和 D 用函数包裹了分区列，裁剪失效；B 是类型不匹配（string vs int），会触发隐式 cast，裁剪失效；C 是裸列的范围比较，可以裁剪。
>
> **2. C**
> Hive 的 `insert overwrite ... partition(dt)`（动态分区）会**先删除所有分区**，再写入新数据。SELECT 只产生了 10-01 一个分区，所以最终只剩 1 个分区，其余 9 个分区的数据全部丢失。
> **这是 Hive 上最危险的操作之一。**
>
> **3. 错误**
> 分桶只能做「桶裁剪」（按 hash 取模定位文件），不能做目录级裁剪，且桶数固定、维护成本高。分区和分桶是互补关系，不是替代关系。
>
> **4. 参考 SQL**
> ```sql
> select ...
> from dwd.order
> where dt >= '2026-10-01' and dt < '2026-11-01';
> ```
> **用 `substr(dt,1,7)='2026-10'` 的后果**
> - 分区裁剪失效，需要扫描全部 1000 个分区
> - 扫描量 = 1000 × 100GB = **100TB**（而不是 31 × 100GB = 3.1TB）
> - 数据量放大 **约 32 倍**
> - 按扫描量计费的场景下，单次查询成本放大 32 倍；按时间算，2 分钟的任务可能变成 1 小时以上，甚至因资源不足失败
> - 另外 `substr` 对每行都要执行一次函数调用，CPU 开销也增加
>
> **5. 设计方案**
> | 维度 | 方案 | 理由 |
> | --- | --- | --- |
> | 分区 | `dt`（天） | 90% 查询按天，分区裁剪收益最大；一年 365 个分区，元数据压力可接受 |
> | 是否加 `hour` 二级分区 | **不加** | 50 亿/天，如果按小时分区，单分区只有 2 亿/20GB，会产生 8760 个分区/年，且 90% 查询是按天，加了反而增加元数据和小文件压力 |
> | 文件格式 | **Parquet**（或 ORC） | 列式存储，列裁剪 + 谓词下推 + 压缩率高（通常 5~10 倍）；埋点表字段多，列裁剪收益极大 |
> | 压缩 | snappy（Parquet 默认）或 zstd | snappy 解压快，zstd 压缩率高，看 CPU/IO 权衡 |
> | 分桶 | **不分桶** | 理由见下 |
> | 文件大小 | 128~256MB | 500GB / 256MB ≈ 2000 个文件/分区，合理 |
>
> **为什么不分桶**
> - 分桶主要收益是「按用户 ID 等值查询时只读一个桶」（场景②）。但场景②只占 5%，为它付出「全表分桶」的写入代价不划算。
> - 更好的方案：为场景②单独建一张**用户维度的索引表/倒排表**（`user_id → 该用户的事件在哪些分区`），或者用支持索引的引擎（如 ClickHouse、Doris）承接点查。
> - 分桶还会导致：桶数不可变（扩缩容要重建表）、Spark 读 Hive 分桶表支持不完善、小文件问题更严重。
>
> **额外建议**
> - 场景③（跨月分析）用 `dt >= 'x' and dt < 'y'` 范围查询，分区裁剪天然支持。
> - 如果场景①里有「按事件类型过滤」，可以把 `event_type` 作为**分区内的排序键**（`distribute by dt sort by event_type`），配合 Parquet 的 row group 统计信息实现「跳过不相关的 row group」。
> - 冷数据（3 个月前）可以转储到更低成本的存储（如 OSS/S3），通过视图或外部表访问。
