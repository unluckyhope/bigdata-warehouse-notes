# 01-05 聚合与多维聚合

> [!abstract] 一句话结论
> 聚合是数仓里 CPU 和网络开销最大的操作，因为几乎每个 `GROUP BY` 都要 shuffle。这一节要解决三类问题：**口径问题**（`sum`/`count`/`avg` 对 NULL 和重复的处理）、**多维问题**（一张表要出「按城市/按品类/按日期/总计」多套汇总）、**形状问题**（行转列、列转行、`collect_list` + `explode`）。
> 学完这节，你应该能用一条 SQL 出「多维汇总报表」，而不是写四遍 SQL 再 `union`。

---

## 一、心智模型：聚合的两个阶段

`GROUP BY` 在分布式引擎里不是「一次算完」，而是分两步：

```
① Map 端局部聚合（Partial Aggregate / Map-side Combine）
   每个 map task 先在本地把相同 key 聚合一次
   输入 1 亿行 → 输出可能只有 10 万行

② Shuffle（按 key 分区，发到对应 reducer）

③ Reduce 端全局聚合（Final Aggregate）
   把各 map 的局部结果再合并一次
```

> [!important] 为什么这个模型重要
> - **不是所有聚合都能「局部先算」**：`sum`/`count`/`max`/`min` 可以，但 `avg` 不能直接合并（要先拆成 `sum` 和 `count`），`count(distinct)` 更麻烦（要传明细或 HyperLogLog 草图）。
> - **局部聚合能大幅减少 shuffle 数据量**：如果 map 端能把 1 亿行压成 10 万行，shuffle 就只传 10 万行。所以**先过滤再聚合**永远比「聚合后再过滤」快。
> - **`group by` 的 key 决定分区数**：key 的基数（distinct 值个数）太大会导致分区过多、小文件泛滥；基数太小会导致分区过大、单 task 内存爆炸。

## 二、核心知识点

### 2.1 聚合函数的语义细节

| 函数 | NULL 处理 | 能否局部聚合 | 常见坑 |
| --- | --- | --- | --- |
| `count(*)` | 数行数 | ✅ | 与 `count(col)` 结果不同 |
| `count(col)` | 跳过 NULL | ✅ | 空串算非空 |
| `sum(col)` | 跳过 NULL；**全 NULL 返回 NULL** | ✅ | 下游做加法会传染 NULL |
| `avg(col)` | 分母是非 NULL 行数 | ⚠️ 需拆成 sum/count | 与 `sum/count(*)` 口径不同 |
| `max/min` | 跳过 NULL；全 NULL 返回 NULL | ✅ | |
| `count(distinct col)` | 跳过 NULL | ❌ 需传明细 | 多列 distinct 性能极差 |
| `collect_list(col)` | **保留 NULL**（Hive 3.x 行为，部分版本会过滤） | ❌ | 结果顺序不确定 |
| `collect_set(col)` | 去重，**不保证顺序** | ❌ | 大基数会导致 OOM |
| `percentile(col, p)` | 跳过 NULL | ❌ | 精确计算，大表很慢 |
| `percentile_approx(col, p, B)` | 跳过 NULL | ✅ | 近似值，B 越大越准 |

> [!warning] `avg` 的「不能直接局部聚合」
> 两个 map 分别算出 `avg=10`（基于 100 行）和 `avg=20`（基于 10 行），直接平均得 15 是**错的**，正确值是 `(10*100 + 20*10)/110 ≈ 10.9`。
> 所以引擎内部会把 `avg` 改写成 `sum/count` 再做两阶段聚合。**你自己写 SQL 时也要注意这个逻辑**——跨表/跨分区合并平均值时，不能直接对平均值再求平均。

> [!danger] `collect_set` 的 OOM 风险
> `collect_set(user_id)` 在千万级用户上会把所有 distinct 值堆到一个数组里，单个 key 就能撑爆 executor 内存。
> 替代方案：`approx_count_distinct(col)`（HyperLogLog，误差约 1~2%），或 `size(collect_set(...))` 前先限制。

### 2.2 `GROUP BY` 的四种写法与代价

```sql
-- 写法1：标准列名（推荐）
select city, category, sum(amount) from t group by city, category;

-- 写法2：位置序号（不推荐，列顺序变了就错）
select city, category, sum(amount) from t group by 1, 2;

-- 写法3：表达式（可以对表达式分组）
select substr(dt,1,7) as month, sum(amount) from t group by substr(dt,1,7);

-- 写法4：别名（Hive 支持，Spark 部分支持，不推荐）
select substr(dt,1,7) as month, sum(amount) from t group by month;
```

> [!tip] 表达式分组的性能影响
> `group by substr(dt,1,7)` 会让引擎对每行都算一次 `substr`，且这个结果不参与分区裁剪。
> 如果 `dt` 是分区键，**应该先 `where dt >= '2026-01-01'` 把范围限定，再 `group by substr(dt,1,7)`**，而不是直接对全表做表达式分组。

**`GROUP BY` 的 shuffle 代价**：

| 数据量 | key 基数 | 主要瓶颈 |
| --- | --- | --- |
| 1 亿行，100 个 key | 小 | 单 reducer 内存（可能 OOM）→ 需要加盐打散 |
| 1 亿行，100 万 key | 中 | shuffle 网络传输 |
| 1 亿行，1 亿 key（几乎唯一） | 大 | shuffle + 小文件；聚合几乎无收益，考虑是否真需要 |

> [!note] 「高基数 group by」的优化
> 如果 key 几乎唯一（如按 `order_id` 分组），聚合的意义不大，但引擎仍要 shuffle。
> 优化手段：① 用 `distribute by key` + `sort by` 代替，避免全局聚合；② 确认是否真的需要聚合，有时 `row_number` 更合适。

### 2.3 `HAVING` 与聚合的配合

```sql
-- 找出「订单数 > 100 且 客单价 > 500」的城市
select city,
       count(*) as order_cnt,
       sum(amount) / count(*) as aov
from dwd.order
where dt = '2026-10-01'          -- 行级过滤，先执行
group by city
having count(*) > 100            -- 组级过滤，后执行
   and sum(amount) / count(*) > 500;
```

> [!tip] `HAVING` 里能用别名吗
> Hive 支持（宽松），Spark 3.x 不支持（严格）。
> **跨引擎可移植的写法**：`HAVING` 里重复写聚合表达式，不要用 SELECT 别名。

### 2.4 多维聚合：`GROUPING SETS` / `ROLLUP` / `CUBE`

**问题场景**：一张报表要同时出「按城市」「按品类」「按城市+品类」「全国总计」四套数据。

**传统做法**（四次扫描，四次 shuffle）：

```sql
select city, null as category, sum(amount) from t group by city
union all
select null, category, sum(amount) from t group by category
union all
select city, category, sum(amount) from t group by city, category
union all
select null, null, sum(amount) from t;
```

**优化做法**（一次扫描，一次 shuffle）：

```sql
select city, category, sum(amount) as gmv
from t
group by city, category
grouping sets (
    (city, category),   -- 城市+品类
    (city),             -- 只有城市
    (category),         -- 只有品类
    ()                  -- 总计
);
```

**三种多维聚合的对比**：

| 语法 | 生成的分组组合 | 组合数（n 个维度） | 适用场景 |
| --- | --- | --- | --- |
| `GROUPING SETS ((a,b),(a),())` | **你指定的**组合 | 任意 | 只要特定几套汇总 |
| `ROLLUP (a, b, c)` | `(a,b,c)`, `(a,b)`, `(a)`, `()` | n+1 | **层级汇总**（如 国家→省→市→总计） |
| `CUBE (a, b, c)` | 所有 2^n 种组合 | 2^n | 全维度交叉分析（维度少时用） |

> [!warning] `CUBE` 的组合爆炸
> 5 个维度 → 32 种组合；10 个维度 → 1024 种组合。数据量会成倍放大，**维度超过 4 个慎用 CUBE**，改用 `GROUPING SETS` 明确指定需要的组合。

**区分「真实的 NULL」和「汇总产生的 NULL」**：`grouping()` / `grouping_id()`

这是多维聚合最容易踩的坑：汇总行里 `city` 是 NULL，但业务数据本身也可能有 `city is NULL` 的记录，两者混在一起无法区分。

```sql
select
    city,
    category,
    sum(amount) as gmv,
    grouping(city)     as g_city,      -- 1 表示这行是"城市维度被汇总掉了"
    grouping(category) as g_category,
    grouping_id(city, category) as gid -- 位图，方便判断
from t
group by city, category
grouping sets ((city, category), (city), (category), ());
```

**结果示例**：

| city | category | gmv | g_city | g_category | 含义 |
| --- | --- | --- | --- | --- | --- |
| 北京 | 手机 | 1000 | 0 | 0 | 明细行 |
| 北京 | NULL | 5000 | 0 | **1** | 北京汇总（category 被汇总） |
| NULL | 手机 | 8000 | **1** | 0 | 手机品类汇总 |
| NULL | NULL | 20000 | **1** | **1** | 全国总计 |
| **NULL** | 手机 | 300 | **0** | 0 | **真实的 city 为 NULL 的明细**（注意 g_city=0） |

> [!success] 关键结论
> **`grouping(col) = 0` 表示这是真实值（哪怕值是 NULL），`= 1` 表示这是汇总产生的 NULL。**
> 报表展示时应该：
> ```sql
> case when grouping(city) = 1 then '全部' else coalesce(city, '未知') end as city_display
> ```

**`ROLLUP` 的层级语义**：

```sql
-- 国家 → 省 → 市 → 总计
select country, province, city, sum(gmv)
from t
group by country, province, city with rollup;

-- 等价于 grouping sets ((country,province,city),(country,province),(country),())
```

> [!note] `WITH ROLLUP` 的写法差异
> - Hive：`group by a, b with rollup` 或 `group by a, b grouping sets(...)`
> - Spark 3.x：`group by rollup(a, b)` 或 `group by a, b with rollup`
> 两种写法在部分版本上行为不同，**建议统一用 `grouping sets` 显式写**，可移植性最好。

### 2.5 行列转换：`collect_list` + `explode` + `lateral view`

**行转列**（多行 → 一行一个数组/字符串）：

```sql
-- 每个订单的所有商品名拼成一个字符串
select
    order_id,
    concat_ws(',', collect_list(sku_name)) as skus,
    size(collect_set(sku_id))              as sku_cnt
from dwd.order_item
group by order_id;
```

> [!warning] `collect_list` 的顺序不确定
> 分布式环境下，`collect_list` 的拼接顺序**不保证**和输入顺序一致。
> 如果需要有序（比如「按时间拼接操作轨迹」），必须：
> ```sql
> -- 方式一：先排序再聚合（需要子查询，因为 collect_list 不支持 order by）
> select order_id, concat_ws(',', collect_list(sku_name)) as skus
> from (select * from dwd.order_item distribute by order_id sort by order_id, item_seq) t
> group by order_id;
>
> -- 方式二：Spark 3.x 支持 sort_array
> select order_id, concat_ws(',', sort_array(collect_list(concat(lpad(item_seq,10,'0'), sku_name)))) ...
> ```

**列转行**（一行多个列 → 多行）：

```sql
-- 把 q1~q4 四个季度列变成四行
select order_id, quarter, amount
from (
    select order_id, q1, q2, q3, q4 from dwd.order_quarter
) t
lateral view explode(map('Q1', q1, 'Q2', q2, 'Q3', q3, 'Q4', q4)) tmp as quarter, amount;
```

**`explode` 的三种用法**：

```sql
-- 1. explode array → 一列多行
select explode(array('a','b','c')) as x;

-- 2. explode map → 两列多行
select explode(map('k1','v1','k2','v2')) as (k, v);

-- 3. posexplode → 带下标
select posexplode(array('a','b','c')) as (pos, val);
```

> [!danger] `explode` 的三个限制
> 1. **不能和其他列一起直接 select**：`select order_id, explode(arr) from t` 会报错，必须用 `lateral view`
> 2. **不能在 `where` / `group by` 里直接用**
> 3. **`explode` 会把行数放大**：数组有 100 个元素，一行变 100 行，如果数组很大要注意数据膨胀

**`lateral view` 的完整语法**：

```sql
select order_id, sku
from dwd.order_item
lateral view explode(split(sku_list, ',')) t as sku;
--                                 ↑ 表别名  ↑ 列别名
```

**`lateral view outer`**：数组为空/NULL 时，保留原行（对应列补 NULL），否则该行会消失。

```sql
-- 如果 sku_list 是空串，split 返回 [""]，explode 后得到一行空值
-- 如果是 NULL，explode 后该行直接消失
-- 用 outer 保留原行
select order_id, sku
from dwd.order_item
lateral view outer explode(split(sku_list, ',')) t as sku;
```

> [!important] 生产建议
> `explode` 会让数据量放大，**放大的倍数取决于数组长度**。如果某个 key 的数组特别长（如用户 3 年的行为序列），会造成严重的数据倾斜。
> 防御：explode 前先 `where size(arr) <= 1000`，或对超长数组单独处理。

### 2.6 聚合的常见「口径陷阱」

**陷阱一：`count(distinct)` 在多维聚合里失真**

```sql
-- ❌ 错误：UV 不能跨维度相加
select city, count(distinct user_id) as uv from t group by city;
-- 北京 100 万 + 上海 80 万 ≠ 全国 180 万（有跨城用户）

-- ✅ 正确：全国 UV 要单独算
select count(distinct user_id) from t;
```

> [!danger] 这是报表对不上的头号原因
> 所有「去重类指标」（UV、去重设备数、去重订单数）都**不可加**。
> 汇总层设计时必须明确：哪些指标可加（`sum`）、哪些是「半可加」（如库存，可跨时间不可跨空间）、哪些完全不可加（`distinct count`）。
> 不可加指标要在汇总层**存明细或存 HLL 草图**，不能靠上卷求和。

**陷阱二：`sum` 的重复计算**

```sql
-- 订单表 join 明细表后 sum(order.amount) → 翻倍（见 01-04）
-- 防御：聚合前确认粒度
```

**陷阱三：`avg` 的平均**

```sql
-- ❌ 错误：各城市客单价的平均 ≠ 全国客单价
select avg(city_aov) from (select city, avg(amount) as city_aov from t group by city) x;

-- ✅ 正确：全国客单价 = 总金额 / 总订单数
select sum(amount) / count(*) from t;
```

### 2.7 聚合性能优化清单

| 手段 | 效果 | 适用 |
| --- | --- | --- |
| 先 `WHERE` 过滤再聚合 | 减少输入行数 | 永远适用 |
| 开启 map 端聚合 | 减少 shuffle 数据量 | 默认开启，确认没被关掉 |
| 用 `GROUPING SETS` 代替多次 `union all` | 一次扫描出多套汇总 | 多维报表 |
| 高基数 `count(distinct)` 改 `approx_count_distinct` | 从 O(n) 到 O(1) 内存 | 允许 1~2% 误差的 UV |
| 倾斜 key 加盐 | 解决单 reducer OOM | 有明显热点 key |
| 增大 `spark.sql.shuffle.partitions` | 提高并行度 | 数据量大、分区数不足 |
| 用 `distribute by` 控制输出文件数 | 减少小文件 | 写入 Hive 表 |

```sql
-- 常用参数
set hive.map.aggr = true;                      -- Hive map 端聚合
set hive.groupby.mapaggr.checkinterval = 100000;
set hive.groupby.skewindata = true;            -- 倾斜时两阶段聚合

set spark.sql.shuffle.partitions = 400;        -- 默认 200，按数据量调
set spark.sql.adaptive.enabled = true;         -- AQE
set spark.sql.adaptive.coalescePartitions.enabled = true;
```

## 三、动手实验

### 3.1 建表造数

```sql
drop table if exists tmp.agg_lab;
create table tmp.agg_lab (
    order_id int,
    city     string,
    category string,
    amount   decimal(10,2),
    user_id  bigint,
    dt       string
);
insert into tmp.agg_lab values
(1, '北京', '手机', 1000.00, 101, '2026-10-01'),
(2, '北京', '电脑', 5000.00, 101, '2026-10-01'),
(3, '北京', '手机', 2000.00, 102, '2026-10-01'),
(4, '上海', '手机', 1500.00, 101, '2026-10-01'),   -- user 101 跨城
(5, '上海', '电脑', 6000.00, 103, '2026-10-01'),
(6, null,  '手机',  800.00, 104, '2026-10-01'),   -- city 真实为 NULL
(7, '广州', '配件',  200.00, 105, '2026-10-01');
```

### 3.2 实验一：多维聚合 + 区分真实 NULL

```sql
select
    city,
    category,
    sum(amount)                as gmv,
    count(distinct user_id)    as uv,
    grouping(city)             as g_city,
    grouping(category)         as g_cat,
    grouping_id(city, category) as gid
from tmp.agg_lab
group by city, category
grouping sets ((city, category), (city), (category), ())
order by gid, city, category;
```

**预期结果解读**：

| city | category | gmv | g_city | g_cat | 说明 |
| --- | --- | --- | --- | --- | --- |
| 北京 | 手机 | 3000 | 0 | 0 | 明细 |
| 北京 | 电脑 | 5000 | 0 | 0 | 明细 |
| 上海 | 手机 | 1500 | 0 | 0 | 明细 |
| 上海 | 电脑 | 6000 | 0 | 0 | 明细 |
| **NULL** | 手机 | 800 | **0** | 0 | **真实 city 为 NULL**（g_city=0 是关键） |
| 广州 | 配件 | 200 | 0 | 0 | 明细 |
| 北京 | NULL | 8000 | 0 | **1** | 北京汇总 |
| 上海 | NULL | 7500 | 0 | 1 | 上海汇总 |
| NULL | 手机 | 5300 | **1** | 0 | 手机汇总 |
| NULL | NULL | 16500 | 1 | 1 | 总计 |

> [!success] 验证点
> 注意「NULL + 手机 + gmv=800 + g_city=0」这一行——它和「NULL + 手机 + gmv=5300 + g_city=1」是两个不同的行，虽然 city 都是 NULL。**这就是 `grouping()` 存在的意义。**

### 3.3 实验二：UV 不可加

```sql
-- 各城市 UV
select city, count(distinct user_id) as uv from tmp.agg_lab group by city;
-- 北京 2（101,102），上海 2（101,103），NULL 1（104），广州 1（105）
-- 相加 = 6

-- 全国 UV
select count(distinct user_id) as uv from tmp.agg_lab;
-- 5（101,102,103,104,105）—— 因为 101 同时在北京和上海

-- 差额 = 1，正是跨城用户
```

### 3.4 实验三：ROLLUP 层级汇总

```sql
select
    coalesce(city, '【合计】')      as city_disp,
    coalesce(category, '【小计】')  as cat_disp,
    sum(amount)                     as gmv
from tmp.agg_lab
group by city, category with rollup;
```

**看什么**：`(city, category)` → `(city)` → `()` 三层，最后一行是全国总计。

### 3.5 实验四：行列转换

```sql
-- 行转列：每个城市买了哪些品类
select
    city,
    concat_ws('|', collect_list(category)) as categories,
    count(distinct category)               as cat_cnt
from tmp.agg_lab
where city is not null
group by city;

-- 列转行：把城市维度的 GMV 打散成行（演示 lateral view）
select city, gmv
from (
    select
        sum(if(city='北京', amount, 0)) as bj,
        sum(if(city='上海', amount, 0)) as sh,
        sum(if(city='广州', amount, 0)) as gz
    from tmp.agg_lab
) t
lateral view explode(map('北京', bj, '上海', sh, '广州', gz)) m as city, gmv;
```

### 3.6 实验五：对比「多次 union」和「grouping sets」的性能

```sql
-- 用大表验证：把 agg_lab 自关联放大到 10 万行
drop table if exists tmp.agg_big;
create table tmp.agg_big as
select a.order_id * 100000 + b.order_id as oid,
       a.city, a.category, a.amount, a.user_id
from tmp.agg_lab a cross join tmp.agg_lab b;

-- A：四次 union all（慢）
select city, null as category, sum(amount) from tmp.agg_big group by city
union all
select null, category, sum(amount) from tmp.agg_big group by category
union all
select city, category, sum(amount) from tmp.agg_big group by city, category
union all
select null, null, sum(amount) from tmp.agg_big;

-- B：grouping sets（快）
select city, category, sum(amount) from tmp.agg_big
group by city, category
grouping sets ((city, category), (city), (category), ());
```

**对比指标**：`explain` 里 A 有 4 个 `HashAggregate` + 4 次 `Exchange`，B 只有 1 次扫描 + 1 次 shuffle。

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 报表各维度相加 ≠ 总计 | 用了 `count(distinct)` 等不可加指标 | 逐个维度核对，看差额是否来自跨维度用户 | 汇总层存明细或 HLL；总计单独算 |
| 汇总行和明细行的 NULL 混在一起 | 没区分「真实 NULL」和「汇总 NULL」 | `grouping()` 检查 | 用 `grouping()` 标记 + `coalesce` 展示 |
| `CUBE` 跑崩 | 维度太多，组合爆炸 | 数一下 2^n | 改 `GROUPING SETS` 明确指定 |
| `collect_list` 结果顺序每次不同 | 分布式聚合顺序不确定 | 多次跑对比 | `distribute by + sort by` 预排序 |
| `explode` 后数据量暴涨 | 数组元素太多 | `max(size(arr))` 检查 | 限制数组长度或分批处理 |
| 单 reducer OOM | group by key 基数太小、数据集中 | 看 task 内存和输入行数 | 加盐打散；两阶段聚合 |
| `avg` 跨表合并后偏差 | 对平均值再求平均 | 对比 `sum/count` 结果 | 合并时用 `sum(sum)/sum(count)` |
| `count(distinct)` 极慢 | 需要传明细去重 | 看 shuffle 数据量 | 改 `approx_count_distinct` |
| `lateral view` 后行数变少 | 数组为 NULL 导致行消失 | 对比 explode 前后行数 | 用 `lateral view outer` |
| 聚合结果为空但表有数据 | `where` 条件类型不匹配 / NULL 过滤 | 先去掉聚合看明细 | 修 where 条件 |
| 小文件过多 | 聚合后写出的文件数 = 分区数 | `show partitions` / `dfs -ls` | `distribute by` 控制文件数 |

## 五、面试追问

> [!question] 1. `GROUPING SETS`、`ROLLUP`、`CUBE` 有什么区别？
> **一句话答法**：`GROUPING SETS` 自定义分组组合；`ROLLUP` 是层级递减（n+1 种）；`CUBE` 是全组合（2^n 种）。
> **追问陷阱**：「生产上你用哪个多」——`GROUPING SETS` 最多，因为可控；`CUBE` 维度一多就爆炸，很少直接用。

> [!question] 2. 多维聚合产生的 NULL 和真实的 NULL 怎么区分？
> **一句话答法**：用 `grouping(col)`，返回 1 表示这列被汇总掉了，返回 0 表示是真实值（哪怕值是 NULL）。
> **追问陷阱**：「报表展示怎么处理」——`case when grouping(city)=1 then '全部' else coalesce(city,'未知') end`。

> [!question] 3. 为什么 `count(distinct)` 不能跨维度相加？
> **一句话答法**：去重指标不可加。北京 100 万 UV + 上海 80 万 UV ≠ 全国 180 万，因为存在跨城用户被重复计数。
> **追问陷阱**：「那怎么算全国 UV」——必须对全量数据单独 `count(distinct)`，或用 HLL 草图做合并。

> [!question] 4. `collect_list` 和 `collect_set` 的区别？有什么风险？
> **一句话答法**：`collect_list` 保留重复（含 NULL，版本相关），`collect_set` 去重。两者都不保证顺序，且大基数时会 OOM。
> **追问陷阱**：「怎么保证顺序」——先 `distribute by key sort by` 再聚合，或者用 `sort_array` 排。

> [!question] 5. `explode` 有什么限制？
> **一句话答法**：不能和其他列直接 select（必须 `lateral view`）、不能在 where/group by 里直接用、会把行数放大。
> **追问陷阱**：「数组是 NULL 会怎样」——该行直接消失，要用 `lateral view outer` 保留。

> [!question] 6. `avg` 为什么不能直接对多个平均值再平均？
> **一句话答法**：分母不同。正确做法是 `sum(sum)/sum(count)`，即先还原成总金额和总行数再除。
> **追问陷阱**：「举个数」——100 行 avg=10，10 行 avg=20，直接平均得 15，正确是 1100/110 ≈ 10.9。

> [!question] 7. 一个 group by 任务卡在 99%，怎么排查？
> **一句话答法**：先看是不是倾斜（少数 task 输入特别大），再找热点 key（`group by key order by count desc`），然后按「加盐 / 两阶段聚合 / 提高并行度」处理。
> **追问陷阱**：「key 基数很小（比如只有 10 个）怎么办」——这种是「分区数不足」，不是倾斜，要加盐把 key 打散成 `key_0~key_9`，局部聚合后再合并。

> [!question] 8. map 端聚合（Map-side Aggregation）是什么？什么时候失效？
> **一句话答法**：map 端先做一次局部聚合，减少 shuffle 数据量。当聚合函数不可分解（如 `count(distinct)`、`collect_list`）或 key 基数极高时效果差。
> **追问陷阱**：「怎么确认开了」——Hive 看 `hive.map.aggr`，Spark 看执行计划里有没有 `HashAggregate(partial)`。

> [!question] 9. 什么是「半可加指标」？
> **一句话答法**：可以沿某些维度聚合、不能沿另一些维度聚合的指标。典型是库存——可以按时间累加（每天库存求和？其实不行），实际库存只能取「某时点的值」，跨门店可以求和，跨时间不能求和。
> **追问陷阱**：「还有哪些」——余额、在线人数、库存、状态类指标都属于此类，汇总层要存快照而不是累加。

> [!question] 10. 一条 SQL 里同时有 `group by` 和窗口函数，执行顺序是什么？
> **一句话答法**：先 `GROUP BY` 聚合，再在聚合结果上开窗。所以窗口里可以直接对 `sum(x)` 做 `rank()`。
> **追问陷阱**：「如果要对原始行开窗再聚合呢」——需要子查询：先在子查询里开窗，外层再 `group by`。

> [!question] 11. `having` 和 `where` 都能过滤，为什么不能都用 `where`？
> **一句话答法**：`where` 在聚合前执行，看不到聚合结果；`having` 在聚合后执行，能过滤 `sum/count` 等。语义上不可互换。
> **追问陷阱**：「性能上怎么选」——不依赖聚合的条件放 `where`，能提前减少数据量。

> [!question] 12. 怎么用一条 SQL 出「明细 + 小计 + 总计」？
> **一句话答法**：`GROUP BY ... GROUPING SETS ((维度...), (子维度...), ())`，配合 `grouping()` 标记层级。
> **追问陷阱**：「前端要怎么排序让总计在最后」——按 `grouping_id` 排序，`gid` 大的在后。

## 六、自测题

> [!question] 1.（单选）`grouping(city)` 返回 1 表示？
> A. city 的值是 NULL
> B. city 这一列被汇总掉了（当前行是该维度的上卷结果）
> C. city 有 1 个 distinct 值
> D. city 是主键

> [!question] 2.（单选）`ROLLUP(a, b, c)` 会生成几种分组组合？
> A. 3
> B. 4
> C. 8
> D. 6

> [!question] 3.（判断）`select city, count(distinct user_id) from t group by city with rollup` 的最后一行（总计行）的 UV，等于各城市 UV 之和。

> [!question] 4.（场景设计）业务要一张「区域-省份-城市」三级汇总的销售报表，同时还要「按品类」的汇总。数据量 5 亿行/天，要求一次扫描出结果。请写出 SQL 骨架，并说明为什么不用 `CUBE`。

> [!question] 5.（场景设计）你要把用户的「近 30 天行为序列」拼成一个字符串存到用户画像表。现在发现任务经常 OOM，且拼出来的顺序每次不一样。请分析原因并给出完整方案。

> [!success]- 答案与解析（点击展开）
> **1. B**
> `grouping(col)=1` 表示这一列在当前分组组合里被「汇总掉」了（即不在 `grouping sets` 的当前组合中），此时该列输出 NULL。`=0` 表示这是真实值。
>
> **2. B**
> `ROLLUP(a,b,c)` 生成 `(a,b,c)`, `(a,b)`, `(a)`, `()` 共 **4** 种 = n+1。
>
> **3. 错误**
> UV 是不可加指标。总计行的 UV 是「全部数据的去重用户数」，可能小于各城市 UV 之和（因为有跨城用户）。
> 注意：`with rollup` 在总计行会重新对全量数据做 `count(distinct)`，所以**结果本身是对的**，但它 ≠ 各城市之和。这一点容易混淆——错的是「以为可以相加」，不是「SQL 算错了」。
>
> **4. 参考 SQL**
> ```sql
> select
>     region, province, city, category,
>     sum(gmv) as gmv,
>     grouping_id(region, province, city, category) as gid
> from dwd.sales
> where dt = '2026-10-01'
> group by region, province, city, category
> grouping sets (
>     (region, province, city, category),   -- 最细：地区+品类
>     (region, province, city),             -- 城市级汇总
>     (region, province),                   -- 省级汇总
>     (region),                             -- 区域级汇总
>     (category),                           -- 品类汇总
>     ()                                    -- 总计
> );
> ```
> **为什么不用 CUBE**：4 个维度 CUBE 会产生 2^4 = 16 种组合，其中大部分业务不需要（如「只有 province 没有 region」这种不合理的层级）。数据量会放大 16 倍，5 亿行变成 80 亿行中间结果。`GROUPING SETS` 只出 6 种组合，数据量放大 6 倍，且组合语义清晰。
>
> **5. 原因分析**
> - **OOM**：`collect_list` 把每个用户 30 天的行为全部堆在内存里。如果某个用户是「刷单号」或「爬虫」，行为量可能是正常用户的 1000 倍，单个 key 就能撑爆 executor。
> - **顺序不定**：`collect_list` 在分布式聚合中，各 map 的局部结果合并顺序不确定，所以最终数组顺序不保证。
>
> **完整方案**
> ```sql
> -- 步骤1：过滤异常用户（关键！）
> -- 先统计每个用户的行为量，超过阈值的单独处理
> select user_id, count(*) as cnt
> from dwd.user_action
> where dt between '2026-09-25' and '2026-10-24'
> group by user_id
> having count(*) > 10000;   -- 超阈值用户单独走另一条链路
>
> -- 步骤2：正常用户，预排序后聚合，限制长度
> select
>     user_id,
>     concat_ws(',', collect_list(action)) as action_seq
> from (
>     select user_id, action, action_time
>     from dwd.user_action
>     where dt between '2026-09-25' and '2026-10-24'
>       and user_id not in (select user_id from tmp.abnormal_users)
>     distribute by user_id
>     sort by user_id, action_time desc
> ) t
> group by user_id;
>
> -- 步骤3：如果还是长，只取最近 N 条
> -- 用 row_number 先截断，再 collect_list
> select user_id, concat_ws(',', collect_list(action)) as action_seq
> from (
>     select user_id, action,
>            row_number() over (partition by user_id order by action_time desc) as rn
>     from dwd.user_action
>     where dt between '2026-09-25' and '2026-10-24'
> ) t
> where rn <= 50          -- 只保留最近 50 条
> group by user_id;
> ```
> **补充建议**：① 序列类字段不适合用字符串存，改用 `array<string>` 或 JSON；② 加监控：`max(size(collect_list(...)))` 超阈值告警；③ `distribute by + sort by` 是保证顺序的标准写法，但要注意它本身也有 shuffle 开销。
