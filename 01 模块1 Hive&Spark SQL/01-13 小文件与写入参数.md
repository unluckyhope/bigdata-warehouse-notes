# 01-13 小文件与写入参数

> [!abstract] 一句话结论
> 小文件不是「磁盘浪费」问题，而是**元数据和启动开销**问题：每个文件在 NameNode 里占约 150 字节内存，每次查询要为每个文件打开一次句柄、读一次 footer。
> 10 万个小文件（每个 1MB）比 100 个大文件（每个 1GB）慢 **10 倍以上**，而存储量完全一样。
> 治理的核心就一句话：**让「输出文件数 ≈ 总数据量 / 128~256MB」，并在写入时就用参数控制住，而不是事后补救。**

---

## 一、心智模型：小文件为什么慢

```
查询 1 个大文件（1GB）：
  打开文件 1 次 → 读 footer 1 次 → 顺序读 1GB
  开销：1 次 IO 建立 + 1GB 传输

查询 1000 个小文件（每个 1MB）：
  打开文件 1000 次 → 读 footer 1000 次 → 读 1000 × 1MB
  开销：1000 次 IO 建立 + 1000 次元数据查询 + 1GB 传输
```

**三层开销**：

| 层 | 开销 | 表现 |
| --- | --- | --- |
| **NameNode 内存** | 每个文件/目录约 150 字节 | 1 亿小文件 = 15GB 内存，NameNode 直接挂 |
| **任务启动** | 每个文件可能对应一个 task（或至少一次 open） | task 数暴涨，调度开销 > 计算开销 |
| **读取效率** | 每次 open 要读 footer（Parquet 的元数据） | 小文件的 footer 占比高，有效数据少 |

> [!important] 一个量化例子
> 100GB 数据：
> - 分成 100 个 1GB 文件 → 100 个 task，每个 task 启动开销 2 秒 → 200 秒开销
> - 分成 10 万个 1MB 文件 → 10 万个 task，每个启动 2 秒 → **55 小时纯开销**
> 这就是「同样的数据量，慢 10 倍」的来源。

## 二、核心知识点

### 2.1 小文件从哪来（五个源头）

| 源头 | 原因 | 典型场景 |
| --- | --- | --- |
| ① **分区过多** | 每个分区至少 1 个文件 | 按小时/按高基数列分区 |
| ② **reducer/分区数过多** | 每个 reducer 输出 1 个文件 | Spark 默认 200 分区，写 10 个分区 = 2000 文件 |
| ③ **数据量小但并行度高** | 每个 task 数据少，还是输出 1 个文件 | 上游过滤后只剩几百行，但有 200 个 task |
| ④ **频繁追加** | 每次 `insert into` 都新增文件 | 流式写入、小时级增量 |
| ⑤ **动态分区写入** | 每个分区 × 每个 reducer 都产生文件 | 动态分区 + 高并行度 |

```sql
-- 典型的「小文件制造机」
insert overwrite table dwd.order partition (dt)
select * from ods.order;    -- 200 个 reducer × 365 个分区 = 73000 个文件
```

### 2.2 文件大小的「黄金区间」

| 大小 | 评价 | 说明 |
| --- | --- | --- |
| < 16MB | ❌ 严重小文件 | 必须合并 |
| 16~64MB | ⚠️ 偏小 | 建议合并 |
| **128~256MB** | ✅ **理想** | 对齐 HDFS 块大小（128MB），一次 IO 读完 |
| 256MB~1GB | ✅ 可接受 | 大文件读取效率高 |
| > 1GB | ⚠️ 偏大 | 单 task 处理慢，可能 OOM；压缩格式可能不可切分 |

> [!note] 为什么是 128MB
> HDFS 默认块大小 128MB。一个文件如果正好 128MB，就是一个块，一次顺序读完成。
> 如果文件远小于块大小，会产生「一个块里有很多文件」的碎片问题；如果远大于，也没问题（多块顺序读），但单 task 处理量太大。

**计算公式**：

```
目标文件数 = 总数据量 / 目标文件大小（如 256MB）
```

例：100GB 数据 → 100GB / 256MB ≈ **400 个文件**。

### 2.3 Hive 的小文件治理参数

```sql
-- ① Map 端合并（只有 map 没有 reduce 的任务）
set hive.merge.mapfiles = true;

-- ② Map-Reduce 任务输出合并
set hive.merge.mapredfiles = true;

-- ③ 合并后的目标文件大小
set hive.merge.size.per.task = 256000000;        -- 256MB

-- ④ 平均文件小于这个值才触发合并
set hive.merge.smallfiles.avgsize = 16000000;    -- 16MB

-- ⑤ 控制 reducer 数（间接控制文件数）
set hive.exec.reducers.bytes.per.reducer = 256000000;
set hive.exec.reducers.max = 999;

-- ⑥ 动态分区时的文件数限制
set hive.exec.max.dynamic.partitions = 10000;
set hive.exec.max.dynamic.partitions.pernode = 1000;
```

> [!tip] 这几个参数的关系
> `hive.merge.mapfiles/mapredfiles` 是「事后合并」——任务跑完后，如果发现平均文件太小，再起一个 job 合并。
> `hive.exec.reducers.bytes.per.reducer` 是「事前控制」——直接算好 reducer 数，从源头减少文件。
> **两者配合最好**：先用 reducer 数控制，再用 merge 兜底。

### 2.4 Spark 的文件数控制

Spark 没有自动合并参数，必须手动控制：

```sql
-- ① 全局 shuffle 分区数（影响所有 shuffle 的输出文件数）
set spark.sql.shuffle.partitions = 400;

-- ② AQE 自动合并小分区（推荐）
set spark.sql.adaptive.enabled = true;
set spark.sql.adaptive.coalescePartitions.enabled = true;
set spark.sql.adaptive.advisoryPartitionSizeInBytes = 268435456;   -- 256MB

-- ③ 写入前显式重分区（最直接）
insert overwrite table dwd.order partition (dt = '2026-10-01')
select /*+ REPARTITION(10) */ order_id, amount
from ods.order where dt = '2026-10-01';

-- ④ coalesce（减少分区，不 shuffle，适合「分区太多」的情况）
select /*+ COALESCE(10) */ ... from ...;

-- ⑤ 用 distribute by 控制（Hive 兼容写法）
select ... from ... distribute by cast(rand() * 10 as int);
```

**`repartition` vs `coalesce`**：

| | `repartition(n)` | `coalesce(n)` |
| --- | --- | --- |
| 是否 shuffle | ✅ 是 | ❌ 否（只是合并相邻分区） |
| 能否增加分区 | ✅ | ❌ 只能减少 |
| 数据分布 | 均匀 | 可能不均（取决于原分区） |
| 适用 | 分区数不合适、需要均匀 | 只是想把小分区合并 |

> [!warning] `coalesce` 的坑
> `coalesce(1)` 会把所有数据集中到 1 个 task，大数据量下必 OOM。
> `coalesce(n)` 只是「把原来的 n 个以上分区合并成 n 个」，如果原分区本身不均匀，合并后也不均匀。
> **大数据量下优先用 `repartition`（有 shuffle 但均匀）**。

### 2.5 分区表的特殊处理

分区表的文件数 = **分区数 × 每个分区的文件数**，所以要分开控制：

```sql
-- ❌ 问题：200 个 shuffle 分区 × 365 个 dt 分区 = 73000 个文件
insert overwrite table dwd.order partition (dt)
select * from ods.order;

-- ✅ 方案一：先按分区列分发，再控制每个分区内的文件数
insert overwrite table dwd.order partition (dt)
select /*+ REPARTITION(365) */ * from ods.order;
-- 这样每个 dt 大致对应 1 个 shuffle 分区 → 每个分区 1 个文件

-- ✅ 方案二：Hive 写法
set hive.exec.reducers.bytes.per.reducer = 256000000;   -- 按数据量算 reducer
insert overwrite table dwd.order partition (dt)
select * from ods.order;

-- ✅ 方案三：分两步（先写临时表，再按分区写入）
insert overwrite table tmp.order_stage
select /*+ REPARTITION(365) */ * from ods.order;

insert overwrite table dwd.order partition (dt)
select * from tmp.order_stage distribute by dt;
```

> [!success] 核心思路
> **让 shuffle 分区数 ≈ 分区数**，这样每个 dt 分区大致对应一个 shuffle 分区，输出 1 个文件。
> 如果某个 dt 数据特别大（如双 11 当天），需要单独处理（`distribute by dt, cast(rand()*N as int)`）。

### 2.6 事后治理：合并小文件

**方案一：`insert overwrite` 重写（最常用）**

```sql
-- 把整个分区重写一遍，合并小文件
insert overwrite table dwd.order partition (dt = '2026-10-01')
select /*+ REPARTITION(10) */ * from dwd.order where dt = '2026-10-01';
```

**方案二：Hive 的 `concatenate`（仅 ORC）**

```sql
-- 只能用于 ORC 格式的表，且是非事务表
alter table dwd.order partition (dt='2026-10-01') concatenate;
```

**方案三：HAR / 归档（不推荐）**

```sql
-- 把多个小文件打成 HAR 归档，减少 NameNode 压力
-- 但查询性能没改善，且很多引擎不支持，不推荐
alter table dwd.order archive partition (dt='2026-10-01');
```

**方案四：定时合并任务**

```sql
-- 每天跑一次，合并「N 天前」的分区（避开当天的读写高峰）
-- 用脚本遍历分区，对每个分区执行重写
```

**方案五：写入时就避免（最优）**

见 2.4 和 2.5。**事后治理的成本远高于事前控制**——重写一遍要读一遍、写一遍，还占资源。

### 2.7 存储格式与压缩的影响

| 格式 | 特点 | 小文件敏感度 |
| --- | --- | --- |
| **Parquet** | 列式，压缩率高，支持谓词下推 | 高（每个文件有 footer） |
| **ORC** | 列式，压缩率更高，支持索引 | 高 |
| **TextFile** | 行式，无压缩，可读 | 中（但存储成本高） |
| **Avro** | 行式，schema 演进好 | 中 |
| **JSON** | 行式，可读性最好 | 高（体积大） |

**压缩对比**：

| 压缩 | 压缩率 | 解压速度 | 可切分 | 适用 |
| --- | --- | --- | --- | --- |
| snappy | 中 | 快 | ❌ | Parquet 默认，平衡 |
| gzip | 高 | 慢 | ❌ | 归档 |
| zstd | 高 | 中 | ❌ | 存储敏感场景 |
| lzo | 中 | 快 | ✅（需索引） | 需要切分的大文件 |
| bzip2 | 最高 | 最慢 | ✅ | 极少用 |

> [!warning] 不可切分格式的「大文件陷阱」
> gzip 压缩的文件**不可切分**，一个 1GB 的 gzip 文件只能由一个 task 处理，无法并行。
> **所以「大文件」也不是越大越好**——如果用不可切分压缩，文件应控制在 128~256MB（一个块）。
> Parquet/ORC 内部有 row group，天然可切分，所以文件可以更大。

```sql
-- ③ 用 SQL 统计（如果表有 HDFS 统计信息）

-- ④ Spark 里看输入文件数
-- 执行计划里 FileScan 节点的 "number of files"
```

**监控指标**：

| 指标 | 阈值 | 说明 |
| --- | --- | --- |
| 单分区文件数 | > 100 告警 | 取决于数据量 |
| 平均文件大小 | < 64MB 告警 | 偏小 |
| 表总文件数 | > 10 万告警 | 元数据压力 |
| 单文件大小 | > 2GB 告警 | 可能不可切分 |

## 三、动手实验

### 3.1 制造小文件（观察现象）

```sql
-- 建表
drop table if exists tmp.small_file_lab;
create table tmp.small_file_lab (id int, val string)
partitioned by (dt string) stored as parquet;

-- 制造 200 个 shuffle 分区 × 3 个 dt 分区
set spark.sql.shuffle.partitions = 200;
insert overwrite table tmp.small_file_lab partition (dt)
select id, val, dt
from (
    select 1 as id, 'x' as val, '2026-10-01' as dt
    union all select 2, 'y', '2026-10-02'
    union all select 3, 'z', '2026-10-03'
) t
distribute by id;   -- 只有 3 个 distinct id，但可能产生很多文件

-- 看文件数
dfs -count /user/hive/warehouse/tmp.db/small_file_lab/dt=2026-10-01;
dfs -ls /user/hive/warehouse/tmp.db/small_file_lab/dt=2026-10-01 | wc -l;
```

> [!tip] 制造小文件的更狠方法
> ```sql
> -- 每个 dt 分区都写 200 个文件
> set spark.sql.shuffle.partitions = 200;
> insert overwrite table tmp.small_file_lab partition (dt)
> select /*+ REPARTITION(200) */ id, val, dt from (...) t;
> ```

### 3.2 实验一：合并前后的查询耗时对比

```sql
-- A：小文件状态（假设有 200 个文件，每个 1KB）
select count(*) from tmp.small_file_lab where dt = '2026-10-01';

-- B：合并成 1 个文件
insert overwrite table tmp.small_file_lab partition (dt = '2026-10-01')
select /*+ COALESCE(1) */ id, val from tmp.small_file_lab where dt = '2026-10-01';

select count(*) from tmp.small_file_lab where dt = '2026-10-01';
```

**看什么**：Spark UI 里两个查询的 task 数（200 vs 1）和总耗时。虽然数据量很小，但 task 启动开销的差异仍然可见。

### 3.3 实验二：`repartition` vs `coalesce`

```sql
-- A：repartition（有 shuffle，均匀）
insert overwrite table tmp.small_file_lab partition (dt = '2026-10-02')
select /*+ REPARTITION(5) */ id, val from tmp.small_file_lab where dt = '2026-10-02';

-- B：coalesce（无 shuffle，可能不均）
insert overwrite table tmp.small_file_lab partition (dt = '2026-10-03')
select /*+ COALESCE(5) */ id, val from tmp.small_file_lab where dt = '2026-10-03';

-- 对比文件大小分布
dfs -du -h /user/hive/warehouse/tmp.db/small_file_lab/dt=2026-10-02;
dfs -du -h /user/hive/warehouse/tmp.db/small_file_lab/dt=2026-10-03;
```

### 3.4 实验三：分区数 × shuffle 分区数

```sql
-- 危险示范：3 个 dt 分区 × 200 shuffle 分区
set spark.sql.shuffle.partitions = 200;
insert overwrite table tmp.small_file_lab partition (dt)
select id, val, dt from (select 1 id, 'a' val, '2026-10-01' dt) t;

-- 文件数 ≈ 200（因为数据都去了 1 个 dt，但 shuffle 是 200 分区）
-- 实际可能是 1~200，取决于数据分布

-- 改进：让 shuffle 分区数 ≈ 分区数
set spark.sql.shuffle.partitions = 3;
insert overwrite table tmp.small_file_lab partition (dt)
select id, val, dt from (select 1 id, 'a' val, '2026-10-01' dt) t;
```

### 3.5 实验四：查看文件统计

```sql
-- Hive
show table extended like 'small_file_lab' partition (dt='2026-10-01');

-- 或用 analyze
analyze table tmp.small_file_lab partition (dt='2026-10-01') compute statistics;
desc formatted tmp.small_file_lab partition (dt='2026-10-01');
-- 看 numFiles、totalSize
```

## 四、生产坑点清单

| 现象 | 根因 | 排查手段 | 修复方案 |
| --- | --- | --- | --- |
| 查询很慢但数据量不大 | 小文件多，task 启动开销大 | `dfs -count` 看文件数 | 合并小文件 |
| NameNode 内存告警 | 文件/目录数过多 | `hdfs dfsadmin -report` | 合并；减少分区 |
| 写入任务最后几个 task 很慢 | 文件数太多，close 开销大 | 看 task 时长分布 | 减少 shuffle 分区 |
| 分区文件数 = 200 × 分区数 | shuffle 分区数没跟着调 | `dfs -ls` 数文件 | 调 `shuffle.partitions` |
| 合并后查询还是慢 | 只合并了文件数，但数据量没变 | 对比合并前后耗时 | 检查是否真的合并（文件数） |
| `concatenate` 报错 | 表不是 ORC 或开启了事务 | 看报错 | 改用 `insert overwrite` |
| 单文件几个 GB，查询慢 | 文件太大，单 task 处理不过来 | 看文件大小 | 拆分；确认压缩格式可切分 |
| gzip 大文件无法并行 | 不可切分 | 看 task 数 = 1 | 改 snappy/parquet；或控制文件大小 |
| 动态分区产生海量小文件 | 分区数 × reducer 数 | `show partitions` + 文件数 | 减少分区；控制 reducer |
| 流式写入持续产生小文件 | 每次微批都写文件 | 看文件增长趋势 | 定期合并；或换 Hudi/Iceberg |

## 五、面试追问

> [!question] 1. 小文件为什么会影响性能？
> **一句话答法**：三层开销——NameNode 内存（每文件约 150 字节）、task 启动开销（每文件可能一个 task）、读取开销（每次 open 要读 footer）。
> **追问陷阱**：「数据量一样，为什么慢」——慢在「建立连接 + 读元数据」的次数，不在数据传输量。

> [!question] 2. 文件多大合适？
> **一句话答法**：128~256MB，对齐 HDFS 块大小。太大单 task 处理慢，太小则元数据开销大。
> **追问陷阱**：「如果是 gzip 压缩呢」——gzip 不可切分，文件必须控制在 128~256MB（一个块），否则无法并行。

> [!question] 3. 小文件是怎么产生的？
> **一句话答法**：五个源头——分区过多、shuffle 分区数过多、数据量小但并行度高、频繁追加、动态分区写入。
> **追问陷阱**：「最常见的是哪个」——分区数 × shuffle 分区数，尤其是动态分区写入时。

> [!question] 4. Hive 怎么自动合并小文件？
> **一句话答法**：`hive.merge.mapfiles`（纯 map 任务）+ `hive.merge.mapredfiles`（MR 任务）+ `hive.merge.size.per.task`（目标大小）+ `hive.merge.smallfiles.avgsize`（触发阈值）。
> **追问陷阱**：「Spark 有吗」——没有自动合并，要靠 `repartition`/`coalesce` 或 AQE 的 `coalescePartitions`。

> [!question] 5. `repartition` 和 `coalesce` 的区别？
> **一句话答法**：`repartition` 有 shuffle，能增能减，数据均匀；`coalesce` 无 shuffle，只能减少，可能不均。
> **追问陷阱**：「`coalesce(1)` 有什么风险」——所有数据集中到一个 task，大数据量必 OOM。

> [!question] 6. 分区表怎么控制文件数？
> **一句话答法**：让 shuffle 分区数 ≈ 分区数，这样每个分区大致对应一个 shuffle 分区，输出 1 个文件；数据量特别大的分区单独加盐打散。
> **追问陷阱**：「为什么是 200 × 365」——Spark 默认 200 个 shuffle 分区，每个分区写 365 个 dt，就是 73000 个文件。

> [!question] 7. 已经产生的小文件怎么治理？
> **一句话答法**：四种方案——`insert overwrite` 重写（通用）、`concatenate`（仅 ORC）、定时合并任务、换 Hudi/Iceberg（自动 compaction）。
> **追问陷阱**：「重写的代价」——读一遍 + 写一遍，占资源；所以要在低峰期做，且优先「事前控制」。

> [!question] 8. 为什么说「事后治理不如事前控制」？
> **一句话答法**：事后治理要重写数据（读+写），成本等于重跑一次任务；事前控制只是调整分区数，零额外成本。
> **追问陷阱**：「那还需要事后治理吗」——需要，作为兜底（比如上游数据量突变导致文件数异常）。

> [!question] 9. Parquet 和 ORC 有什么区别？
> **一句话答法**：都是列式存储，ORC 压缩率略高、对 Hive 更友好（支持 ACID），Parquet 生态更广（Spark、Presto、Hive 都支持好）。
> **追问陷阱**：「怎么选」——Hive 为主选 ORC（能用 ACID 和 concatenate），Spark/多引擎选 Parquet。

> [!question] 10. 大文件有什么问题？
> **一句话答法**：单 task 处理慢（无法并行）、可能 OOM；如果压缩格式不可切分（gzip），完全无法并行。
> **追问陷阱**：「多大算大」——超过 1GB 要注意；超过 2GB 且不可切分就是问题。

> [!question] 11. 怎么监控小文件问题？
> **一句话答法**：监控四个指标——单分区文件数、平均文件大小、表总文件数、单文件最大 size，设阈值告警。
> **追问陷阱**：「用什么工具」——HDFS 的 `fsck`、`dfs -count`，或数据平台的元数据服务。

> [!question] 12. 流式写入怎么避免小文件？
> **一句话答法**：三种方案——微批合并（攒够一定量再写）、定期 compaction 任务、用支持自动 compaction 的表格式（Hudi/Iceberg/Delta）。
> **追问陷阱**：「Hudi 怎么做」——Hudi 有 inline/async compaction，会自动合并小文件。

## 六、自测题

> [!question] 1.（单选）100GB 数据，目标文件大小 256MB，理想文件数约为？
> A. 100
> B. 400
> C. 1000
> D. 256

> [!question] 2.（单选）Spark 中 `coalesce(1)` 的主要风险是？
> A. 数据丢失
> B. 所有数据集中到一个 task，可能 OOM
> C. 产生更多小文件
> D. 无法执行

> [!question] 3.（判断）`repartition` 和 `coalesce` 都会触发 shuffle。

> [!question] 4.（场景设计）一个每日任务写 `dwd.order` 表（按 `dt` 分区，365 个分区/年），发现每个分区有 200 个文件，每个文件约 500KB。请分析原因并给出完整的治理方案（包括事前和事后）。

> [!question] 5.（场景设计）你的团队有一张 3 年历史的表，累计 50 万个小文件（平均 2MB），现在查询很慢，NameNode 内存也告警。请设计一个治理方案，要求不影响线上业务，并说明如何验证效果。

> [!success]- 答案与解析（点击展开）
> **1. B**
> 100GB / 256MB = 100 × 1024 / 256 = **400** 个文件。
>
> **2. B**
> `coalesce(1)` 把所有分区合并成 1 个，数据全进一个 task，大数据量下必然 OOM 或极慢。
>
> **3. 错误**
> `repartition` 会 shuffle（重新分布数据）；`coalesce` **不 shuffle**，只是把相邻分区合并（所以只能减少分区数，且可能不均匀）。
>
> **4. 原因分析**
> - 每个分区 200 个文件 → **Spark 的 `spark.sql.shuffle.partitions` 默认是 200**
> - 每个文件 500KB → 单分区数据量约 100MB，但被切成了 200 份，每份 500KB
> - 根因：**shuffle 分区数（200）远大于数据量所需（100MB / 256MB < 1）**
>
> **治理方案**
> **事前（治本）**
> ```sql
> -- 方案1：按数据量设置 shuffle 分区数
> -- 假设每天数据量 100GB，256MB/文件 → 400 个分区
> set spark.sql.shuffle.partitions = 400;
>
> -- 方案2（更好）：开 AQE，让它自动合并
> set spark.sql.adaptive.enabled = true;
> set spark.sql.adaptive.coalescePartitions.enabled = true;
> set spark.sql.adaptive.advisoryPartitionSizeInBytes = 268435456;   -- 256MB
>
> -- 方案3：写入前显式控制
> insert overwrite table dwd.order partition (dt)
> select /*+ REPARTITION(400) */ ... from ods.order;
> ```
>
> **事后（兜底）**
> ```sql
> -- 对已有分区重写合并
> insert overwrite table dwd.order partition (dt = '2026-10-01')
> select /*+ REPARTITION(1) */ * from dwd.order where dt = '2026-10-01';
> -- 单分区 100MB，1 个文件刚好
> ```
>
> **补充**：这个例子说明「200 个文件 × 500KB」的典型症状——**分区数（200）和数据量不匹配**。诊断时先算「单分区数据量 / 256MB」，得到理想文件数，再对比实际文件数。
>
> **5. 治理方案（不影响线上）**
> **第 1 步：评估与分级**
> ```sql
> -- 统计每个分区的文件数和大小，找出最严重的
> -- 按「文件数 × 平均大小」排序，优先处理「文件多且小」的分区
> ```
> 分级：
> - P0：文件数 > 5000 的分区（NameNode 压力最大）
> - P1：文件数 1000~5000
> - P2：文件数 < 1000
>
> **第 2 步：选择治理窗口**
> - 低峰期（凌晨 2:00~6:00）
> - 避开上游写入时间
> - 分批处理（每天处理 30 天数据，不要一次全跑）
>
> **第 3 步：灰度验证（关键）**
> ```sql
> -- 先在一个测试分区上做，验证正确性
> -- 1. 备份原分区
> create table tmp.order_backup_20261001 as
> select * from dwd.order where dt = '2026-10-01';
>
> -- 2. 重写
> insert overwrite table dwd.order partition (dt = '2026-10-01')
> select /*+ REPARTITION(4) */ * from dwd.order where dt = '2026-10-01';
>
> -- 3. 对比（行数、金额、哈希）
> select
>     (select count(*) from dwd.order where dt='2026-10-01') as new_cnt,
>     (select count(*) from tmp.order_backup_20261001) as old_cnt,
>     (select sum(amount) from dwd.order where dt='2026-10-01') as new_sum,
>     (select sum(amount) from tmp.order_backup_20261001) as old_sum;
> ```
>
> **第 4 步：批量执行**
> - 用脚本遍历分区，逐个重写
> - 每个分区处理完立即校验（行数 + 金额）
> - 失败则回滚（从备份恢复）
>
> **第 5 步：长期机制**
> - 在写入任务里加 `repartition` 或开 AQE（防新增）
> - 加监控：单分区文件数、平均文件大小，超阈值告警
> - 加定期合并任务（每周合并一次「7 天前」的分区）
>
> **如何验证效果**
> | 指标 | 治理前 | 治理后（预期） |
> | --- | --- | --- |
> | 总文件数 | 50 万 | ~2 万（50万/25） |
> | 平均文件大小 | 2MB | ~50MB（需进一步合并到 128MB+） |
> | NameNode 内存 | 告警 | 下降 90% |
> | 典型查询耗时 | 10 分钟 | 1 分钟 |
> | 单分区文件数 | 5000 | 4 |
>
> **注意**：如果 3 年数据总量很大（比如 500TB），一次性全合并成本太高。可以只合并「近 1 年」的热数据，冷数据保持原样（或用归档存储）。
